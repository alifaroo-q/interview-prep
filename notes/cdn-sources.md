RFC section numbers are from the rfc-editor.org .txt files.

## 1. Caching rules

Base URLs: RFC 9111 https://www.rfc-editor.org/rfc/rfc9111 ; RFC 9110 https://www.rfc-editor.org/rfc/rfc9110 ; RFC 5861 https://www.rfc-editor.org/rfc/rfc5861

- Cacheable methods. RFC 9110 s9.2.3 (Safe/idempotent/cacheable) text near "9.3": "This specification defines caching semantics for GET, HEAD, and POST, although the overwhelming majority of cache implementations only support GET and HEAD."
- POST condition. RFC 9110 s9.3.3 (POST): "Responses to POST requests are only cacheable when they include explicit freshness information (see Section 4.2.1 of [CACHING]) and a Content-Location header field that has the same value as the POST's target URI". "A cached POST response can be reused to satisfy a later GET or HEAD request." A POST request cannot be satisfied from a cached POST response.
- What a cache may store. RFC 9111 s3: "A cache MUST NOT store a response to a request unless" ... the no-store directive is absent; for shared caches the `private` directive is absent; "if the cache is shared: the Authorization header field is not present in the request ... or a response directive is present that explicitly allows shared caching"; and the response has at least one of: `public`, `private` (private cache only), Expires, `max-age`, `s-maxage` (shared), a cache extension, or "a status code that is defined as heuristically cacheable".
- Authorization. RFC 9111 s5.2.2.2 (must-revalidate), s5.2.2.9 (public), s5.2.2.10 (s-maxage): each "permits a shared cache to reuse a response to a request containing an Authorization header field". So a shared cache may store such a response only with must-revalidate, public or s-maxage.
- Set-Cookie. RFC 9111 s7 (Security): "the Set-Cookie response header field [COOKIE] does not inhibit caching; a cacheable response with a Set-Cookie header field can be (and often is) used to satisfy subsequent requests to caches." Servers "are encouraged to emit appropriate Cache-Control response header fields." (So the RFC allows caching; nginx does not, see s4.)
- max-age (s5.2.2.1): "the response is to be considered stale after its age is greater than the specified number of seconds."
- s-maxage (s5.2.2.10): "for a shared cache, the maximum age specified by this directive overrides the maximum age specified by either the max-age directive or the Expires header field." It also implies proxy-revalidate for shared caches.
- private (s5.2.2.7): "a shared cache MUST NOT store the response (i.e., the response is intended for a single user). It also indicates that a private cache MAY store the response".
- public (s5.2.2.9): "a cache MAY store the response even if it would otherwise be prohibited".
- no-store (s5.2.2.5): "a cache MUST NOT store any part of either the immediate request or the response and MUST NOT use the response to satisfy any other request."
- no-cache (s5.2.2.4): "the response MUST NOT be used to satisfy any other request without forwarding it for validation and receiving a successful response". It may be stored. Note in RFC: the qualified form (with field names) "is not widely implemented".
- must-revalidate (s5.2.2.2): once stale, "a cache MUST NOT reuse that response to satisfy another request until it has been successfully validated by the origin". If disconnected, the cache "MUST generate an error response" (SHOULD be 504).
- Age (s5.1): "conveys the sender's estimate of the time since the response was generated or successfully validated at the origin server." "The presence of an Age header field implies that the response was not generated or validated by the origin server for this request."
- Vary / cache key (s4.1): a cache "MUST NOT use that stored response without revalidation unless all the presented request header fields nominated by that Vary field value match those fields in the original request". s2 says many caches "only cache GET responses and therefore only use the URI as the cache key", and Vary adds request headers to the key.
- Heuristic freshness (s4.2.2): "caches are encouraged to use a heuristic expiration value that is no more than some fraction of the interval since that time [Last-Modified]. A typical setting of this fraction might be 10%." Also: "A cache MUST NOT use heuristics to determine freshness when an explicit expiration time is present". The 10% is an example ("might be"), not a rule.
- Conditional requests. RFC 9110 s13.1.2 If-None-Match: "When a client desires to update one or more stored responses that have entity tags, the client SHOULD generate an If-None-Match header field ... this allows recipient servers to send a 304 (Not Modified) response". s15.4.5: 304 "indicates that a conditional GET or HEAD request has been received and would have resulted in a 200 (OK) response if it were not for the fact that the condition evaluated to false". ETag: s8.8.3, "an opaque validator".
- stale-while-revalidate (RFC 5861 s3): "caches MAY serve the response in which it appears after it becomes stale, up to the indicated number of seconds." Example: `Cache-Control: max-age=600, stale-while-revalidate=30` = fresh 600 s, may be served stale for 30 s more while "an asynchronous validation is attempted".
- stale-if-error (RFC 5861 s4): "when an error is encountered, a cached stale response MAY be used". Error means "any situation that would result in a 500, 502, 503, or 504 HTTP response status code". RFC 5861 is dated May 2010 and still mentions a "warning header"; RFC 9111 later removed Warning. Treat that sentence as old.

## 2. Connection cost

- TCP three-way handshake. RFC 793 text: "three-way hand shake" (https://www.rfc-editor.org/rfc/rfc793). The "1 RTT before data" figure is my reading of SYN, SYN-ACK, ACK. No source quote found that says "1 RTT". Mark as derived.
- TLS 1.2 = 2 RTT. Cloudflare blog "RFC 8446 aka TLS 1.3" https://blog.cloudflare.com/rfc-8446-aka-tls-1-3/ : "When establishing a new connection to a server that you haven't seen before, it takes two round-trips before data can be sent on the connection." That sentence is for TLS 1.2 and counts TLS only, not TCP. Also: "the TLS 1.3 handshake latency [can] drop from two round-trips to only one round-trip".
- TLS 1.3 1-RTT. Same blog, "1-RTT mode": the client sends key shares in the first message, so "the server can learn the shared secret and send encrypted data one round trip earlier". RFC 8446 s1.2 (list of changes) says 0-RTT mode was added, "saving a round trip at connection setup for some application data, at the cost of certain security properties." I did not find the literal words "full handshake is 1-RTT" in RFC 8446.
- 0-RTT. RFC 8446 s2.3 (0-RTT Data). Weaker properties: "This data is not forward secret" and "There are no guarantees of non-replay between connections." s8 "0-RTT and Anti-Replay": "TLS does not provide inherent replay protections for 0-RTT data." Appendix E.5: applications must be "engineered to be safe under replay (minimally, this means idempotent ...)". s8 text: clients "MUST only send early data which they deem safe to be replayed". Server defences: s8.1 single-use tickets, s8.2 ClientHello recording, s8.3 freshness checks. HTTP side: RFC 8470 defines status "425 (Too Early)" (https://www.rfc-editor.org/rfc/rfc8470).
- Cloudflare on 0-RTT replay (same blog): "If an attacker captures a 0-RTT packet that was sent to server, they can replay it". Safe use: "HTTP GET requests are supposed to be safe".
- Initial congestion window. RFC 6928 s1: "This document proposes to raise the upper bound on TCP's initial window (IW) to 10 segments (maximum 14600 B)." RFC 6928 is Experimental/proposal text ("proposes an experiment"). RFC 5681 s3.1 limits IW to 2-4 segments by SMSS; RFC 6928 raises it.
- Slow start (RFC 5681 s3.1): "During slow start, a TCP increments cwnd by at most SMSS bytes for each ACK received that cumulatively acknowledges new data. Slow start ends when cwnd exceeds ssthresh ... or when congestion is observed."

## 3. HTTP versions

- HTTP/1.1 persistent (RFC 9112 s9.3): "HTTP/1.1 defaults to the use of 'persistent connections', allowing multiple requests and responses to be carried over a single connection."
- Pipelining (RFC 9112 s9.3.2): client may send requests "without waiting for each response"; the server "MUST send the corresponding responses in the same order that the requests were received". RFC 9113 s1: HTTP/1.1 pipelining "only partially addressed request concurrency and still suffers from application-layer head-of-line blocking. Therefore, HTTP/1.0 and HTTP/1.1 clients use multiple connections".
- HTTP/2 streams (RFC 9113 s5): "A 'stream' is an independent, bidirectional sequence of frames exchanged between the client and server within an HTTP/2 connection." "A single HTTP/2 connection can contain multiple concurrently open streams, with either endpoint interleaving frames from multiple streams."
- SETTINGS_MAX_CONCURRENT_STREAMS (RFC 9113 s6.5.2): "Initially, there is no limit to this value. It is recommended that this value be no smaller than 100, so as to not unnecessarily limit parallelism."
- TCP HOL (RFC 9113 s1): "TCP head-of-line blocking is not addressed by this protocol." RFC 9114 s1.1: "a lost or reordered packet causes all active transactions to experience a stall regardless of whether that transaction was directly impacted by the lost packet."
- HTTP/3 (RFC 9114 s1.2): "Streams are independent of each other, so one stream that is blocked or suffers packet loss does not prevent progress on other streams."
- QUIC loss (RFC 9000 s13, packetization): "When a packet loss occurs, only streams with data in that packet are blocked waiting for a retransmission". If one packet holds data of many streams, losing it blocks all of them.
- QUIC connection ID (RFC 9000 s5.1): "The primary function of a connection ID is to ensure that changes in addressing at lower protocol layers (UDP, IP) do not cause packets for a QUIC connection to be delivered to the wrong endpoint." Migration: s9.

### Coordinator extra question: keepalive default, proxy_http_version, HTTP/2 upstream
- Default of upstream `keepalive` now: `Default: keepalive 32 local;` Quote: "Since 1.29.7, keepalive connections are enabled by default, with a default limit of 32 connections per each worker process." Also: "Since 1.29.7, by default the cache for connections is activated and these connections are not shared between different locations."

- Same release: "Change: now ngx_http_proxy_module supports keepalive by default; the default value for "proxy_http_version" is "1.1"; the "Connection" proxy header is not sent by default anymore."
- `proxy_http_version` docs: syntax `1.0 | 1.1 | 2`; "Default: proxy_http_version 1.1;" "Since 1.29.7, version 1.1 is used by default. Before 1.29.7, version 1.0 was used by default. Version 1.1 or 2 (1.29.4) is recommended for use with keepalive connections and NTLM authentication. Version 2 requires the ngx_http_v2_module module."
- HTTP/2 to upstream added in 1.29.4 (09 Dec 2025). CHANGES: "Feature: the ngx_http_proxy_module supports HTTP/2." nginx community post (https://community.nginx.org/t/nginx-1-29-4-mainline-released/8513): "Support for HTTP/2 protocol to upstreams". So yes, `proxy_http_version 2` exists in 1.31.6.
- Keepalive "max idle, not a total limit" (upstream docs, keepalive): "The connections parameter sets the maximum number of idle keepalive connections to upstream servers that are preserved in the cache of each worker process. When this number is exceeded, the least recently used connections are closed. The zero value disables keepalive connections to upstream servers." and "It should be particularly noted that the keepalive directive does not limit the total number of connections to upstream servers that an nginx worker process can open." So `keepalive 0;` is valid and turns reuse off. Docs for HTTP: "the proxy_http_version directive should be "1.1" (by default since 1.29.7) or set to "2" and the "Connection" header field should be cleared."
- Multiplexing on HTTP/2 upstream: NOT answered by a primary source. The nginx docs I read do not say whether one upstream HTTP/2 connection carries many requests at once. A WebSearch summary (secondary, snippet only, not verified) said nginx's HTTP/2-to-backend does not multiplex yet. CHANGES line (1.29.x): "Bugfix: connections with HTTP/2 backends might not be cached when using the "proxy_set_body" or "proxy_pass_request_body" directives" shows HTTP/2 upstream connections go through the keepalive cache. Test it in the lab before claiming either way.
- Compare: Cloudflare to origin does multiplex HTTP/2 (see s5).
- upstream `keepalive_timeout` (upstream context, 1.15.3): "Default: keepalive_timeout 60s;" "Sets a timeout during which an idle keepalive connection to an upstream server will stay open."
- upstream `keepalive_requests` (1.15.3): "Default: keepalive_requests 1000;" "Sets the maximum number of requests that can be served through one keepalive connection. After the maximum number of requests is made, the connection is closed."
- upstream `keepalive_time` (1.19.10): default 1h. "Limits the maximum time during which requests can be processed through one keepalive connection."

### Caching directives (proxy module)
- `proxy_cache_lock` (default off, 1.1.12): "only one request at a time will be allowed to populate a new cache element ... Other requests of the same cache element will either wait for a response to appear in the cache or the cache lock for this element to be released, up to the time set by the proxy_cache_lock_timeout directive."
- `proxy_cache_lock_timeout` (default 5s): "When the time expires, the request will be passed to the proxied server, however, the response will not be cached." (Before 1.7.8 it could be cached.)
- `proxy_cache_lock_age` (default 5s): "If the last request passed to the proxied server for populating a new cache element has not completed for the specified time, one more request may be passed to the proxied server."
- `proxy_cache_use_stale` (default off) values: error, timeout, invalid_header, updating, http_500, http_502, http_503, http_504, http_403, http_404, http_429, off. "the updating parameter permits using a stale cached response if it is currently being updated. This allows minimizing the number of accesses to proxied servers when updating cached data." "The error parameter also permits using a stale cached response if a proxied server to process a request cannot be selected." The "stale-while-revalidate" and "stale-if-error" Cache-Control extensions are honoured (since 1.11.10) with "lower priority than ... the directive parameters". "To minimize the number of accesses to proxied servers when populating a new cache element, the proxy_cache_lock directive can be used."
- `proxy_cache_background_update` (default off, 1.11.10): "Allows starting a background subrequest to update an expired cache item, while a stale cached response is returned to the client. Note that it is necessary to allow the usage of a stale cached response when it is being updated." (needs `proxy_cache_use_stale updating`.)
- `proxy_cache_revalidate` (default off, 1.5.7): "Enables revalidation of expired cache items using conditional requests with the "If-Modified-Since" and "If-None-Match" header fields."
- `proxy_cache_methods` (default `GET HEAD`): "GET" and "HEAD" methods are always added to the list. POST can be added.
- `$upstream_cache_status` (upstream module vars, 0.8.3): "The status can be either "MISS", "BYPASS", "EXPIRED", "STALE", "UPDATING", "REVALIDATED", or "HIT"."
- Set-Cookie / Vary (proxy_cache_valid section): "If the header includes the "Set-Cookie" field, such a response will not be cached. If the header includes the "Vary" field with the special value "*", such a response will not be cached (1.7.7)." (This is stricter than RFC 9111 s7.) "parameters of caching may be set in the header fields "Expires" or "Cache-Control"" and `X-Accel-Expires` has priority.
- `proxy_ignore_headers`: "The following fields can be ignored: "X-Accel-Redirect", "X-Accel-Expires", "X-Accel-Limit-Rate" (1.1.6), "X-Accel-Buffering" (1.1.6), "X-Accel-Charset" (1.1.6), "Expires", "Cache-Control", "Set-Cookie" (0.8.44), and "Vary" (1.7.7)." If not ignored, `X-Accel-Expires`, `Expires`, `Cache-Control`, `Set-Cookie`, `Vary` "set the parameters of response caching".
- Cache-Control private / no-store in nginx: the proxy module page I read does NOT mention `private`, `no-store` or `no-cache` by name (searched the page text). Not confirmed from nginx docs. Verify in the lab (nginx source honours them, but I have no doc quote).

### Status, variables, rate limit
- `stub_status` (https://nginx.org/en/docs/http/ngx_http_stub_status_module.html): "accepts: The total number of accepted client connections. handled: The total number of handled connections. Generally, the parameter value is the same as accepts unless some resource limits have been reached (for example, the worker_connections limit). requests: The total number of client requests." Also Active connections, Reading, Writing, Waiting ("idle client connections waiting for a request"). Not built by default: needs `--with-http_stub_status_module`. Example from docs: `16630948 16630948 31070465` (accepts handled requests).
- Core vars (ngx_http_core_module): `$connection` = "connection serial number"; `$connection_requests` = "current number of requests made through a connection"; `$connection_time` = "connection time in seconds with a milliseconds resolution (1.19.10)".
- `limit_req` (https://nginx.org/en/docs/http/ngx_http_limit_req_module.html): "The limitation is done using the "leaky bucket" method." "If the requests rate exceeds the rate configured for a zone, their processing is delayed such that requests are processed at a defined rate. Excessive requests are delayed until their number exceeds the maximum burst size in which case the request is terminated with an error. By default, the maximum burst size is equal to zero." `nodelay` skips the delay. Example in docs: `limit_req_zone $binary_remote_addr zone=one:10m rate=1r/s;` with `burst=5`.

## 5. CDN to origin

### CloudFront (AWS docs)
- Keep-alive timeout: https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DownloadDistValuesOrigin.html : "The keep-alive timeout is how long (in seconds) CloudFront tries to maintain a connection to your custom origin after it gets the last packet of a response. Maintaining a persistent connection saves the time that is required to re-establish the TCP connection and perform another TLS handshake". "For response timeout, the default is 30 seconds. For keep-alive timeout, the default is 5 seconds." "your origin must be configured to allow persistent connections" for it to have effect.
- Quotas page https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cloudfront-limits.html : keep-alive timeout per origin "1-300 seconds" (with "Request a higher quota"); response timeout per origin "1-120 seconds"; connection timeout per origin 1-10 seconds. So the 300 s max is a quota (raise by request, not a hard cap in the table).
- HTTP version to origin: https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/RequestAndResponseBehaviorCustomOrigin.html : "CloudFront forwards requests to your custom origin using HTTP/1.1."
- Request collapsing (same page): "if there are simultaneous requests for the same object ... CloudFront pauses before forwarding the additional requests to the origin ... CloudFront sends the response from the original request to all the requests that it received while it was paused." Logs: first request "Miss", collapsed ones "Hit". "CloudFront only collapses requests that share a cache key." Prevent it with `CachingDisabled`, or min TTL 0 plus `Cache-Control: private` from origin.
- Origin Shield: https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/origin-shield.html : "an additional layer in the CloudFront caching infrastructure that helps to minimize your origin's load". "Requests for content that is not in Origin Shield's cache are consolidated with other requests for the same object, resulting in as few as one request going to your origin." "Requests that are made in the same Region as your origin will bypass Origin Shield."

## 6. Nearest edge

- Anycast (Cloudflare blog, 21 Oct 2011, old) https://blog.cloudflare.com/a-brief-anycast-primer/ : "With Anycast, multiple machines can share the same IP address. When a request is sent to an Anycasted IP address, routers will direct it to the machine on the network that is closest." "we can take an entire data center offline and traffic will automatically flow to the next closest data center." "Closest" means BGP-closest, which is my note, not in the quote. - CloudFront: https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/HowCloudFrontWorks.html : "DNS routes the request to the CloudFront POP (edge location) that can best serve the request, typically the nearest CloudFront POP in terms of latency."
- ECS, RFC 7871 https://www.rfc-editor.org/rfc/rfc7871 : informational. Abstract: "an EDNS0 option that is in active use to carry information about the network that originated a DNS query and the network for which the subsequent response can be cached. Since it has some known operational and privacy shortcomings, a revision will be worked through the IETF". The resolver sends a truncated client prefix so the authoritative server can pick a close edge. s2 is a "Privacy Note".
- Akamai (snippet from WebSearch summarising an Akamai research paper "A look at the ECS behavior of DNS resolvers", akamai.com): Akamai name servers "triangulate the assumed location of the recursive DNS resolver" and return the address of the best content server; this breaks for open resolvers such as 8.8.8.8 and 1.1.1.1. ## 7. DDoS at the edge

- Types. Cloudflare Learning Center page was blocked (403/challenge). Snippet only from a third-party summary (not Cloudflare, not primary): volumetric, protocol/state exhaustion (SYN flood), application layer (HTTP flood). The Cloudflare H1 2026 report https://blog.cloudflare.com/ddos-threat-report-2026-h1/ names "SYN Flood" and DNS flood/amplification and CLDAP reflection as vectors, and "DNS-based attacks accounted for 34.3% of all network-layer activity in the first half of 2026". Learning Center definitions: not confirmed from primary page.
- SYN cookies, RFC 4987 s3.6 https://www.rfc-editor.org/rfc/rfc4987 (Aug 2007): "SYN cookies go a step further and allocate no state at all for connections in SYN-RECEIVED. Instead, they encode most of the state ... into the sequence number transmitted on the SYN-ACK."
- Largest attack. Cloudflare 2025 Q4 report (5 Feb 2026) https://blog.cloudflare.com/ddos-threat-report-2025-q4/ : "A record-setting 31.4 Tbps attack"; "one reaching 31.4 Tbps in a DDoS attack that lasted just 35 seconds"; "Aisuru-Kimwolf" botnet; "just weeks after a record-breaking 31.4 Terabits per second (Tbps) attack" came a campaign above "200 million requests per second". The attack date itself is not given in the lines I read; the report is dated February 5, 2026 and the attack was in Q4 2025. ## 8. Edge to origin TLS

- Cloudflare SSL/TLS modes https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/ (last updated Apr 16, 2026):
  - Off: "No encryption is used for traffic between visitors and Cloudflare or between Cloudflare and origins. Everything is cleartext HTTP."
  - Flexible: "Traffic from visitors to Cloudflare can be encrypted via HTTPS, but traffic from Cloudflare to the origin server is not."
  - Full: "Cloudflare matches the visitor request protocol when connecting to the origin. If the visitor uses HTTP, Cloudflare connects to the origin via HTTP; if HTTPS, Cloudflare uses HTTPS without validating the origin's certificate."
  - Full (strict): "Similar to Full Mode, but with added validation of the origin server's certificate, which can be issued by a public CA like Let's Encrypt or by Cloudflare Origin CA."
  - Strict (SSL-Only Origin Pull): "Regardless of whether the visitor-to-Cloudflare connection uses HTTP or HTTPS, Cloudflare always connects to the origin over HTTPS with certificate validation."
  - "Cloudflare strongly recommends using Full or Full (strict) modes to prevent malicious connections to your origin."
- Two separate connections: the client TLS ends at the CDN, a new connection goes to origin. The docs show two legs ("visitors to Cloudflare" and "Cloudflare and origins") with separate settings. Same idea in CloudFront (separate origin protocol policy, docs not quoted).

## 9. Cloudflare Learning Center (read in Chrome through the page, 2026-10-07)

- What is a CDN https://www.cloudflare.com/learning/cdn/what-is-a-cdn/ : "A content delivery network (CDN) is a geographically distributed group of servers that speeds up the delivery of web content by caching it closer to users."
- What is a DDoS attack https://www.cloudflare.com/learning/ddos/what-is-a-ddos-attack/ : three types. Volumetric: "attempts to create congestion by consuming all available bandwidth between the target and the larger Internet". Protocol: "over-consuming server resources and/or the resources of network equipment like firewalls and load balancers" using "weaknesses in layer 3 and layer 4". Application layer: "a single HTTP request can be expensive for the target server to respond to." Mitigations listed: rate limiting, WAF, "Anycast network diffusion: Using an Anycast network to scatter the attack traffic across a distributed network", blackhole routing.

By repeatedly sending initial connection request (SYN) packets, the attacker is able to overwhelm all available ports". Mitigations listed: bigger backlog queue, recycling the oldest half-open connection, SYN cookies.

## 10. Measured in the lab (nginx 1.31.6 edge and origin, on this machine, 2026-10-07)

- `proxy_http_version 2` to the origin: 20 parallel requests opened 20 origin connections, each with 1 request. One nginx HTTP/2 upstream connection carried one request at a time. No multiplexing.
- `keepalive 4`: 20 parallel requests opened up to 20 origin connections; afterwards only 4 stayed idle for reuse.
- `proxy_cache_lock on`: 20 parallel misses for one key sent 1 request to the origin (19 HIT, 1 MISS). Off: 20 requests to the origin.
- Default `proxy_cache_key` uses the URI after proxy_pass rewriting, so two locations that map to the same origin path shared one entry. The lab sets `proxy_cache_key $scheme://$host$request_uri`.
- nginx ETag = file mtime + size. Same size and same second gave the same ETag, so the edge got 304 for changed content.
