## 1. S3

- Bucket = container for objects; object = file plus metadata; key = unique ID in the bucket. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html | "An *object* is a file and any metadata that describes the file. A *bucket* is a container for objects."
- Key is the unique identifier of an object within a bucket. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html | "Each object has a *key* (or *key name*), which is the unique identifier for the object within the bucket."
- Bucket + key + optional version ID address an object (a data map). | https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html | "you can think of Amazon S3 as a basic data map between \"bucket \+ key \+ version\" and the object itself."
- Flat namespace. No real folders. Prefix plus "/" delimiter only gives a folder view. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-keys.html | "The Amazon S3 data model is a flat structure: You create a bucket, and the bucket stores objects. There is no hierarchy of subbuckets or subfolders."
- Console "folders" are prefixes; a folder can be a zero-byte object. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-keys.html | "The Amazon S3 console implements folder object creation by creating a zero-byte object with the folder *prefix and delimiter* value as the key."
- Key max length is 1,024 bytes, UTF-8, case sensitive. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-keys.html | "with a maximum length of 1,024 bytes"
- Bucket names are globally unique within a partition (default namespace). | https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html | "each bucket name must be unique across all AWS accounts in all the AWS Regions within a partition."
- Account regional namespace now exists as an option (newer than the "globally unique" rule). | https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html | "you can choose to create a bucket in your account regional namespace."
- Max object size: the page now says 50 TB (actual 53.7 TB), NOT 5 TB. The 5 TB figure is outdated. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingObjects.html | "Objects can range in size from zero to 50 TB."
- Why 50 TB: 10,000 parts x 5 GiB. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingObjects.html | "10,000 maximum parts x 5 GiB per part = 50,000 GiB (53.7 TB)"
- The multipart limits table lists 48.8 TiB as max object size. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html | "Maximum object size | 48.8 TiB"
- Single PUT up to 5 GB. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/upload-objects.html | "With a single `PUT` operation, you can upload a single object up to 5 GB in size."
- Console single upload max 160 GB. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/upload-objects.html | "The maximum size of a file that you can upload by using the Amazon S3 console is 160 GB."
- Use multipart from about 100 MB. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html | "In general, when your object size reaches 100 MB, you should consider using multipart uploads instead of uploading the object in a single operation."
- Multipart: 10,000 parts, part size 5 MiB to 5 GiB, no minimum for last part. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html | "Maximum number of parts per upload | 10,000" and "Part size | 5 MiB to 5 GiB. There is no minimum size limit on the last part of your multipart upload."
- Multipart parts upload in any order and in parallel. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/upload-objects.html | "These object parts can be uploaded independently, in any order, and in parallel."
- Strong read-after-write consistency for PUT and DELETE in all Regions. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html | "Amazon S3 provides strong read-after-write consistency for PUT and DELETE requests of objects in your Amazon S3 bucket in all AWS Regions."
- LIST after PUT shows the new object. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html | "A process writes a new object to Amazon S3 and immediately lists keys within its bucket. The new object appears in the list."
- Concurrent writes to one key: last writer wins. No cross-key atomicity. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html | "If two PUT requests are simultaneously made to the same key, the request with the latest timestamp wins."
- Bucket configuration is eventually consistent (e.g. wait 15 min after enabling versioning). | https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html | "Bucket configurations have an eventual consistency model."
- Durability 11 nines for the classes in the table (Standard, Standard-IA, Intelligent-Tiering, One Zone-IA, Express One Zone, Glacier IR/FR/DA). | https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html | "S3 Intelligent-Tiering is designed for 99.9% availability and 99.999999999% durability." (table row for each class shows 99.999999999%)
- Storage classes list with min duration: Standard none; Standard-IA 30 days; One Zone-IA 30 days; Glacier IR 90 days; Glacier FR 90 days; Deep Archive 180 days; Intelligent-Tiering none; Express One Zone none. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html | "S3 Standard-IA (`STANDARD_IA`) | ... | 30 days | 128 KB" and "S3 Glacier Deep Archive (`DEEP_ARCHIVE`) | ... | 180 days"
- Standard-IA and One Zone-IA bill 128 KB minimum and 30-day minimum. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html | "If you delete an object before the end of the 30-day minimum storage duration period, you are charged for 30 days."
- One Zone-IA stores in one AZ, not resilient to AZ loss. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html | "the data is not resilient to the physical loss of the Availability Zone"
- Intelligent-Tiering moves objects by access: 30 days to Infrequent, 90 days to Archive Instant Access. Optional archive tiers at 90 and 180 days. Objects under 128 KB are not auto-tiered. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html | "moves objects that have not been accessed in 30 consecutive days to the Infrequent Access tier."
- Express One Zone: single AZ, single-digit ms, directory buckets. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html | "a high-performance, single-zone Amazon S3 storage class that is purpose-built to deliver consistent, single-digit millisecond data access"
- Glacier Flexible Retrieval and Deep Archive need a restore before access. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html | "You must first restore archived objects before you can access them."
- Lifecycle rules: transition and expiration actions. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lifecycle-mgmt.html | "There are two types of actions: **Transition actions** ... **Expiration actions**"
- Lifecycle applies to existing and new objects. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lifecycle-mgmt.html | "the configuration rules apply to both existing objects and objects that you add later."
- Versioning: delete creates a delete marker, not a removal. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html | "if you delete an object, Amazon S3 inserts a delete marker instead of removing the object permanently."
- Versioning: overwrite makes a new version; each version is a full copy and is billed. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html | "Each version of an object is the entire object; it is not just a diff from the previous version."
- Versioning cannot be turned off once on; it can be suspended. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html | "After you version-enable a bucket, it can never return to an unversioned state. But you can *suspend* versioning on that bucket."
- Pre-existing objects get version ID "null". | https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html | "Objects that already existed in the bucket at the time that you enable versioning have a version ID of `null`."
- Block Public Access on at bucket level by default. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html | "By default, Block Public Access settings are turned on at the bucket level."
- New buckets/objects do not allow public access by default. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html | "By default, new buckets, access points, and objects don't allow public access."
- ACLs disabled by default (Bucket owner enforced). | https://docs.aws.amazon.com/AmazonS3/latest/userguide/about-object-ownership.html | "By default, Object Ownership is set to the Bucket owner enforced setting and all ACLs are disabled."
- Default encryption SSE-S3 for all new uploads since 5 Jan 2023, cannot be disabled, no cost. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/default-encryption-faq.html | "Starting January 5, 2023, all new object uploads to Amazon S3 are automatically encrypted at no additional cost and with no impact on performance."
- Existing objects are not auto-encrypted. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/default-encryption-faq.html | "Beginning on January 5, 2023, Amazon S3 only automatically encrypts new object uploads."
- Presigned URL: console 1 min to 12 h; CLI/SDK up to 7 days; IAM user creds with SigV4 up to 7 days. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html | "If you use the AWS CLI or AWS SDKs, the expiration time can be set as high as 7 days."
- Presigned URL with temporary credentials ends when the credentials end. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html | "If you created a presigned URL using a temporary credential, the URL expires when the credential expires."
- Presigned URL is a bearer token and uses the creator's permissions. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html | "presigned URLs are bearer tokens that grant access to those who possess them."
- Request rate per prefix: 3,500 write-type and 5,500 read-type per second. No limit on number of prefixes. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html | "at least 3,500 PUT/COPY/POST/DELETE or 5,500 GET/HEAD requests per second per partitioned Amazon S3 prefix."
- Scaling is gradual; 503 Slow Down may show while it scales. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html | "you may see some 503 (Slow Down) errors."
- Conditional write: If-None-Match blocks overwrite of an existing key; failure is 412. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html | "The `If-None-Match` header prevents overwrites of existing data by validating that there's not an object with the same key name already in your bucket."
- If-None-Match expects "*"; works with PutObject, CompleteMultipartUpload, CopyObject. Needs SigV4. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html | "The `If-None-Match` header expects the \* (asterisk) value."
- If-Match compares the ETag before write. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html | "Amazon S3 compares the provided ETag value with the ETag value of the object in S3. If the ETag values don't match, the operation fails."
- Event notifications go to SNS, SQS, Lambda, EventBridge; delivery is at least once. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/EventNotifications.html | "Amazon S3 event notifications are designed to be delivered at least once."
- SQS FIFO is not a direct S3 event target; use EventBridge. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/EventNotifications.html | "Amazon Simple Queue Service FIFO (First-In-First-Out) queues aren't supported as an Amazon S3 event notification destination."
- Loop risk: a function writing to the same bucket can retrigger itself. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/EventNotifications.html | "If your notification writes to the same bucket that triggers the notification, it could cause an execution loop."

## 2. RDS

- RDS engines: Db2, MariaDB, SQL Server, MySQL, Oracle, PostgreSQL (Aurora has its own guide). | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Welcome.html | "IBM Db2, MariaDB, Microsoft SQL Server, MySQL, Oracle Database, and PostgreSQL."
- AWS manages backups, patching, failure detection, recovery. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Welcome.html | "Amazon RDS manages backups, software patching, automatic failure detection, and recovery."
- Customer still owns query tuning. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Welcome.html | "You are responsible for query tuning"
- Automated backup retention 0 to 35 days; 0 turns them off. Console default 7 days, API/CLI default 1 day. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.BackupRetention.html | "You can set the backup retention period of a DB instance to between 0 and 35 days. Setting the backup retention period to 0 disables automated backups."
- Changing retention between 0 and non-zero causes an outage. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.BackupRetention.html | "An outage occurs if you change the backup retention period of a DB instance from 0 to a nonzero value or from a nonzero value to 0."
- Transaction logs go to S3 every 5 minutes; check LatestRestorableTime. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html | "RDS uploads transaction logs for DB instances to Amazon S3 every five minutes."
- PITR makes a NEW DB instance. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html | "You can restore a DB instance to a specific point in time, creating a new DB instance without modifying the source DB instance."
- Backups live in S3; up to 100 manual snapshots per Region. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html | "You can have up to 100 manual snapshots per Region."
- Multi-AZ DB instance: synchronous standby in another AZ, standby cannot serve reads. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZSingleStandby.html | "Amazon RDS automatically provisions and maintains a synchronous standby replica in a different Availability Zone."
- Standby is not a read scale tool. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZSingleStandby.html | "You can't use a standby replica to serve read traffic."
- Multi-AZ adds write/commit latency (synchronous). | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZSingleStandby.html | "can have increased write and commit latency compared to a Single-AZ deployment."
- Failover typically 60-120 s; large transactions or long recovery add time. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZ.Failover.html | "Failover times are typically 60–120 seconds."
- Failover works by changing the DNS record; clients must reconnect; JVM TTL <= 60 s advised. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZ.Failover.html | "The failover mechanism automatically changes the Domain Name System (DNS) record of the DB instance to point to the standby DB instance."
- Multi-AZ DB cluster: writer + two readable standbys in three AZs, semisynchronous. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/multi-az-db-clusters-concepts.html | "A Multi-AZ DB cluster has a writer DB instance and two reader DB instances in three separate Availability Zones in the same AWS Region."
- Cluster commit needs ack from at least one reader. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/multi-az-db-clusters-concepts.html | "requires acknowledgment from at least one reader DB instance in order for a change to be committed."
- Multi-AZ DB cluster has lower write latency than Multi-AZ instance and readers serve reads. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/multi-az-db-clusters-concepts.html | "Multi-AZ DB clusters typically have lower write latency when compared to Multi-AZ DB instance deployments."
- Read replica: asynchronous copy for read scaling and DR. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html | "Amazon RDS copies them asynchronously to the read replica."
- Up to 15 read replicas per source for RDS MySQL (same Region). | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_MySQL.Replication.ReadReplicas.html | "You can create up to 15 read replicas from one DB instance within the same Region."
- Read replicas are NOT auto-scaled; you add and delete them. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html | "RDS doesn't support autoscaling of read replicas"
- Read replica can be promoted to a standalone instance (DR). | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html | "You can promote a read replica to a standalone instance as a disaster recovery solution if the primary DB instance fails."
- Storage autoscaling triggers: free space <= 10% for 5 min, and fewer than 4 changes in 24 h. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIOPS.Autoscaling.html | "Free available space is less than or equal to 10 percent of the allocated storage."
- Autoscaling is scale up only, capped by a max storage threshold you set. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIOPS.Autoscaling.html | "Autoscaling can't decrease the allocated storage."
- Enabling storage autoscaling needs no reboot or downtime. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIOPS.Autoscaling.html | "Enabling storage autoscaling doesn't require a database reboot and doesn't cause any downtime."
- RDS Proxy pools and shares connections; absorbs connection surges. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-proxy.html | "RDS Proxy establishes a database connection pool and reuses connections in this pool."
- RDS Proxy keeps app connections through failover to the standby. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-proxy.html | "RDS Proxy makes applications more resilient to database failures by automatically connecting to a standby DB instance while preserving application connections."
- RDS Proxy queues or throttles, and sheds load over limits. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-proxy.html | "RDS Proxy queues or throttles application connections that can't be served immediately from the connection pool."
- RDS Proxy session pinning for statements over 16 KB; proxy attaches to writer only. | https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-proxy.html | "Any statement with a text size greater than 16 KB causes the proxy to pin the session to the current connection."

## 3. Aurora

- Cluster volume spans three AZs; a copy of data in each AZ; replication independent of instance count. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Overview.StorageReliability.html | "A cluster volume consists of copies of the data across three Availability Zones in a single AWS Region."
- Writes go to six storage nodes synchronously. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Concepts.AuroraHighAvailability.html | "Aurora synchronously replicates the data across Availability Zones to six storage nodes associated with your cluster volume."
- Six copies in three AZs, 4-of-6 write quorum (AWS database blog, not the user guide). | https://aws.amazon.com/blogs/database/amazon-aurora-under-the-hood-quorum-and-correlated-failure/ | "issue writes to all six copies of data and acknowledge the write as complete once we obtain an acknowledgement from four of the six copies." (paraphrase of fetch; page also says it can "tolerate losing an entire AZ without losing write availability")
- Storage split into 10 GB chunks, each replicated, for fast repair. | https://aws.amazon.com/blogs/database/amazon-aurora-under-the-hood-quorum-and-correlated-failure/ | "large volumes are divided into 10 GB chunks" (from fetch summary; see Not confirmed)
- Storage shared by all instances; adding an instance copies no data. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Overview.StorageReliability.html | "you can add a DB instance quickly because Aurora doesn't make a new copy of the table data."
- Up to 15 Aurora Replicas, automatic failover to a replica, per-replica priority. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Overview.html | "Each Aurora DB cluster can have up to 15 Aurora Replicas in addition to the primary DB instance."
- Aurora Replicas use async replication but share the storage volume. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Concepts.AuroraHighAvailability.html | "Aurora Replicas use asynchronous replication to support high availability without affecting primary instance performance."
- Cluster endpoint = current writer; reader endpoint balances across replicas. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Overview.Endpoints.html | "Aurora automatically performs connection-balancing among all the Aurora Replicas."
- Cluster/reader endpoints follow failover; instance endpoints do not. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Overview.Endpoints.html | "Unlike the instance endpoints, the writer and reader endpoints automatically change which DB instance they connect to if a DB instance in your cluster becomes unavailable."
- Failover: service typically back in under 60 s, often under 30 s. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Concepts.AuroraHighAvailability.html | "service is typically restored in less than 60 seconds, and often less than 30 seconds."
- With no replicas, a new primary is created: typically under 10 minutes. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Concepts.AuroraHighAvailability.html | "which typically takes less than 10 minutes."
- Promotion priority 0 (highest) to 15; ties go to the largest replica. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Concepts.AuroraHighAvailability.html | "Priorities range from 0 for the highest priority to 15 for the lowest priority."
- Max cluster volume: 256 TiB on newer engine versions, 128 TiB on older. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/CHAP_Limits.html | "Aurora cluster volume maximum size varies by engine version:" "**256 TiB maximum:** ... Aurora PostgreSQL versions: 17.5 and all higher versions" "**128 TiB maximum:** All earlier Aurora PostgreSQL versions"
- Volume grows automatically; you pay only for used space; it shrinks when data is dropped. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Overview.StorageReliability.html | "Aurora cluster volumes automatically grow as the amount of data in your database increases."
- Serverless v2: compute unit is the ACU, about 2 GiB memory each. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2.how-it-works.html | "Each ACU is a combination of approximately 2 gibibytes (GiB) of memory, corresponding CPU, and networking."
- Serverless v2 range 0 to 256 ACU; 0 ACU needs auto-pause capable versions; scales in steps as small as 0.5 ACU. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2.how-it-works.html | "Aurora serverless offers capacity from 0 ACUs to 256 ACUs." and "Scaling happens in increments as small as 0.5 ACUs."
- Serverless scales compute only; storage stays six copies in three AZs. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2.how-it-works.html | "it's always compute capacity that's increasing or decreasing."
- Global Database: one primary Region, up to 10 secondary Regions, replication lag typically under 1 s. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database.html | "an Aurora global database has a primary DB cluster in one Region, and up to 10 secondary DB clusters in different Regions." and "with latency typically under a second."
- Global Database replication uses the storage layer, not the engine. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database.html | "Aurora uses the cluster storage volume and not the database engine for fast, low-overhead replication."
- Global Database: switchover (no data loss) vs failover (outage). Secondary can have 16 readers. | https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database.html | "you can relocate the primary cluster of a healthy Aurora Global Database to one of its secondary Regions with no data loss."
- Aurora FAQ also states 256 TiB and 15 replicas. | https://docs.aws.amazon.com/rds/latest/auroraextendedcontent/aurora-faq.html | "it automatically scales up to 256 TiB per database instance and replicates your data across three Availability Zones (AZs)"

## 4. DynamoDB

- Table > items > attributes; no limit on items per table. | https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.CoreComponents.html | "A *table* is a collection of items, and each item is a collection of *attributes*."
- Schemaless except the primary key. | https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.CoreComponents.html | "Other than the primary key, the *People* table is schemaless"
- Partition key is hashed to pick the partition. | https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.CoreComponents.html | "DynamoDB uses the partition key's value as input to an internal hash function. The output from the hash function determines the partition"
- Same partition key items stored together, sorted by sort key. | https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.CoreComponents.html | "All items with the same partition key value are stored together, in sorted order by sort key value."
- Key types: string, number, binary only. | https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.CoreComponents.html | "The only data types allowed for primary key attributes are string, number, or binary."
- Max item size 400 KB (names + values). | https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Constraints.html | "The maximum item size in DynamoDB is 400 KB, which includes both attribute name binary length (UTF-8 length) and attribute value lengths"
- Key size limits: partition key 2048 bytes, sort key 1024 bytes. | https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Constraints.html | "The maximum length is 2048 bytes." (partition key) / "The maximum length is 1024 bytes." (sort key)
- Per-partition ceiling 3,000 read units/s and 1,000 write units/s. | https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-design.html | "Every partition in a DynamoDB table is designed to deliver a maximum capacity of 3,000 read units per second and 1,000 write units per second."
- Adaptive capacity applies to on-demand and provisioned. | https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-design.html | "Adaptive capacity applies to on-demand mode and provisioned capacity."
- Design for uniform access across partition keys. | https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-design.html | "You should design your application for uniform activity across all partition keys in the table and its secondary indexes."
- 1 RCU = 1 strongly consistent read/s up to 4 KB, or 2 eventually consistent. | https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Constraints.html | "One read capacity unit = one strongly consistent read per second, or two eventually consistent reads per second, for items up to 4 KB in size."
- 1 WCU = 1 write/s up to 1 KB. Transactional reads/writes cost 2x. | https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Constraints.html | "One write capacity unit = one write per second, for items up to 1 KB in size." and "Transactional write requests require two write capacity units"
- Reads round up to 4 KB; writes round up to 1 KB. | https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/read-write-operations.html | "Item sizes for reads are rounded up to the next 4 KB multiple."

- Sequence numbers increase per partition key within a shard (ordering per key). | https://docs.aws.amazon.com/streams/latest/dev/key-concepts.html | "Each data record has a *sequence number* that is unique per partition-key within its shard."
