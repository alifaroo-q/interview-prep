## 1. URL to pixels

- TLS 1.3 saves a round trip vs older versions: RFC 8446, https://www.rfc-editor.org/rfc/rfc8446 . Fetched. "A zero round-trip time (0-RTT) mode was added, saving a round trip at connection setup for some application data". NOTE: RFC 8446 never states "full handshake = 1 round trip" in words. Use the Cloudflare line below.
- TLS 1.3 = 1 round trip: Cloudflare, https://blog.cloudflare.com/introducing-0-rtt/ . Fetched (summarised). "One of the biggest advantages of TLS 1.3 over earlier versions is that it only requires one round trip to set up the connection, resumed or not."
- TLS 1.2 = 2 round trips: same Cloudflare page. Fetched (summarised). "For TLS 1.2 and earlier, this takes two round trips." RFC 5246 has no round-trip count (grep found none): NOT CONFIRMED from RFC 5246.
- HTTP/1.1 persistent connections by default: RFC 9112 section 9.3, https://www.rfc-editor.org/rfc/rfc9112 . Fetched. "HTTP/1.1 defaults to the use of "persistent connections", allowing multiple requests and responses to be carried over a single connection."
- Critical rendering path: MDN, https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Critical_rendering_path . Fetched. "The Critical Rendering Path is the sequence of steps the browser goes through to convert the HTML, CSS, and JavaScript into pixels on the screen." and "With the DOM and CSSOM complete, the browser builds the render tree, computing the styles for all the visible content. After the render tree is complete, layout occurs, defining the location and size of all the render tree elements."
- Latency vs business, Vodafone: https://web.dev/case-studies/vodafone . Fetched. Title: "Vodafone: A 31% improvement in LCP increased sales by 8%". Body: "a 31% improvement in LCP led to 8% more sales, a 15% improvement in their lead to visit rate, and a 11% improvement in their cart to visit rate." (A/B test, 2021.)

## 2. HTTP semantics

- Safe methods: RFC 9110 section 9.2.1, https://www.rfc-editor.org/rfc/rfc9110 . Fetched. "Request methods are considered "safe" if their defined semantics are essentially read-only"
- Idempotent list: RFC 9110 section 9.2.2. Fetched. "Of the request methods defined by this specification, PUT, DELETE, and safe request methods are idempotent."
- PATCH: RFC 5789, https://www.rfc-editor.org/rfc/rfc5789 . Fetched. "PATCH is neither safe nor idempotent as defined by [RFC2616], Section 9.1." and "A PATCH request can be issued in such a way as to be idempotent".
- 401: RFC 9110 15.5.2. Fetched. "The 401 (Unauthorized) status code indicates that the request has not been applied because it lacks valid authentication credentials for the target resource."
- 403: RFC 9110 15.5.4. Fetched. "The 403 (Forbidden) status code indicates that the server understood the request but refuses to fulfill it."
- 409: RFC 9110 15.5.10. Fetched. "The 409 (Conflict) status code indicates that the request could not be completed due to a conflict with the current state of the target resource."
- 422: RFC 9110 15.5.21. Fetched. "The 422 (Unprocessable Content) status code indicates that the server understands the content type of the request content ..., and the syntax of the request content is correct, but it was unable to process the contained instructions."
- 429: RFC 6585 section 4, https://www.rfc-editor.org/rfc/rfc6585 . Fetched. "The 429 status code indicates that the user has sent too many requests in a given amount of time ("rate limiting")."
- Stripe cursors: https://docs.stripe.com/api/pagination . Fetched. Params "starting_after" and "ending_before"; "Both parameters accept an existing object ID value (see below)" (source text, markup stripped).
- Slack cursors: https://api.slack.com/docs/pagination . Fetched. "Most methods that support pagination use a cursor-based approach." and "Cursors are like pointers. ... They help avoid loading an entire set just to give you a slice." Why Slack moved away from offset: NOT CONFIRMED (page does not say).
- GitHub Link header: https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api . Fetched. "you can use the link header from the response to request additional pages of data." Example: `link: <https://api.github.com/repositories/1300192/issues?page=2>; rel="prev", ... rel="next", ... rel="last"`.

## 3. JavaScript event loop

- Microtask checkpoint after each task: HTML spec, https://html.spec.whatwg.org/multipage/webappapis.html . Fetched. Event loop steps: "Perform oldestTask's steps. Set the event loop's currently running task back to null. Perform a microtask checkpoint." Also: "The microtask queue is not a task queue."
- MDN microtasks, https://developer.mozilla.org/en-US/docs/Web/API/HTML_DOM_API/Microtask_guide/In_depth . Fetched. "Whenever a task exits and the execution context stack is empty, all microtasks in the microtask queue are executed in turn. ... microtasks can enqueue new microtasks and those new microtasks will execute before the next task begins to run".
- Node event loop phases: https://nodejs.org/en/learn/asynchronous-work/event-loop-timers-and-nexttick . Fetched. "pending callbacks : executes I/O callbacks deferred to the next loop iteration." "poll : retrieve new I/O events; execute I/O related callbacks". Intro: "The event loop is what allows Node.js to perform non-blocking I/O operations — despite the fact that a single JavaScript thread is used by default".
- Node, do not block: https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop . Fetched. "One common way to block the Event Loop disastrously is by using a "vulnerable" regular expression." and "in some cases the regexp match might require an exponential number of trips through the input string --- O(2^n) time." and "A vulnerable regular expression is one on which your regular expression engine might take exponential time, exposing you to REDOS on "evil input"."
- Timer clamping: HTML spec, https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html . Fetched. "If nestingLevel is greater than 5, and timeout is less than 4, then set timeout to 4."

## 4. Browser rendering and performance

"pages should maintain a CLS of 0.1. or less". Percentile: "a good threshold to measure is the 75th percentile of page loads, segmented across mobile and desktop devices."
- INP replaced FID: https://web.dev/blog/inp-cwv-march-12 . Fetched. "INP will officially become a Core Web Vital and replace FID on March 12 of this year, and that FID will be deprecated in this transition." Year is 2024 (post says "this year"; the same page says "INP would be promoted to stable status in March 2024"). Vitals page note: "INP is now a stable Core Web Vital metric, and has officially replaced First Input Delay (FID)."
- hadRecentInput: https://web.dev/articles/cls . Fetched. "Layout shifts that occur within 500 milliseconds of user input will have the hadRecentInput flag set, so they can be excluded from calculations." Also "The hadRecentInput flag will only be true for discrete input events, such as tap, click, or keypress." MDN PerformanceObserver "layout-shift" page itself: not fetched.
- Image dimensions: https://web.dev/articles/optimize-cls . Fetched. "Always include width and height size attributes on your images and video elements. Alternatively, reserve the required space with CSS aspect-ratio or similar."
- Case study, Yahoo! JAPAN News: https://web.dev/case-studies/yahoo-japan-news . Fetched. "Optimizing CLS by 0.2 led to a 15% increase in page views per session, 13% longer session durations, and a 1.72 percentage point decrease in bounce rate."

## 7. Auth

- JWT exp: RFC 7519 section 4.1.4, https://www.rfc-editor.org/rfc/rfc7519 . Fetched. "The "exp" (expiration time) claim identifies the expiration time on or after which the JWT MUST NOT be accepted for processing." "iat" is section 4.1.6 (quote not pulled).
- RFC 8725, https://www.rfc-editor.org/rfc/rfc8725 . Fetched. "The algorithm can be changed to "none" by an attacker, and some libraries would trust this value and "validate" the JWT without checking any signature." Also: "JWT libraries SHOULD NOT consume JWTs using "none" unless explicitly requested to do so by the caller."
- Auth0 / Tim McLean: https://auth0.com/blog/critical-vulnerabilities-in-json-web-token-libraries/ . Fetched. Page shows "(Updated 2015-04-20)". Original publish date: NOT CONFIRMED from the page (2015 per the user). "Unfortunately, some libraries treated tokens signed with the none algorithm as a valid token with a verified signature. The result? Anyone can create their own "signed" tokens". RS/HS: "If a server is expecting a token signed with RSA, but actually receives a token signed with HMAC, it will think the public key is actually an HMAC secret key."
- Cookies, MDN: https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies . Fetched. "If no SameSite attribute is set, the cookie is treated as Lax by default." "A cookie with the HttpOnly attribute can't be accessed by JavaScript, for example using Document.cookie; it can only be accessed when it reaches the server." "A cookie with the Secure attribute is only sent to the server with an encrypted request over the HTTPS protocol."
- Lax default in Chrome 2020: OWASP CSRF cheat sheet, https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html . Fetched. "Chrome implemented SameSite=Lax as the default behavior in 2020, and Firefox and Edge have followed suit."
- PKCE: RFC 7636, https://www.rfc-editor.org/rfc/rfc7636 . Fetched. "OAuth 2.0 [RFC6749] public clients are susceptible to the authorization code interception attack." (Abstract names PKCE as the fix.)
- RFC 9700, https://www.rfc-editor.org/rfc/rfc9700 section 2.1.2. Fetched. "clients SHOULD NOT use the implicit grant (response type token) or other response types issuing access tokens in the authorization response, unless access token injection in the authorization response is prevented". Publication month (January 2025): NOT CONFIRMED by me (did not read the header).
- Token storage: OWASP HTML5 Security cheat sheet, https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html . Fetched. "Do not store session identifiers in local storage as the data is always accessible by JavaScript. Cookies can mitigate this risk using the httpOnly flag." and "A single Cross Site Scripting can be used to steal all the data in these objects".
