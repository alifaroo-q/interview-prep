# TCP, TLS, HTTP/2, QUIC, anycast: sources

Date checked: 2026-10-07. RFC section numbers and quotes are from the rfc-editor.org .txt files. Base: https://www.rfc-editor.org/rfc/rfcNNNN.txt (HTML: .../rfcNNNN.html). Does not repeat facts in `cdn-sources.md`.

## 1. TCP (RFC 9293, RFC 6298, Linux)

- Three-way handshake. https://www.rfc-editor.org/rfc/rfc9293.txt §3.5: "The "three-way handshake" is the procedure used to establish a connection." Steps listed in §3.5 as SYN, then ACK+SYN (steps 2 and 3 combined), then ACK: "Because steps 2 and 3 can be combined in a single message this is called the three-way (or three message) handshake (3WHS)."
- Why three: §3.5: "The principal reason for the three-way handshake is to prevent old duplicate connection initiations from causing confusion."
- States. §3.3.2 (diagram is Figure 5): "The states are: LISTEN, SYN-SENT, SYN-RECEIVED, ESTABLISHED, FIN-WAIT-1, FIN-WAIT-2, CLOSE-WAIT, CLOSING, LAST-ACK, TIME-WAIT, and the fictional state CLOSED." Also "CLOSED is fictional because it represents the state when there is no TCB, and therefore, no connection." "LISTEN - represents waiting for a connection request from any remote TCP peer and port." "SYN-SENT - represents waiting for a matching connection request after having sent a connection request." "SYN-RECEIVED - represents waiting for a confirming connection request acknowledgment after having both received and sent a connection request." "ESTABLISHED - represents an open connection, data received can be delivered to the user."
- ISN is chosen per connection (random-looking, clock based, not zero). §3.4.1: "When new connections are created, an initial sequence number (ISN) generator is employed that selects a new 32-bit ISN. There are security issues that result if an off-path attacker is able to predict or guess ISN values." Reason (old duplicates), same section: "the initial sequence number selection described below further protects against ambiguity about which incarnation of a connection an incoming packet corresponds to." Clock: "a 32-bit counter that typically increments at least once every roughly 4 microseconds".
- Connection identity (socket pair). §3.4.1: "A connection is defined by a pair of sockets." §3.9.1.1 (OPEN call, text near "local connection name"): "the connection defined by the <local socket, remote socket> pair." §3.3.1: "the local and remote IP addresses and port numbers" are stored in the TCB. (The words "4-tuple" do not appear in RFC 9293.)
- TIME-WAIT = 2 MSL. §3.6.1 (closing): "When a connection is closed actively, it MUST linger in the TIME-WAIT state for a time 2xMSL (Maximum Segment Lifetime) (MUST-13)." MSL value, §3.4.2: "For this specification the MSL is taken to be 2 minutes. This is an engineering choice, and may be changed if experience indicates it is desirable to do so." (So 2*MSL = 4 minutes in the RFC.) TIME-WAIT purpose, §3.3.2: "waiting for enough time to pass to be sure the remote TCP peer received the acknowledgment of its connection termination request and to avoid new connections being impacted by delayed segments from previous connections."
- Linux TIME_WAIT is 60 s. https://raw.githubusercontent.com/torvalds/linux/master/include/net/tcp.h: "#define TCP_TIMEWAIT_LEN (60*HZ) /* how long to wait to destroy TIME-WAIT state, about 60 seconds */". Fixed at compile time.
- Initial RTO 1 s. https://www.rfc-editor.org/rfc/rfc6298.txt §2.1: "the sender SHOULD set RTO <- 1 second, though the "backing off" on repeated retransmission discussed in (5.5) still applies." RTO may stay at 3 s if SYN is lost, §7: "unless the SYN or the ACK of the SYN is lost, in which case the default RTO is reverted to 3 seconds before data transmission begins."
- RTO doubles on timeout. RFC 6298 §5.5: "The host MUST set RTO <- RTO * 2 ("back off the timer")."
- tcp_syn_retries. https://docs.kernel.org/networking/ip-sysctl.html: "tcp_syn_retries - INTEGER: Number of times initial SYNs for an active TCP connection attempt will be retransmitted. Should not be higher than 127. Default value is 6, which corresponds to 67seconds (with tcp_syn_linear_timeouts = 4) till the last retransmission with the current initial RTO of 1second. With this the final timeout for an active TCP connection attempt will happen after 131seconds." Passive side, same page: "tcp_synack_retries ... Default value is 5, which corresponds to 31seconds till the last retransmission with the current initial RTO of 1second. With this the final timeout for an active TCP connection attempt will happen after 63seconds." (The page itself says "for a passive TCP connection" in that last sentence.)
- Throughput model (Mathis 1997). Paper PDF: https://cseweb.ucsd.edu/classes/wi01/cse222/papers/mathis-tcpmodel-ccr97.pdf (CCR 27(3), July 1997), Eq. 3: BW = MSS/RTT * C/sqrt(p), with "C = sqrt(3/2)" (text extraction shows "C = 3=2"); Table 1 row "Every Packet" lists "1.22 = sqrt(3/2)". Simpler bound, Eq. 4: BW < MSS/RTT * 1/sqrt(p) (the paper says "C is normally less than 1" in practice; "C = 1.2" is used in its modem example for the non-delayed-ACK periodic case). Second source: https://www.rfc-editor.org/rfc/rfc3649.txt §1: "the current Standard TCP's average congestion window is roughly 1.2/sqrt(p) segments", and §5: "The TCP response function, w = 1.2/sqrt(p), gives TCP's average congestion window w in MSS-sized segments, as a function of the steady-state packet drop rate p". Throughput = w * MSS / RTT. Also RFC 5348 §3.1 gives the fuller TFRC equation with t_RTO (not the 1.22 form).

## 2. TLS 1.3 (RFC 8446, RFC 6066, RFC 8744)

- Full handshake flow. https://www.rfc-editor.org/rfc/rfc8446.txt §2, Figure 1: client sends "ClientHello + key_share* + signature_algorithms* + psk_key_exchange_modes* + pre_shared_key*"; server sends "ServerHello + key_share* + pre_shared_key*", "{EncryptedExtensions}", "{CertificateRequest*}", "{Certificate*}", "{CertificateVerify*}", "{Finished}", "[Application Data*]"; client then sends "{Certificate*} {CertificateVerify*} {Finished}" and "[Application Data]".
- Meaning of marks. §2, Figure 1 legend: "{} Indicates messages protected using keys derived from a [sender]_handshake_traffic_secret." "[] Indicates messages protected using keys derived from [sender]_application_traffic_secret_N." "* Indicates optional or situation-dependent messages/extensions that are not always sent." "+ Indicates noteworthy extensions sent in the previously noted message."
- Three properties. §1: "Authentication: The server side of the channel is always authenticated; the client side is optionally authenticated." "Confidentiality: Data sent over the channel after establishment is only visible to the endpoints." "Integrity: Data sent over the channel after establishment cannot be modified by attackers without detection."
- HelloRetryRequest. §2.1 (Incorrect DHE Share): "If the client has not provided a sufficient "key_share" extension (e.g., it includes only DHE or ECDHE groups unacceptable to or unsupported by the server), the server corrects the mismatch with a HelloRetryRequest and the client needs to restart the handshake with an appropriate "key_share" extension, as shown in Figure 2." §4.1.4: "The server will send this message in response to a ClientHello message if it is able to find an acceptable set of parameters but the ClientHello does not contain sufficient information to proceed with the handshake." Cost, §4.2.8: "Clients MAY send an empty client_shares vector in order to request group selection from the server, at the cost of an additional round trip (see Section 4.1.4)."
- Resumption with PSK and ticket. §2.2: "Once a handshake has completed, the server can send the client a PSK identity that corresponds to a unique key derived from the initial handshake (see Section 4.6.1). The client can then use that PSK identity in future handshakes to negotiate the use of the associated PSK." Figure 3 shows "[NewSessionTicket]" after the initial handshake. §4.6.1: "At any time after the server has received the client Finished message, it MAY send a NewSessionTicket message." No Certificate on resumption, §2.2: "As the server is authenticating via a PSK, it does not send a Certificate or a CertificateVerify message." Also §2.2: "In TLS 1.2 and below, this functionality was provided by "session IDs" and "session tickets" [RFC5077]. Both mechanisms are obsoleted in TLS 1.3."
- SNI is in ClientHello, in clear. RFC 8446 §4.4.2: "The "server_name" [RFC6066] and "certificate_authorities" extensions are used to guide certificate selection. As servers MAY require the presence of the "server_name" extension, clients SHOULD send this extension, when applicable." https://www.rfc-editor.org/rfc/rfc6066.txt §3: "clients MAY include an extension of type "server_name" in the (extended) client hello." The ClientHello is not in {} in Figure 1, so it is not encrypted. Explicit cleartext statement: https://www.rfc-editor.org/rfc/rfc8744.txt §2: "The SNI extension is carried in cleartext in the TLS "ClientHello" message." And §1: "This protocol element is transmitted in cleartext." RFC 8446 §1.2 (changes from TLS 1.2): "All handshake messages after the ServerHello are now encrypted." (so the certificate is hidden, SNI is not).

## 3. HTTP/1.1 connections (RFC 9112, MDN)

- Persistent by default. https://www.rfc-editor.org/rfc/rfc9112.txt §9.3: "HTTP/1.1 defaults to the use of "persistent connections", allowing multiple requests and responses to be carried over a single connection."
- Connection: close. §9.3: "If the "close" connection option is present (Section 9.6), the connection will not persist after the current response". §9.6: "The "close" connection option is defined as a signal that the sender will close this connection after completion of the response." And: "in a response, the same field indicates that the server is going to close this connection after the response message is complete."
- Client connection limit has no number. §9.4: "A client ought to limit the number of simultaneous open connections that it maintains to a given server." "Previous revisions of HTTP gave a specific number of connections as a ceiling, but this was found to be impractical for many applications. As a result, this specification does not mandate a particular maximum number of connections". Reason for many connections, §9.4: "Multiple connections are typically used to avoid the "head-of-line blocking" problem".
- Browser parallel connections. https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Connection_management_in_HTTP_1.x, section "Domain sharding": "Default was once 2 to 3 connections, but this has now increased to a more common use of 6 parallel connections." Same section: "As a solution, browsers open several connections to each domain, sending parallel requests." and "In HTTP/2, domain sharding is no longer useful: the HTTP/2 connection is able to handle parallel unprioritized requests very well." (Page last modified 2026-09-11 per its footer.)

## 4. HTTP/2 (RFC 9113, RFC 7541)

All from https://www.rfc-editor.org/rfc/rfc9113.txt.
- Frame header. §4.1: "All frames begin with a fixed 9-octet header followed by a variable-length frame payload." Fields: "Length (24), Type (8), Flags (8), Reserved (1), Stream Identifier (31)". "Stream Identifier: ... The value 0x00 is reserved for frames that are associated with the connection as a whole as opposed to an individual stream."
- Default frame size. §4.1 Length: "Values greater than 2^14 (16,384) MUST NOT be sent unless the receiver has set a larger value for SETTINGS_MAX_FRAME_SIZE." §4.2: "This setting can have any value between 2^14 (16,384) and 2^24-1 (16,777,215) octets, inclusive."
- Stream IDs. §5.1.1: "Streams initiated by a client MUST use odd-numbered stream identifiers; those initiated by the server MUST use even-numbered stream identifiers. A stream identifier of zero (0x00) is used for connection control messages; the stream identifier of zero cannot be used to establish a new stream."
- Initial window. §6.9.2: "When an HTTP/2 connection is first established, new streams are created with an initial flow-control window size of 65,535 octets. The connection flow-control window is also 65,535 octets." Also §5.2.1 item 4: "The initial value for the flow-control window is 65,535 octets for both new streams and the overall connection."
- Frame types (§6, each section opens with its code): DATA "type=0x00" (§6.1), HEADERS "type=0x01" (§6.2), RST_STREAM "type=0x03" (§6.4), SETTINGS "type=0x04" (§6.5), GOAWAY "type=0x07" (§6.8), WINDOW_UPDATE "type=0x08" (§6.9). §6 intro: "This specification defines a number of frame types, each identified by a unique 8-bit type code."
- RST_STREAM ends one stream only. §6.4: "The RST_STREAM frame (type=0x03) allows for immediate termination of a stream." §5.4.2: "A stream error is an error related to a specific stream that does not affect processing of other streams." GOAWAY, §6.8: "GOAWAY allows an endpoint to gracefully stop accepting new streams while still finishing processing of previously established streams."
- HPACK. https://www.rfc-editor.org/rfc/rfc7541.txt Abstract: "This specification defines HPACK, a compression format for efficiently representing HTTP header fields, to be used in HTTP/2." §1: "In HTTP/1.1 (see [RFC7230]), header fields are not compressed." Dynamic table starts at 4,096 bytes, RFC 9113 §4.3.1 text: "the dynamic table size for the HPACK decoder and encoder at both endpoints starts at 4,096 bytes".

## 5. QUIC and HTTP/3 (RFC 9000, 9001, 9114, 9460)

- Combined handshake. https://www.rfc-editor.org/rfc/rfc9000.txt §7: "QUIC relies on a combined cryptographic and transport handshake to minimize connection establishment latency. QUIC uses the CRYPTO frame (Section 19.6) to transmit the cryptographic handshake." https://www.rfc-editor.org/rfc/rfc9001.txt §4: "QUIC carries TLS handshake data in CRYPTO frames". §4 also / §1: "TLS record protection is not used by QUIC." (RFC 9001 line: "TLS record protection is not used by QUIC.")
- 1-RTT and 0-RTT. RFC 9001 §2.1: "A full 1-RTT handshake, in which the client is able to send application data after one round trip and the server immediately responds after receiving the first handshake message from the client." and "A 0-RTT handshake, in which the client uses information it has previously learned about the server to send application data immediately." (second quote is the start of the next bullet; the text after "uses information it has" is cut at line end in the file, so check wording on the page before quoting in full). RFC 9001 §1: "Absent packet loss, most new connections can be established and secured within a single round trip".
- Only the client migrates. RFC 9000 §9: "Clients are responsible for initiating all migrations. Servers do not send non-probing packets (see Section 9.1) toward a client address until they see a non-probing packet from that address." Also §9: "An endpoint MUST NOT initiate connection migration before the handshake is confirmed". Reason a connection survives: "The use of a connection ID allows connections to survive changes to endpoint addresses (IP address and port)".
- Path validation. §8.2: "where an address is the 2-tuple of IP address and port." "Path validation is used to ensure that packets received from a migrating peer do not carry a spoofed source address." §8.2.2: "On receiving a PATH_CHALLENGE frame, an endpoint MUST respond by echoing the data contained in the PATH_CHALLENGE frame in a PATH_RESPONSE frame."
- New connection ID on migration. §9.5: "Using a stable connection ID on multiple network paths would allow a passive observer to correlate activity between those paths." "An endpoint MUST NOT reuse a connection ID when sending from more than one local address".
- disable_active_migration. §18.2: "The disable active migration transport parameter is included if the endpoint does not support active connection migration (Section 9) on the address being used during the handshake. An endpoint that receives this transport parameter MUST NOT use a new local address when sending to the address that the peer used during the handshake."
- NAT rebinding. §9: "The peer could experience NAT rebinding: a change of address due to a middlebox, usually a NAT, allocating a new outgoing port or even a new outgoing IP address for a flow. An endpoint MUST perform path validation (Section 8.2) if it detects any change to a peer's address, unless it has previously validated that address." §9.3: "Receiving a packet from a new peer address could be the result of a NAT rebinding at the peer."
- Header protection. RFC 9001 §5.4: "Parts of QUIC packet headers, in particular the Packet Number field, are protected using a key that is derived separately from the packet protection key and IV." RFC 9000 §7: "QUIC packet protection is used to encrypt as much of the handshake protocol as possible."
- HTTP/3 discovery via Alt-Svc. https://www.rfc-editor.org/rfc/rfc9114.txt §3.1.1: "An HTTP origin can advertise the availability of an equivalent HTTP/3 endpoint via the Alt-Svc HTTP response header field or the HTTP/2 ALTSVC frame ([ALTSVC]) using the "h3" ALPN token." Example "Alt-Svc: h3=":50781"". "On receipt of an Alt-Svc record indicating HTTP/3 support, a client MAY attempt to establish a QUIC connection to the indicated host and port".
- UDP blocked, fall back to TCP. RFC 9114 §3.1: "Connectivity problems (e.g., blocking UDP) can result in a failure to establish a QUIC connection; clients SHOULD attempt to use TCP-based versions of HTTP in this case."
- HTTPS DNS record. https://www.rfc-editor.org/rfc/rfc9460.txt §9: "the HTTPS RR type is defined as a SVCB-compatible RR type, specific to the "https" and "http" schemes." §7.1: "The "alpn" and "no-default-alpn" SvcParamKeys together indicate the set of Application-Layer Protocol Negotiation (ALPN) protocol identifiers [ALPN] and associated transport protocols supported by this service endpoint". Example: "if the SVCB ALPN set is ["http/1.1", "h3"] and the client supports HTTP/1.1, HTTP/2, and HTTP/3, the client could attempt to connect using TLS over TCP with a ProtocolNameList of ["http/1.1", "h2"] and could also attempt a connection using QUIC with a ProtocolNameList of ["h3"]."

## 6. BGP and anycast (RFC 4271, 4786, 7094)

- BGP decision order. https://www.rfc-editor.org/rfc/rfc4271.txt §9.1.1: "If the route is learned from an internal peer, either the value of the LOCAL_PREF attribute is taken as the degree of preference, or the local system computes the degree of preference of the route based on preconfigured policy information." §9.1.2: the speaker picks the route that has "a) the highest degree of preference of any route to the same set of destinations, or b) is the only route to that destination, or c) is selected as a result of the Phase 2 tie breaking rules specified in Section 9.1.2.2."
- Tie-break order. §9.1.2.2: "The criteria MUST be applied in the order specified." a) "Remove from consideration all routes that are not tied for having the smallest number of AS numbers present in their AS_PATH attributes." b) lowest Origin number. c) less-preferred MULTI_EXIT_DISC (only comparable from the same neighboring AS). d) "If at least one of the candidate routes was received via EBGP, remove from consideration all routes that were received via IBGP." e) less-preferred interior cost to NEXT_HOP. f) lowest BGP Identifier. g) "Prefer the route received from the lowest peer address."
- Anycast and TCP. https://www.rfc-editor.org/rfc/rfc4786.txt §4.1: "Since it is usually a requirement that a single client-server interaction is carried out between a client and the same server node for the duration of the transaction, it follows that the routing system's node selection decision ought to be stable for substantially longer than the expected transaction time, if the service is to be provided reliably." Same section: "Operators should be aware that, especially for long running flows, there are potential failure modes using anycast that are more complex than a simple 'destination unreachable' failure using unicast." §4.4.3 (equal-cost paths): "there is a risk that different request packets associated with a single transaction might be delivered to more than one node. Services provided over TCP [RFC0793] necessarily involve transactions with multiple request packets, due to the TCP setup handshake."
- "Nearest" is topological. RFC 4786 §3.2: "Topological nearness within the routing system does not, in general, correlate to round-trip performance across a network". https://www.rfc-editor.org/rfc/rfc7094.txt §1: "is to the "closest" instance as determined by unicast routing topology metric(s)". Definition of catchment, RFC 4786 §2: "the topological region of a network within which packets directed at anycast addresses are routed to one particular node."

## 7. Cloud providers

Also: "Global Accelerator terminates TCP connections from clients at AWS edge locations and, almost concurrently, establishes a new TCP connection with your endpoints." And "Traffic travels over the well-monitored, congestion-free, redundant AWS global network to the endpoint." Intro page https://docs.aws.amazon.com/global-accelerator/latest/dg/what-is-global-accelerator.html: "The static IP addresses are anycast from the AWS edge network." and "With a standard accelerator, Global Accelerator directs traffic over the AWS global network to endpoints in the nearest Region to the client." (The exact words "enters the AWS global network at the edge location closest to users" were not found; the quote above is the page's wording.)
- CloudFront network (viewer side only). https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Introduction.html: "CloudFront speeds up the distribution of your content by routing each user request through the AWS backbone network to the edge location that can best serve your content." CloudFront to origin, https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/HowCloudFrontWorks.html: "CloudFront also keeps persistent connections with origin servers so objects are fetched from the origins as quickly as possible."
- Cloudflare path. https://developers.cloudflare.com/fundamentals/reference/tcp-connections/ (last updated Apr 20, 2026): "Users connect to Cloudflare by sending requests from their devices to Cloudflare's global network. Cloudflare connects to the origin server by acting as an intermediary between the user and the origin." Diagram: Visitor <-- Connection --> Cloudflare global network <-- Connection --> Origin server. "User traffic is routed to the nearest Cloudflare data center based on the shortest Border Gateway Protocol (BGP) path, thanks to anycast routing." "In case a request is not served from Cloudflare's data centers, Cloudflare will open a connection to the origin server to forward the request." Idle: "For connections to users, Cloudflare has a default idle timeout of 400 seconds. After the 400 seconds, Cloudflare will start sending keep-alive probes every 75 seconds. Also: "TCP connection settings between the user and Cloudflare, and between Cloudflare and Origin can be customized for Enterprise customers."

## 8. nginx, OpenSSL, curl

- nginx directive. https://nginx.org/en/docs/http/ngx_http_ssl_module.html, ssl_early_data: "Syntax: ssl_early_data on | off; Default: ssl_early_data off;" "Enables or disables TLS 1.3 early data." "Requests sent within early data are subject to replay attacks. To protect against such attacks at the application layer, the $ssl_early_data variable should be used." Example: "proxy_set_header Early-Data $ssl_early_data;" "OpenSSL built-in replay protection is disabled, because it interferes with session resumption. It can be turned back if deemed necessary." Command: "ssl_conf_command Options AntiReplay;"
- nginx variable. Same page, embedded variables: "$ssl_early_data returns "1" if TLS 1.3 early data is used and the handshake is not complete, otherwise "" (1.15.3)."
- OpenSSL anti-replay. https://docs.openssl.org/master/man3/SSL_read_early_data/ (also covers SSL_CTX_set_max_early_data), section REPLAY PROTECTION: "When early data is in use the TLS protocol provides no security guarantees that the same early data was not replayed across multiple connections. As a mitigation for this issue OpenSSL automatically enables replay protection if the server is configured with a nonzero max early data value. With replay protection enabled sessions are forced to be single use only. If a client attempts to reuse a session ticket more than once, then the second and subsequent attempts will fall back to a full handshake (and any early data that was submitted will be ignored)." "The replay protection mechanism relies on the internal OpenSSL server session cache (see SSL_CTX_set_session_cache_mode(3)). When replay protection is being used the server will operate as if the SSL_OP_NO_TICKET option had been selected". Opt-out: "it is possible to turn off the built-in replay protection feature using the SSL_OP_NO_ANTI_REPLAY option." (So: stateful single-use tickets in the server cache are what block replay; stateless tickets cannot do this.) Note on page: these functions cannot be used with QUIC SSL objects.
- curl -w variables. https://curl.se/docs/manpage.html (--write-out): "time_connect: The time, in seconds, it took from the start until the TCP connect to the remote host (or proxy) was completed." "time_appconnect: The time, in seconds, it took from the start until the SSL/SSH/etc connect/handshake to the remote host was completed." "time_starttransfer: The time, in seconds, it took from the start until the first byte was received. This includes time_pretransfer and also the time the server needed to calculate the result." "num_connects: Number of new connects made in the recent transfer." Also "time_namelookup: ... until the name resolving was completed."
