1. The interview and how to answer

Covers: what the rounds test, the shape of a good answer, what makes a question easy, medium or hard, project questions · Sources: none needed (method chapter); every fact in later chapters names its source

A full stack interview checks that you can build and run one feature end to end: the page in the browser, the API, the database, and the deploy. This explainer skips data structures and algorithms. It covers the questions about how the web works, and the patterns you use to make it work under load, failure and attack.

Most questions are about one layer of the stack. A good answer knows where that layer sits and what it talks to. So first, the stack itself, one layer at a time.

The browser runs your front end. Questions here are about the JavaScript runtime, rendering, React, and how the page gets data.

Between the browser and your code sit the network and the edge. Questions: what happens when you type a URL, HTTPS, caching at a CDN, load balancing.

The API servers hold your back end code. Questions: REST design, status codes, authentication, input validation, security.

State lives in a database, often with a cache in front. Questions: indexes, N+1 queries, transactions, cache invalidation.

Slow work goes to a queue. Deploys, logs and metrics keep it running. Questions: background jobs, migrations without downtime, debugging production. The system design round asks you to draw all of this for a new product (chapter 15).

Questions

EasyWalk me through a feature you built, from the UI to the database.

Pick one feature and follow one request through it. Say what the user clicks, which API it calls, what the server checks, which tables it reads and writes, and how the UI shows the result. Name one decision you made at each layer and why. Interviewers use this to see if you know the layers you did not write yourself.

MediumTell me about a bug you shipped to production.

Use four parts: the situation, what you had to do, what you did, and the result. Say how you found it (an alert, a user report, logs), how you limited the damage (rollback, feature flag), the root cause, and the change that stops it from coming back (a test, a check, a process change). Blame no one. The interviewer wants to see that you find causes and fix systems, not only symptoms.

HardTell me about a technical decision you would make differently now.

Name the decision, the facts you had then, and the facts that changed. For example: "We stored sessions in server memory. It was simple with one server. When we added a second server behind a load balancer, users got logged out." Then say what you would choose now and what that choice costs. A good answer shows a trade-off, not a mistake you hide.

2. From URL to pixels

Covers: DNS, TCP, TLS 1.2 vs 1.3, HTTP request, connection reuse, HTTP/1.1 vs 2 vs 3, critical rendering path, render-blocking CSS and JS · Sources: RFC 8446 (TLS 1.3), Cloudflare blog "Introducing 0-RTT" (round trips of TLS 1.2 and 1.3), RFC 9112 s9.3 (persistent connections), RFC 9113 (HTTP/2), RFC 9114 (HTTP/3), MDN "Critical rendering path", MDN <script> defer/async, web.dev case studies

When you type a URL and press Enter, the browser finds the server's IP address (DNS), opens a connection (TCP), makes it private (TLS), sends an HTTP request, and gets HTML back. Then it turns the HTML and CSS into pixels. The network steps cost round trips. The render steps cost CPU time.

A round trip is one message to the server and the reply back. Its time (the RTT) depends on distance. Light in fibre is not instant, so a server on another continent costs much more per round trip than a server in your city. A cold page load needs several round trips before the first byte of HTML arrives. That is why most speed work on the network side removes round trips.

The browser first checks its own cache. A fresh cached copy needs no network at all. That is the fastest request: the one you don't send.

DNS turns acmeshop.com into an IP address. The browser and the OS cache answers for the record's TTL. A resolver that has the answer cached replies in one round trip to the resolver. See the DNS explainer for the full lookup.

TCP opens a reliable connection with a three-way handshake: SYN, SYN-ACK, ACK. The client can send its data with the ACK, so this costs one round trip.

TLS agrees on keys and proves the server owns the name, with a certificate. TLS 1.3 does this in one round trip. TLS 1.2 needs two. Now the connection is encrypted.

The browser sends GET / and waits for the reply. That is one more round trip, plus the time the server needs to build the page. The time from the request to the first byte of the reply is the TTFB.

The browser parses HTML into the DOM and CSS into the CSSOM. It combines them into the render tree, computes sizes and positions (layout), fills in pixels (paint), and puts the layers together (composite). CSS blocks rendering. A plain <script> blocks HTML parsing until it has loaded and run.

Questions

EasyWhat happens when you type a URL and press Enter?
  1. The browser checks its HTTP cache.
  2. DNS turns the name into an IP address.
  3. TCP handshake (1 round trip), then TLS handshake (1 round trip in TLS 1.3).
  4. The browser sends the HTTP request. The server (or a CDN in front of it) replies with HTML.
  5. The browser parses HTML into the DOM, finds CSS, JS and images, and fetches them.
  6. It builds the render tree, does layout and paint, and shows the page.

Say where each step can be cached or skipped. That turns an easy answer into a strong one.

EasyWhat is the difference between HTTP and HTTPS?

HTTPS is HTTP inside a TLS connection. TLS gives three things: encryption (others on the path can't read it), integrity (they can't change it unnoticed) and authentication (the certificate proves the server owns the name). It costs a handshake on each new connection: one round trip in TLS 1.3, two in TLS 1.2.

MediumWhy is the second page load faster than the first?

Four caches save work. The DNS answer is cached for its TTL. The TCP and TLS connection is often still open (HTTP/1.1 connections are persistent by default, RFC 9112). Static files are in the HTTP cache, so they need no request, or only a short revalidation. TLS can resume a session with less work. The lab shows it: a repeat visit pays one round trip, not three or four.

MediumWhat changed from HTTP/1.1 to HTTP/2 to HTTP/3?

HTTP/1.1 sends one request at a time per connection, so browsers open several connections to one host. HTTP/2 (RFC 9113) sends many requests at once on one connection, as separate streams, and compresses headers. But it still runs on TCP. One lost packet stops all streams until it is resent. That is head-of-line blocking. HTTP/3 (RFC 9114) runs on QUIC over UDP. QUIC puts each stream in its own order, so a lost packet only stops its own stream. QUIC also merges the transport and TLS 1.3 handshakes into one round trip.

MediumWhat blocks the first render, and how do defer and async help?

The browser does not paint until it has the CSS in the <head>, because it would paint the wrong styles. A plain <script> stops the HTML parser until the script is downloaded and has run, because the script can change the DOM. defer downloads in parallel and runs after parsing, in document order. async downloads in parallel and runs as soon as it arrives, in any order. Use defer for app code, async for independent scripts such as analytics.

HardThe site is fast in your office in Frankfurt but slow for users in Sydney. Why, and what do you do?

The server code is the same, so the difference is distance. Every round trip to Frankfurt costs Sydney users far more, and a cold load needs several before the first byte. Fixes, in order of effect:

  • Put a CDN in front, so TLS ends near the user and static files come from a nearby cache.
  • Cut round trips: TLS 1.3, HTTP/2 or 3, keep connections open, <link rel="preconnect"> to other origins you need early.
  • Cut requests on the critical path: inline the critical CSS, defer scripts.
  • If the HTML itself is dynamic, run that part closer to the users (a region in Australia, or edge rendering).

Measure first with real-user data from that region (TTFB, LCP). The lab "Far, cold" case shows why: every step grows with the RTT.

HardWhy does a new HTTPS connection cost more than the handshake round trips?

A new TCP connection starts with a small congestion window, so it can only send a little data before it waits for acknowledgements. It grows the window each round trip (slow start). A large first response therefore takes several more round trips on a new connection than on a warm one. This is one more reason to reuse connections, and the reason CDNs keep warm connections to the origin. See the CDN explainer, chapter 8.

Real examples

  • Vodafone (2021): faster LCP, more sales. In an A/B test, "a 31% improvement in LCP led to 8% more sales, a 15% improvement in their lead to visit rate, and a 11% improvement in their cart to visit rate." (web.dev/case-studies/vodafone, checked 2026-10-07)
  • One round trip less with TLS 1.3. Cloudflare: TLS 1.3 "only requires one round trip to set up the connection, resumed or not", while "For TLS 1.2 and earlier, this takes two round trips." The curl lab above shows the TLS 1.3 handshake as one round trip on the 80 ms link. (blog.cloudflare.com/introducing-0-rtt, read through a summary tool)

3. HTTP and REST API design

Covers: methods, safe and idempotent, PUT vs PATCH, status codes, 401 vs 403, versioning, offset vs cursor pagination, long-running requests, REST vs GraphQL vs gRPC · Sources: RFC 9110 (HTTP semantics), RFC 5789 (PATCH), RFC 6585 (429), PostgreSQL 18 docs (LIMIT and OFFSET, row comparison), Stripe, Slack and GitHub API docs (checked 2026-10-07)

HTTP is a request and reply protocol: a method and a path go in, a status code and a body come back. REST is a style of API on top of it. Each thing is a resource with a URL, and the HTTP method says what to do with it.

The method is a promise to everything on the path. Browsers, caches, proxies and retry logic read it. A safe method (GET, HEAD, OPTIONS) asks to read only. An idempotent method (the safe ones plus PUT and DELETE) has the same effect if you send it once or five times. So a client may retry it after a timeout. POST and PATCH are neither, so a blind retry can do the work twice.

Pagination: offset vs cursor

A list endpoint returns one page at a time. Offset pagination says "skip 40 rows, give me 20" (?page=3). It is simple and lets users jump to any page. But the database still reads and throws away every skipped row, so deep pages get slow. And if a row is added or removed while the user pages, every later row shifts. The user sees a row twice, or misses one.

Cursor pagination (also called keyset) says "give me 20 rows after this one" (?after=9996). The server turns the cursor into a WHERE on the sort key, so an index jumps straight there. Inserts don't shift anything. The cost: no jumping to page 50, and the sort key must be unique. Add the ID as a tie-breaker, as in (created_at, id).

Questions

EasyWhat is the difference between PUT and PATCH?

PUT sends the whole new resource and replaces the old one. Fields you leave out are gone. Sending the same PUT twice gives the same result, so it is idempotent. PATCH sends only the changes. RFC 5789 says PATCH is not always idempotent: {"op":"increment","field":"stock"} sent twice adds 2. A PATCH that only sets fields to values is idempotent in practice.

EasyWhat is the difference between 401 and 403?

401 Unauthorized means "I don't know who you are": the credentials are missing, expired or wrong. Log in and try again. The server sends a WWW-Authenticate header with it. 403 Forbidden means "I know who you are, and you may not do this". Logging in again does not help. Some APIs return 404 instead of 403 to hide that the resource exists at all.

EasyWhat does idempotent mean, and why does it matter?

Sending the request many times has the same effect on the server as sending it once. It matters because networks fail in the middle. After a timeout, the client can't know if the server did the work. If the method is idempotent, it can just retry. If not (POST), a retry may create two orders or charge a card twice.

MediumHow do you make "create payment" safe to retry?

The client makes a unique idempotency key per operation (a UUID) and sends it in a header. The server stores the key with the result, in the same transaction as the work. A retry with the same key gets the stored result, and no second charge. A unique constraint on the key stops two parallel copies. Stripe's API works this way. The microservices explainer, chapter 9, has a lab on real Redis.

MediumHow do you version an API, and how do you avoid needing to?

Common ways: the path (/v1/orders), a header (Accept: application/vnd.acme.v2+json), or a dated version header, as Stripe does. The path is the easiest to see and to route. Most changes need no new version if they only add: new fields, new endpoints, new optional parameters. Clients must ignore fields they don't know. Breaking changes are removing or renaming a field, changing a type or meaning, or adding a required parameter. For those, run both versions for a time and track who still calls the old one.

MediumOffset or cursor pagination?

Offset for small, stable lists where users jump to a page number, such as an admin table. Cursor for feeds, infinite scroll, large tables and public APIs. The lab shows both reasons: a deep offset reads every skipped row, and new rows cause duplicates. Make the cursor opaque to clients (for example base64 of created_at,id), so you can change it later.

HardA request takes 3 minutes (a big CSV export). How do you design the API?

Don't hold the HTTP request open: proxies and load balancers time out, and a retry starts the work again. Accept the job and return 202 Accepted with a job URL (Location: /exports/881). A worker does the export from a queue and stores the file. The client polls GET /exports/881 for pending / done + download URL, or the server sends a webhook or a push message when done. Make job creation idempotent, so a double click makes one export.

HardREST, GraphQL or gRPC?
  • REST: simple, works with HTTP caches and every tool. The client may need many calls per screen, or get fields it doesn't need.
  • GraphQL: one endpoint, and the client asks for exactly the fields a screen needs. Good when many clients need different shapes. Costs: queries come as POST, so HTTP caches don't help. Nested fields can cause N+1 queries on the server (use a batching loader). One deep query can be very expensive, so limit depth and cost.
  • gRPC: binary Protocol Buffers over HTTP/2, with a typed contract and streaming. Good between services. Browsers need a proxy (gRPC-Web).

A common answer: REST or GraphQL at the edge for browsers, gRPC between internal services.

Real examples

  • Stripe: cursor pagination and idempotency keys. List endpoints take starting_after and ending_before, and "Both parameters accept an existing object ID value". For retries: Stripe saves "the resulting status code and body of the first request made for any given idempotency key", and keys may be removed "after they're at least 24 hours old". (docs.stripe.com/api/pagination and /api/idempotent_requests, checked 2026-10-07)
  • Slack: cursors. "Most methods that support pagination use a cursor-based approach." Cursors "help avoid loading an entire set just to give you a slice." (api.slack.com/docs/pagination)
  • GitHub: the Link header. The REST API puts page URLs in a link response header with rel="next", rel="prev" and rel="last", so clients follow links instead of building page numbers. (docs.github.com, Using pagination in the REST API)

4. The JavaScript event loop

Covers: call stack, tasks and microtasks, async/await, timers, closures, var/let/const, this, Promise combinators, blocking the main thread, memory leaks · Sources: WHATWG HTML Living Standard (event loops, timers), MDN (microtasks, closures, this, Promise), Node.js docs ("The Node.js Event Loop", "Don't Block the Event Loop")

JavaScript runs your code on one thread with one call stack. The event loop is the rule for what runs next when the stack is empty: first every queued microtask (promise callbacks), then one task (a timer, a click, a network event), then microtasks again, and so on.

Your code never runs in parallel with other JavaScript on the same page. A function always runs to the end before anything else starts. So async code is not about doing two things at once on the thread. It is about not waiting: you start the work (a timer, a fetch), give the thread back, and a callback is queued when the work is done.

There are two queues. The task queue gets timers, events and I/O callbacks. The microtask queue gets promise reactions (.then, the rest of an async function after await) and queueMicrotask. After each task, the browser runs a microtask checkpoint: it empties the microtask queue completely, including microtasks that were added while it ran. Only then can it render or take the next task.

Call stackruns one function at a time, to the end
Web APIs / Node APIstimers, fetch, DOM events, file I/O
Task queuesetTimeout, click, message, I/O

Event loopstack empty → all microtasks → render if due → one task

The call stack runs your script. While it runs, nothing else in JavaScript can run.

Calls such as setTimeout or fetch hand the waiting to the browser (or to Node's libuv). The stack is free at once.

When the timer fires or the event happens, its callback goes into the task queue.

When a promise settles, its .then callback goes into the microtask queue. The rest of an async function after await is one of these.

When the stack is empty, the loop runs all microtasks, lets the browser render if a frame is due, then takes one task. So a promise callback always runs before a timer that was queued earlier.

Questions


EasyWhat is the difference between var, let and const?


var is scoped to the function and is hoisted with the value undefined, so you can read it before the line that declares it. let and const are scoped to the block ({ }). They are also hoisted, but reading them before the declaration throws a ReferenceError (the temporal dead zone). const can't be reassigned, but an object in a const can still change: const a = []; a.push(1) works. In a loop, let makes a new binding per pass. The lab shows what that does to callbacks.



EasyWhat is a closure?


A function together with the variables it could see where it was created. The function keeps those variables alive after the outer function returned. Uses: private state (the counter preset), callbacks that remember their context, function factories, memoization. Cost: everything the closure can reach stays in memory while the closure is reachable.



EasyWhat is the difference between == and ===?


=== compares without type conversion. == converts types first, with surprising rules: 0 == '' and null == undefined are true, but null == 0 is false. Use ===. The one common exception is x == null, which checks for both null and undefined.



MediumExplain the event loop. In which order does this code print?


Synchronous code first, to the end. Then all microtasks, in the order they were queued, including new ones added meanwhile. Then one task, such as a timer. For the lab code: A E G C D F B. E prints at once because an async function runs synchronously until its first await. F is a microtask queued by await. B is a task, so it comes last although its delay was 0.



MediumHow does this work?


For a normal function, this is set by how you call it, not where you wrote it. obj.f() gives obj. A plain call f() gives undefined in strict mode (the global object in sloppy mode). new F() gives the new object. f.call(x), f.apply(x) and f.bind(x) set it to x. Arrow functions have no own this: they use the this of the place where they were written. That is why arrow functions are used for callbacks inside methods. The classic bug: button.onclick = obj.handle loses obj, because the browser calls the function with this set to the button.



MediumPromise.all, allSettled, race and any: when do you use each?


  • all: you need every result. It rejects at the first failure, but the other operations keep running.
  • allSettled: you want every outcome, success or failure, for example to show which uploads failed.
  • race: the first to settle wins, success or failure. Used for a timeout: race the fetch against a timer.
  • any: the first success wins. It rejects only if all fail. Used to ask several mirrors.
Also: await in a for loop runs the calls one after the other. If they don't depend on each other, start them all and await Promise.all.



HardOne request with a slow regex makes your whole Node.js server stop answering. Why, and how do you fix it?


Node runs all JavaScript for all requests on one thread. While one request runs CPU work, no other callback can run, so every other request waits. The lab "Block the thread" shows the same on the page. A regex with nested repetition, such as (a+)+$, can take exponential time on a crafted input. Attackers use this (ReDoS). Fixes: limit input size, avoid nested quantifiers, use a regex engine with linear time (such as RE2) for user input, move heavy CPU work to worker_threads or a job queue, and split long loops into chunks. Monitor event loop delay as a metric.



HardYour single-page app uses more memory every hour. How do you find the leak?


Typical causes: event listeners or setInterval that are never removed when a component unmounts, subscriptions (WebSocket, store) not closed, caches with no size limit, and DOM nodes that are removed from the page but still referenced from JavaScript (detached nodes). Each of these keeps a closure alive, and the closure keeps everything it can reach. To find it: take a heap snapshot in DevTools, do the action several times (open and close the dialog), take another snapshot, and compare. Look for object counts that only grow, and for "Detached" DOM trees. Then follow the retainer path to the reference that holds it.

5. Rendering, Web Vitals, debounce


Covers: style, layout, paint, composite; reflow and layout thrashing; Core Web Vitals (LCP, INP, CLS) and their thresholds; debounce vs throttle; long tasks · Sources: web.dev (Core Web Vitals, INP, CLS, LCP, optimize long tasks), MDN (LayoutShift, PerformanceObserver, critical rendering path), Chrome for Developers


After the browser has the DOM and CSS, it turns them into pixels in steps: compute styles, lay out boxes (sizes and positions), paint, and composite layers. A change that moves boxes forces layout again (a reflow). Core Web Vitals are three numbers Google uses to measure how this feels to users: how fast the main content shows (LCP), how fast the page reacts to input (INP), and how much the layout jumps (CLS).


All of this runs on the main thread, the same thread as your JavaScript (chapter 4). If a script runs for 300 ms, the page can't paint or react to a click for 300 ms. So rendering speed and JavaScript speed are one problem.

Debounce and throttle


Some events fire very often: input on every key, scroll and mousemove many times a second. If the handler is expensive (a search request, a layout read), you run it less often. Debounce waits until the events stop for a set time, then runs once. Use it for search-as-you-type. Throttle runs at most once per interval while the events keep coming. Use it for scroll position or resize.

Questions


EasyWhat is the difference between reflow and repaint?


Reflow (layout) computes the size and position of boxes. Changing width, height, font size or adding elements causes it, and it can affect many elements. Repaint fills in pixels again, for example after a color change, without moving anything. Changes to transform and opacity can often skip both and happen in the compositor, which is why animations should use them.



EasyWhat is the difference between debounce and throttle?


Debounce runs the function once after the events stop for N ms. Throttle runs it at most once every N ms while the events continue. Search box: debounce. Scroll or resize handler: throttle. The lab shows both on the same key presses.



EasyWhat are the Core Web Vitals?


LCP (loading, good ≤ 2.5 s), INP (responsiveness, good ≤ 200 ms) and CLS (visual stability, good ≤ 0.1), each at the 75th percentile of real page visits. INP replaced FID in March 2024. FID measured only the delay before the first input was handled. INP measures the full time to the next paint, for interactions across the whole visit.



MediumLCP is 4 seconds. How do you improve it?


Split LCP into its parts and fix the biggest: time to first byte (server, CDN, caching), the delay before the browser starts to load the LCP resource, its load time, and the render delay. Common fixes: serve HTML from a cache or CDN. Make the hero image findable in the HTML (not set by JavaScript or CSS later). Give it fetchpriority="high" and never loading="lazy". Serve it in a modern format at the right size. Inline critical CSS and defer scripts. Render the main content on the server instead of after a client fetch.



MediumHow do you stop layout shifts?


Give images and videos width and height attributes (or CSS aspect-ratio), so the browser reserves the box before the file loads. Reserve space for ads, embeds and banners with a fixed slot size. Don't insert content above content the user already sees, unless the user asked (a click). Load web fonts with fallback metrics close to the real font (size-adjust), so text does not reflow when the font arrives. Animate with transform, which does not shift layout.



MediumWhat is layout thrashing?


Code that writes a style and then reads a layout value (such as offsetHeight) in a loop. Each read forces the browser to do layout now, because the write made the old layout wrong. 100 items cost 100 layouts instead of 1. Fix: do all reads first, then all writes, or put writes in requestAnimationFrame.



HardINP is 600 ms on your product page. How do you find and fix the cause?


Find the slow interaction first: real-user data (the web-vitals library reports which element and which phase), then record it in the DevTools Performance panel. An interaction has three parts: input delay (the thread was busy with something else), processing time (your handlers), and presentation delay (style, layout, paint of the result). Fixes for each:
  • Input delay: break up long tasks from other scripts (third-party tags, hydration), so the thread is free more often.
  • Processing: do only the visible update first, then yield to the browser (await scheduler.yield(), or setTimeout) before the rest, such as analytics. In React, mark the slow part with startTransition.
  • Presentation: reduce the DOM size and the area that changes. Virtualize long lists.
A task over 50 ms is a "long task". The goal is that no single task holds the thread long enough to miss a frame after input.

6. React: rendering, keys, state


Covers: render and commit, reconciliation, keys, state updates and batching, updater functions, useEffect and when not to use it, memoization, controlled inputs, CSR vs SSR vs SSG, hydration, Server Components · Sources: react.dev (Preserving and Resetting State, Rendering Lists, Queueing a Series of State Updates, You Might Not Need an Effect, useEffect, useMemo, memo, Server Components)


A React component is a function from props and state to a description of UI. When state changes, React calls the function again (render), compares the new description with the old one (reconciliation), and changes only the DOM nodes that differ (commit).


Reconciliation must decide which old element matches which new element. It matches by type and by position in the parent. In a list, position is not enough, because items move. So you give each item a key. React then matches old and new items by key. A matched item keeps its DOM node and its state. A new key gets a new node with fresh state.


That is where the bug comes from. If the key is the array index, then after you add an item at the top, the old first item and the new first item both have key 0. React thinks it is the same item with new props. Text that came from props updates. But state inside the item, such as an uncontrolled input's text, a checkbox or a component's useState, stays with key 0, so it now sits next to the wrong item.

Questions


EasyWhat is the difference between props and state?


Props come from the parent and are read-only in the child. State belongs to the component, and only it can change it, through the setter. A state change renders that component and its children again. If two siblings need the same data, move the state up to their common parent and pass it down (lifting state up).



EasyWhy does React need keys in lists, and why not use the index?


Keys tell React which item is which between renders, so it can keep each item's DOM node and state when the list changes order. The index changes when you insert, delete or sort, so state stays at a position instead of with its item. The lab shows a note moving to the wrong todo. Use a stable ID from the data. The index is fine only for lists that never reorder and have no item state.



EasyWhat is the difference between a controlled and an uncontrolled input?


Controlled: React state holds the value (value={text} onChange={...}). React is the one source of truth, so you can validate or change the text on each key. Uncontrolled: the DOM holds the value, and you read it with a ref or from the form on submit. Less code and fewer renders, good for simple forms.



MediumI call setCount(count + 1) three times and the count goes up by 1. Why?


count is a constant in this render. All three calls queue "set to 1". React batches them into one render. Use the updater form setCount(c => c + 1): React passes each one the result of the one before. The batching lab shows the queue.



MediumWhen should you NOT use useEffect?


  • To compute a value from props or state: compute it during render. If it is slow, use useMemo.
  • To respond to a user event: do it in the event handler. You know what happened there.
  • To reset state when a prop changes: give the component a key from that prop.
  • To fetch data in a large app: a data library or the framework's loader handles caching and races (chapter 7).
An effect is for syncing with an outside system. Each extra effect costs one more render and adds a chance of loops and stale values.



MediumWhat do useMemo, useCallback and React.memo do, and when are they worth it?


React.memo skips rendering a component if its props are equal (compared with Object.is) to last time. A new object or function on each render is never equal, so useMemo (for values) and useCallback (for functions) keep the same reference between renders. Use them when you measured a slow render, when a value is passed to a memo component, or when it is a dependency of an effect. Elsewhere they add code and comparisons for nothing. The React Compiler can add this memoization for you.



HardCSR, SSR, SSG and Server Components: what is the difference, and what is hydration?


  • CSR (client-side rendering): the server sends an empty HTML shell and a JS bundle. The browser runs it, fetches data, renders. Slow first content, simple hosting.
  • SSR (server-side rendering): the server renders HTML for each request, so content shows fast and search engines see it. Then the JS loads and hydrates: React renders the same tree in the browser and attaches event handlers to the existing HTML. Until then, the page shows but does not react. If the server and client output differ (dates, Math.random, window checks), you get a hydration mismatch.
  • SSG (static generation): render at build time, serve from a CDN. Fast and cheap, for content that changes rarely. Incremental regeneration rebuilds pages after a set time.
  • Server Components: components that run only on the server and send their result, not their code, to the browser. They can read the database directly. Only components marked 'use client' ship JS and hydrate.



HardAn effect with setInterval shows the same count forever. Why?


The interval callback is a closure from the first render, so it always sees count = 0 (a stale closure). setCount(count + 1) sets 1 every second. Fixes: use the updater form setCount(c => c + 1), so the closure needs no state. Or list count in the dependency array, so the effect re-subscribes with a fresh closure. Always return a cleanup function that clears the interval, or each re-run adds one more timer.

A client sends a request and gets the answer later. In between, the user keeps typing, clicking and leaving pages. Most front end data bugs come from that gap: an old answer arrives after a new one, an answer arrives for a page that is gone, or the screen shows a change the server then refuses.

Questions


EasyDoes fetch throw on a 404 or 500?


No. The promise rejects only on a network failure (no connection, DNS failure, CORS block, abort). A 404 or 500 resolves normally. You must check res.ok (status 200 to 299) or res.status yourself. Also, fetch has no timeout by default: pass signal: AbortSignal.timeout(5000).



EasyWhere should you keep server data compared with UI state?


Server data (a list of orders) is a copy of something the server owns. It goes stale, many components need it, and it must be refetched after changes. Keep it in a cache layer such as TanStack Query, SWR or your framework's loader, which handles caching, dedup and refetch. UI state (is the menu open, form input) belongs to the component. State that should survive a reload or a shared link (filters, page, tab) belongs in the URL.



MediumThe search results sometimes don't match what is typed. What is the bug and how do you fix it?


Responses arrive out of order, and the code shows every one, so a slow early response overwrites a fast late one. Fix it in one of three ways (the lab shows each): drop answers that are not for the latest request (a flag set in the effect cleanup, or compare a request ID), cancel old requests with AbortController, or debounce so fewer requests exist. Use abort plus debounce for search: fewer requests, and none can arrive late.



MediumAfter the user edits an item, the list still shows the old value. Why?


The list came from a client cache, and nothing told the cache that the item changed. After a mutation, either invalidate the queries that contain the item (they refetch), or write the new value into the cache from the mutation's response. Also check HTTP caching: a GET with Cache-Control: max-age may be served from the browser cache without asking the server.



MediumHow do you implement an optimistic update safely?


Before the request: cancel any refetch of that data, save the old value, write the new value to the cache. On error: restore the saved value and show a message. On settle (success or error): refetch, so the cache matches the server. The lab shows why each request must undo only its own change.



HardTwo people edit the same record in two tabs. The second save silently wipes the first. How do you stop it?


This is a lost update. Use optimistic concurrency. Each record has a version (a number, or an ETag from the server). The client sends the version it read with the save: If-Match: "v7", or WHERE id = 42 AND version = 7. If someone saved in between, the version no longer matches. The server changes nothing and answers 412 Precondition Failed (or 409). The client shows "this was changed by someone else", with a reload or merge. No locks are held while users think. Chapter 10 shows the same race inside the database.



HardHow do you build an infinite list of 50,000 items that stays fast?


Load with cursor pagination (chapter 3), so pages stay correct while new items arrive. Render with virtualization: only the rows in view plus a small buffer exist in the DOM, and spacers keep the scroll height right. Keep item heights fixed or measured. Cap how many pages stay in memory. Keep the cursor and scroll position in the URL or history state, so "Back" returns to the same place. Make the "load more" trigger an IntersectionObserver on a sentinel row, not a scroll handler.

Questions


EasyHow should you store passwords?


Never in plain text and never with reversible encryption. Store a slow, salted password hash: Argon2id is OWASP's first choice, bcrypt is common. The salt is random per user, so two users with the same password get different hashes and precomputed tables don't work. "Slow" is the point: it makes each guess expensive for an attacker who stole the table. A fast hash such as SHA-256 lets a GPU try billions of guesses per second.



EasyWhat do HttpOnly, Secure and SameSite do on a cookie?


HttpOnly: JavaScript can't read the cookie (document.cookie), so an XSS bug can't steal it. Secure: sent only over HTTPS. SameSite=Lax: not sent on cross-site sub-requests (images, fetch, POST forms from other sites), but sent when the user follows a link to your site. Strict never sends it cross-site. None always does, and needs Secure. A cookie with no SameSite is treated as Lax by modern browsers.



MediumSessions or JWT?


Sessions: instant logout and revocation, small cookie, easy to change a user's role. Cost: a store lookup per request, and the store must be shared by all servers. JWT: no lookup, so any service can check it, which suits many services and third-party APIs. Cost: you can't revoke one before exp without state, the token grows with claims, and the data in it can be stale (role changed 10 minutes ago). For one web app with its own back end, a session in an HttpOnly cookie is the simpler, safer default.



MediumWhere should a single-page app keep its tokens?


Not in localStorage: any script on the page can read it, so one XSS bug can steal every token. OWASP says not to store session identifiers there. Better: an HttpOnly, Secure cookie, which JavaScript can't read, plus CSRF defence (chapter 9). A common pattern is a backend-for-frontend: the browser has only a session cookie with your own server, and that server holds the OAuth tokens. If the SPA must hold an access token, keep it in memory only, short-lived, and get new ones with a refresh token in an HttpOnly cookie.



MediumHow do refresh tokens work?


The access token lives a short time (minutes). The refresh token lives long (days) and is used only to get new access tokens, at one endpoint. So a leaked access token is useful only briefly. With rotation, each refresh returns a new refresh token and invalidates the old one. If an old refresh token is ever used again, two parties have it, so the server revokes the whole family and forces a new login.



HardWalk through "Log in with Google" (OAuth 2.0 authorization code flow with PKCE).


  1. Your app makes a random code_verifier and sends its SHA-256 hash (code_challenge) with a redirect to Google, plus a random state.
  2. The user logs in at Google and agrees. Google redirects back to your redirect_uri with a short-lived code and the same state.
  3. Your app checks state (this stops CSRF on the login), then sends the code and the original code_verifier to Google's token endpoint.
  4. Google hashes the verifier, checks it matches the challenge, and returns an access token, and with OpenID Connect an ID token (a JWT about the user).
PKCE stops an attacker who intercepts the code from using it: they don't have the verifier. OAuth is for authorization (access to an API). OpenID Connect adds authentication (who the user is) on top. The old implicit flow, which returned tokens in the URL, should not be used (RFC 9700).



HardHow do you log a user out everywhere when you use JWTs?


Options, often combined: keep access tokens short (a few minutes) so they die soon. Revoke refresh tokens in the database, so no new access tokens are issued. For instant effect, keep a denylist of token IDs (jti) until their exp (the Redis lab), or a per-user "token version" that every token must match. Each of these adds a lookup, which is the cost JWTs were meant to avoid. That trade-off is the answer the interviewer wants to hear.



HardWhat can go wrong when you verify a JWT?


  • alg: none: a library that trusts the header accepts an unsigned token (the lab).
  • Algorithm confusion: the server expects RS256 and verifies with the public key. An attacker sends an HS256 token signed with that public key as the HMAC secret. A library that picks the algorithm from the header accepts it.
  • Not checking exp, aud (meant for this API?) or iss (from the right issuer?).
  • A weak HMAC secret that can be guessed offline from one token.
Fix: pin the allowed algorithm in the server config, never take it from the token, and check every claim.

9. Web security: XSS, CSRF, injection, CORS


Covers: SQL injection and parameterized queries, XSS (stored, reflected, DOM) and output encoding, Content Security Policy, CSRF and SameSite, CORS and preflight, broken access control (IDOR), SSRF, supply chain, OWASP Top 10 · Sources: OWASP Top 10:2025 and 2021, OWASP cheat sheets (SQL Injection, XSS, CSRF Prevention), MDN (CORS, CSP), ICO (TalkTalk 2016, British Airways 2020), samy.pl (2005)


Most web attacks have one cause: data from a user ends up treated as code. In SQL injection, the database runs it. In XSS, the victim's browser runs it. CSRF and CORS are about a different thing: which website may send requests with the user's cookies, and which may read the answers.


The fix for injection is always the same idea: keep code and data apart, so data can never change the structure of the code. Parameterized queries do this for SQL. For HTML, you encode output for the place it goes (text, attribute, URL), or set it as text instead of markup.

Break it: with q = ' OR '1'='1, the quote closes the string and the rest becomes SQL. AND binds tighter than OR, so the condition is true for every row: the hidden prototype shows up. With a UNION input, the attacker reads another table: emails and password hashes. Now the fix. The "parameterized" presets send the query and the value apart (PREPARE with $1, then EXECUTE). The same attack text is only a name to compare with, so 0 rows come back.

 
 
 
 
 
 




XSS


Cross-site scripting (XSS) is when an attacker gets their script to run in your page, in another user's browser. The script runs as your site: it can read the page, call your API with the user's cookies, and send data away. Stored XSS comes from the database (a comment). Reflected XSS comes from the URL in the same request. DOM XSS happens in the browser, when your JavaScript puts input into an unsafe sink such as innerHTML.




 
Lab: XSS in a real browser frame

 
Each button renders the comment in a small frame, the way a comment section would. The attack text here only turns the frame red and reports back. Below the frame you see the DOM the frame really built, and whether a script ran. "Render as text" uses textContent: the markup shows as text, no script runs. Break it: "Render with innerHTML" parses the comment as HTML. The <img> fails to load, its onerror runs, and the frame turns red. A <script> tag inserted with innerHTML does not run, but an event handler attribute does. "Escaped, but in an href" HTML-escapes the input and puts it in a link. Escaping stops new tags, but a javascript: URL is still code when the link is clicked (the frame clicks it). Escaping must fit the place where the data goes. For URLs, allow only http: and https:.

 

 

 
 





CSRF and CORS


The browser attaches your cookies to a request to your site, even when another site started the request. CSRF (cross-site request forgery) uses that: a page on evil-site.example submits a hidden form to api.acmeshop.com/transfer, and the user's session cookie goes with it. The attacker can't read the answer, but the transfer already happened.


CORS is a browser rule for the opposite side: which other origins may read your responses from JavaScript. It does not stop requests from arriving. A "simple" request (GET, HEAD or POST with a form content type and no custom headers) is sent at once, and CORS only decides if the page may read the reply. Any other request (JSON body, PUT, an Authorization header) needs a preflight: the browser first sends OPTIONS and asks the server for permission.

Then break it: "Evil form POST" is a simple request, so it reaches the server with the user's cookie, although the page can't read the reply. That is CSRF, and CORS does not stop it. It works here because the session cookie is SameSite=None. Switch it to SameSite=Lax and send again: the request still arrives, but without the cookie, so the server treats it as logged out. EasyWhat is SQL injection and how do you prevent it?


User input is glued into a SQL string, so input with a quote can change the query (the lab). Prevent it with parameterized queries: the SQL text and the values travel apart, and the database never parses the values as SQL. ORMs and query builders do this for you, until you use their raw-string escape hatch. Also give the app's database user only the rights it needs. Escaping by hand is fragile. Identifiers (a column name to sort by) can't be parameters, so check them against an allowlist.



EasyWhat is XSS and how do you prevent it?


An attacker's script runs in your page in another user's browser. Prevent it by encoding output for its context, and by setting text as text (textContent, or React's {value}, which escapes). Avoid raw HTML sinks (innerHTML, dangerouslySetInnerHTML). If you must render user HTML, clean it with a sanitizer such as DOMPurify. Allow only http(s): in user URLs. Add a Content Security Policy as a second layer, and keep session cookies HttpOnly.



EasyWhat is CORS?


A browser rule that lets a server say which other origins may read its responses from JavaScript. An origin is scheme + host + port. By default, a page can send requests to other origins but can't read the answers (the same-origin policy). The server opts in with Access-Control-Allow-Origin. A "CORS error" is the browser protecting the user. The server got the request (or the preflight) and its reply lacked the right headers.



MediumWhat is CSRF and how do you prevent it?


Another site makes the user's browser send a request to your site, with the user's cookies, to change something. Defences: SameSite=Lax or Strict cookies (the default is now Lax in major browsers, but treat it as one layer). A CSRF token: a random value in the page that the server checks on every state-changing request, which another site can't read. Check the Origin header on writes. Never change state on GET. APIs that take tokens only in an Authorization header are not exposed, because the browser does not add that header by itself.



MediumDoes CORS protect your API from attackers?


No. CORS is enforced only by browsers, to protect their users. curl, scripts and servers ignore it. And simple requests reach your server even when CORS fails (the lab's evil form POST). Your API still needs authentication, authorization on every request, and CSRF defence. Also: never reflect any Origin back with Allow-Credentials: true. That lets every site read your users' data.



MediumWhat does a Content Security Policy do?


A response header that tells the browser which sources of script, style, images and connections the page may use. A strict policy (scripts only with a per-response nonce, no inline event handlers, no eval) stops most injected scripts from running even if an XSS bug exists. Start with Content-Security-Policy-Report-Only to see what would break, then enforce.



HardGET /api/orders/1043 returns another customer's order if you change the number. What is wrong and how do you fix it?


Broken access control, also called IDOR (insecure direct object reference). The server checked that the user is logged in, but not that this order is theirs. It is #1 in the OWASP Top 10 (2021 and 2025). Fix: check ownership on every object access, in one place: WHERE id = $1 AND customer_id = $current_user, or a policy layer every handler must use. Return 404 for objects that are not theirs. Random IDs (UUIDs) make guessing harder but are not the fix. Add tests that call each endpoint as the wrong user.



HardYour app fetches a user-given URL to show a link preview. What can go wrong?


Server-side request forgery (SSRF). The attacker gives a URL that points inside your network: an admin service, a database port, or the cloud metadata address 169.254.169.254, which can return credentials. Your server makes the request from inside. Fixes: allow only http(s). Resolve the name and refuse private, loopback and link-local addresses, and check again after each redirect, since DNS can change between check and use. Run the fetcher in an isolated network with no access to internal services. On AWS, require IMDSv2 tokens for metadata.



HardHow do you defend against a compromised npm package?


OWASP Top 10:2025 lists software supply chain failures at #3. Defences: commit the lockfile and install with npm ci, so CI uses the exact versions you reviewed. Review new dependencies and their install scripts. Turn off install scripts where you can. Use automated advisories (Dependabot, npm audit). Load third-party scripts with Subresource Integrity (integrity="sha384-..."), so a changed file is refused. Keep payment pages free of third-party scripts.

10. Databases in app code


Covers: SQL vs NoSQL, indexes and why one is not used, composite index order, N+1 queries, transactions and ACID, isolation levels, lost updates (read-modify-write), SELECT FOR UPDATE, atomic updates, connection pools · Sources: PostgreSQL 18 docs (Transaction Isolation, Explicit Locking, SELECT, Indexes), Rails guide "Active Record Query Interface" (eager loading), Django QuerySet API. Deeper: the SQL and PostgreSQL explainer


Most back end bugs and slowdowns are in how the app talks to the database, not in the database itself. Three questions come up in almost every interview: why is this query slow (indexes), why does this page make 200 queries (N+1), and what happens when two requests change the same row at once (transactions and locks).



N+1 queries


An ORM makes it easy to load a list, then touch a relation on each item in a loop: for post in posts: post.author.name. Each access sends one more query. 1 query for the list plus N queries for the items is N+1. Each query costs at least one network round trip to the database, so the time grows with the list. The fix is to load the relation for all items at once: a JOIN, or one WHERE id IN (...) query (eager loading).




 
Lab: N+1 vs one query (model)

 
A model of a page that lists 20 posts with their authors. The query log is the hidden state: every query the ORM sends, and the time each one costs. Each query costs one round trip to the database plus 0.2 ms of work (example numbers). Start with "N+1" and an RTT of 0.5 ms (database in the same data center): 21 queries, which is fast enough that nobody notices in development. Then break it: move the RTT to 20 ms (database in another region, or a busy network). Now the page waits 21 × 20 ms. "Eager load (IN)" sends 2 queries and "JOIN" sends 1, at any list size.

 

 

 





Indexes


An index is a sorted copy of one or more columns with a pointer to each row, usually a B-tree. With it, the database finds matching rows in a few page reads instead of reading the whole table (a sequential scan). It costs disk space, and every insert and update must change the index too. An index helps only if the query's condition matches what is sorted. lower(email) = ... can't use an index on email, because the index stores email, not lower(email).





 
Lab: when an index is used, on real PostgreSQL

 
Real PostgreSQL in your browser, with 50,000 customers. Run the presets in order and read the first line of each plan. "No index" shows Seq Scan and Rows Removed by Filter: 49999: it read every row to find one. "Add index on email", then "Same query" shows Index Scan using customers_email: a few page reads. Then break it: "lower(email)" wraps the column in a function, and the plan goes back to Seq Scan. "Expression index" indexes lower(email) itself, and the index is used again. "Leading wildcard" (LIKE '%4242%') can't use a B-tree at all: a sorted list can't find text in the middle. Timings are on your machine and will vary.

 
 
 
 
 
 
 




Two requests, one row


A common shop bug: the code reads the stock, checks it is above 0, then writes stock - 1. Two buyers click at the same moment. Both requests read 1, both pass the check, both write 0. Two orders exist for one lamp. A transaction alone does not stop this. PostgreSQL's default isolation level is Read Committed, where each statement sees data committed before it started. Both reads saw 1 legally. Fixes: do the check and the write in one statement (UPDATE ... SET stock = stock - 1 WHERE stock > 0), lock the row when you read it (SELECT ... FOR UPDATE), or use a version check (chapter 7).

Click "2. Write 0 + order + COMMIT" in session 1, then in session 2. Both commit. "Check" shows two orders and stock 0: an oversell. Click "Reset" (session 1). Now the lock fix: "Read FOR UPDATE" in session 1, then in session 2. Session 2 shows "waiting…": the row is locked. Click "2. Write..." in session 1. Session 1 commits, session 2 wakes up and reads 0. Click "Give up: ROLLBACK" in session 2. Reset again. The atomic fix: "Atomic sell" in both sessions. The first returns stock 0 and an order. The second returns 0 rows: its UPDATE matched no row, so no order was made and the app knows it is sold out. No lock is held between statements.

 
 
 
 
 
 
 
 
 
 
 
 




Questions


EasySQL or NoSQL?


Start with a relational database (PostgreSQL, MySQL) unless you have a reason not to. You get transactions, constraints, joins and flexible queries, and it scales further than most products need. Pick a document store (MongoDB, DynamoDB) when data is read and written as whole documents by key, the access patterns are known in advance, and you need easy horizontal scale. Pick a key-value store (Redis) for caches, sessions and counters. Name the access pattern, not the trend.



EasyWhat is a transaction, and what does ACID mean?


A group of statements that succeed or fail as one. Atomic: all or nothing. Consistent: constraints hold before and after. Isolated: concurrent transactions don't see each other's half-done work (how much depends on the isolation level). Durable: once committed, it survives a crash (it is in the write-ahead log on disk). Example: move money between two accounts. Both updates commit, or neither does.



EasyWhat is an index, and what does it cost?


A sorted structure (usually a B-tree) on one or more columns that lets the database find rows without reading the whole table. Costs: disk space, and slower writes, since every insert, update and delete changes each index. Index the columns you filter, join and sort on, and check with EXPLAIN.



MediumWhat is the N+1 query problem and how do you fix it?


One query loads a list, then one more query per item loads a relation, often hidden inside an ORM property access. Fix with eager loading (includes in Rails, select_related / prefetch_related in Django, include in Prisma), a JOIN, or a batching loader (DataLoader in GraphQL). Find it by logging query counts per request, or with an APM tool that shows many identical queries in one trace.



MediumThe query has an index on the column, but EXPLAIN shows a sequential scan. Why?


  • The column is wrapped in a function or cast (lower(email), created_at::date): index the expression, or rewrite the condition (the lab).
  • LIKE '%text' with a leading wildcard: use a trigram (pg_trgm) or full-text index.
  • The condition matches a large part of the table, so reading it all is cheaper. The planner is right.
  • Statistics are old: run ANALYZE.
  • A composite index whose first column is not in the condition.
  • A type mismatch between the column and the parameter.



MediumIn which order should the columns of a composite index be?


An index on (a, b) is sorted by a, then by b inside each a. So it helps conditions on a, or on a and b, but not on b alone. Put columns compared with = first and the range or sort column last: for WHERE customer_id = ? ORDER BY created_at DESC, use (customer_id, created_at). Then the database reads one customer's rows already in order and stops after the LIMIT.



HardTwo requests buy the last item at the same time. Walk me through what happens and how you prevent it.


With read-then-write code, both read stock 1 under Read Committed, both pass the check, both write 0, and you sold two (the lab's first run). Options:
  • Atomic conditional update: UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock > 0, and check the row count. Simplest and fastest.
  • Pessimistic lock: SELECT ... FOR UPDATE, so the second request waits. Good when the logic between read and write is complex. Keep the transaction short.
  • Optimistic: a version column, retry on conflict. Good when conflicts are rare.
  • Serializable isolation: the database aborts one transaction with a serialization error, and the app retries.
Add a CHECK (stock >= 0) constraint as a last guard.



HardAfter a traffic spike, the API returns errors like "too many clients". What happened?


Each PostgreSQL connection is a server process with its own memory, and max_connections is limited (100 by default). Each app instance has a pool. 50 instances × a pool of 20 = 1,000 connections wanted. Autoscaling or serverless functions make it worse, because each new copy opens its own. Fixes: put a pooler such as PgBouncer (transaction mode) between the app and the database, size app pools from the database's limit down, keep transactions short, and never hold a connection while you call another service.



Real examples


    

  • N+1 in the Rails guide. Loading 10 books and then each book's author "executes 1 (to find 10 books) + 10 (one per each book to load the author) = 11 queries in total." The guide's fix is eager loading with includes. (guides.rubyonrails.org, Active Record Query Interface, section 16.1, checked 2026-10-07)
    • 

  • PostgreSQL's default isolation. "Read Committed is the default isolation level in PostgreSQL." A SELECT without FOR UPDATE "sees only data committed before the query began". That is why both buyers in the lab read 1. (postgresql.org/docs/current/transaction-iso.html)

11. Caching


Covers: cache layers, cache-aside, write-through, write-back, TTL, invalidation, delete vs update on write, versioned file names, stampede (thundering herd), locks and stale-while-revalidate, hot keys, the fill race · Sources: AWS ElastiCache docs (caching strategies), Redis docs (SET, EXPIRE), "Scaling Memcache at Facebook" (NSDI 2013), Facebook outage note (23 Sep 2010), RFC 9111 and RFC 5861. Deeper: the CDN explainer


A cache keeps a copy of data in a faster place, so most reads skip the slow source. Reads get fast and the database gets less load. The cost is that the copy can be wrong: every cache needs a rule for when the copy stops being trusted.


Caches sit at every layer: the browser's HTTP cache, a CDN, a reverse proxy, memory inside the app process, a shared cache such as Redis, and the database's own buffer. The closer to the user, the faster, and the harder to clear. The most common pattern in app code is cache-aside (AWS calls it lazy loading): the app checks the cache. On a miss, it reads the database and writes the result to the cache with a TTL. On a write, it updates the database and deletes the cache key.

Stampede


A popular key expires. In the next moment, every request for it misses at once, and every one of them runs the same expensive database query. The database gets hundreds of copies of one query exactly when the cache stopped protecting it. This is a cache stampede (or thundering herd). Fixes: let one request rebuild while others wait (a lock with SET NX EX), or serve the stale value while one request refreshes in the background (stale-while-revalidate), or refresh hot keys a little before they expire.

"Lock" sends one query; the others wait about 200 ms and read the new value. "Serve stale" sends one query, and no request waits, but they get the old value for 200 ms.

 

 

 





Questions


EasyWhat is cache-aside, and how is it different from write-through and write-back?


Cache-aside: the app reads the cache, fills it on a miss, and deletes the key on write. Only data that is read gets cached. Write-through: every write goes to the cache and the database together, so the cache is always fresh, but you cache data nobody reads. Write-back (write-behind): writes go to the cache and are saved to the database later. Fast writes, but data is lost if the cache dies before it flushes.



EasyWhere can you cache in a web app?


Browser (HTTP cache, controlled by Cache-Control), CDN (static files and public pages), reverse proxy, app memory (fastest, but each server has its own copy and it is lost on restart), a shared cache such as Redis (shared by all servers, one network hop), and the database buffer. Cache as close to the user as the data's privacy and freshness allow.



EasyHow do you cache JS and CSS files forever and still ship updates?


Put a hash of the content in the file name (app.3f9a1c.js) and serve it with Cache-Control: max-age=31536000, immutable. A new build makes a new name, so the HTML points to the new file. Serve the HTML itself with a short max-age or no-cache (store, but check with the server each time).



MediumHow do you keep the cache in step with the database?


Delete the key after the database write commits. Keep a TTL on every key as a backstop for missed deletes. For data many keys depend on, use versioned keys (product:1:v7) or tag-based purge. If several services write, publish change events (or read the database's change log) and delete keys from those. Accept, and state, how stale each kind of data may be: a price shown for 60 s may be fine, the price charged at checkout must come from the database.



MediumIn-process memory cache or Redis?


In-process: no network hop, nothing to run. But each server has its own copy, so after a write some servers serve old data until their TTL ends, and memory is lost on restart. Redis: one shared copy, one delete clears it for all servers, survives app restarts. Costs a round trip (well under a millisecond in the same data center, as a rough value) and one more service to run. Common answer: Redis as the main cache, plus a tiny in-process cache with a few seconds of TTL for the hottest keys.



HardWhat is a cache stampede, and how do you prevent it?


A hot key expires and many requests miss at once and all query the database (the lab). Prevent it with a rebuild lock (SET lock NX EX: one rebuilds, others wait briefly or serve stale), stale-while-revalidate, refreshing hot keys early, and random jitter on TTLs so many keys don't expire at the same second. Facebook's memcache uses "leases": the cache hands one client a token to rebuild a key, and returns a token "only once every 10 seconds per key".



HardCan cache-aside leave a stale value in the cache forever?


Yes, with this order. Reader A misses and reads the old value from the database. Writer B updates the database and deletes the key. Then A, which was slow, writes its old value into the cache. Now the cache holds the old value until the TTL ends, with no write coming to delete it. Fixes: always set a TTL. Only fill the cache if the key was not deleted since your read (a lease or version token, as Facebook does). Or delete the key a second time a moment after the write.



HardOne key gets 100,000 reads per second and its Redis node is overloaded. What do you do?


This is a hot key: sharding does not help, because one key lives on one node. Options: a short in-process cache in front of Redis, so each app server asks Redis about once per second. Copy the key to several keys (hot:1#0 to hot:1#9) and read a random one. Read from replicas. Or push the data to the CDN if it is public.

Because the fix involves making a query to a cluster of databases, that cluster was quickly overwhelmed by hundreds of thousands of queries a second." 12. Scaling, load balancing, rate limits


Covers: vertical vs horizontal scaling, load balancers, stateless servers, where sessions and files go, sticky sessions, read replicas and replication lag, background jobs and queues, rate limiting (fixed window, sliding window, token bucket), retries with backoff and jitter · Sources: The Twelve-Factor App (Processes), Redis docs (INCR rate limiter pattern, EXPIRE), Stripe blog "Scaling your API with rate limiters" (2017), RFC 6585 (429), AWS Builders' Library (backoff and jitter). Deeper: the microservices explainer (gateways, retries, queues, idempotency)


To serve more users, you either give one server more CPU and memory (vertical scaling) or run more copies of the server behind a load balancer (horizontal scaling). Horizontal scaling has no fixed ceiling and survives the loss of one server, but it only works if any copy can serve any request. So the servers must keep no state of their own.


A server that keeps sessions or uploaded files in its own memory or disk breaks this. The load balancer sends the next request to another copy, and that copy knows nothing about the user. The Twelve-Factor App puts it plainly: "Twelve-factor processes are stateless and share-nothing." Questions


EasyVertical or horizontal scaling?


Vertical: a bigger machine. No code changes, but there is a ceiling, it costs more per unit at the top end, and it is still one machine that can fail. Horizontal: more machines behind a load balancer. No ceiling and it tolerates failure, but the app must be stateless and you need shared state services. Usual path: stateless app servers that scale out, and a database you scale up first, then with replicas.



EasyWhat does a load balancer do?


It spreads requests over servers (round robin, least connections, or a hash of the client), runs health checks and stops routing to failed servers, and often ends TLS. A layer 4 balancer routes TCP connections by IP and port. A layer 7 balancer reads HTTP and can route by path, host or header, retry, and add headers.



EasyWhen do you move work to a background job?


When the user does not need the result to get their response: sending email, resizing images, generating reports, calling slow third-party APIs, webhooks. The request puts a job on a queue and returns. Workers process jobs and retry failures. Jobs can run twice (a worker crashes after the work but before it acknowledges), so make them idempotent. Send jobs that keep failing to a dead-letter queue. The microservices explainer has a lab on real Redis Streams.



MediumWhy are sticky sessions a weak fix?


They make the load balancer send a user back to the same server, so in-memory sessions seem to work. But the load is uneven, a server that dies or is replaced in a deploy logs out all its users, and scaling in has the same effect. The Twelve-Factor App: "Sticky sessions are a violation of twelve-factor and should never be used or relied upon." Put sessions in a shared store with a TTL (Redis) instead.



MediumHow do users upload large files when you have many servers?


Don't stream them through your app servers. The server checks the user and returns a presigned URL for object storage (S3, GCS), valid for a few minutes and for one object key. The browser uploads straight to storage. Storage sends an event (or the client confirms) and a worker processes the file: virus scan, thumbnails. App servers stay stateless and are not tied up by slow uploads.



MediumHow would you rate limit an API?


Pick the key (API key or user for logged-in traffic, IP for anonymous), the limit and the algorithm. A token bucket allows short bursts, which suits most APIs. Keep counters in Redis and update them in one atomic step (INCR, or a Lua script for a token bucket), so parallel requests can't both pass. Return 429 with Retry-After and rate limit headers. Decide what happens when Redis is down: fail open (allow) for normal endpoints, fail closed for login and other abuse targets.



HardThe database is the bottleneck. What do you do, in order?


  1. Measure: find the top queries by total time (pg_stat_statements). Fix indexes and N+1 queries. This is often enough.
  2. Cache hot reads (chapter 11).
  3. Add read replicas and send reads there. Replicas lag behind the primary, so a user may not see their own write. Read from the primary right after a user's write, or for that user for a few seconds.
  4. Add a connection pooler.
  5. Move slow work to queues, and old data to archive tables.
  6. Only then split the data: by feature into separate databases, or shard one table by a key such as tenant ID. Sharding makes cross-shard queries and transactions hard, so it comes last.



HardA service slows down, and the retries from its callers make the outage worse. Why, and what is the fix?


Each caller retries failed calls, so a struggling service gets 2× or 3× its normal load exactly when it can serve the least (a retry storm). If all clients retry on the same schedule, the waves arrive together. Fixes: exponential backoff with random jitter (AWS: "Jitter adds some amount of randomness to the backoff to spread the retries around in time"), a cap on retries, a retry budget (retries at most 10% of calls, as an example), a circuit breaker that stops calls for a while, and retries only at one layer, not at every layer of the stack.



HardThe rate limit is 100 per minute. A client sends 200 in 2 seconds and gets through. How?


With a fixed window, 100 requests at 0:59 and 100 at 1:00 fall in two windows, so all pass (the lab). Use a sliding window or a token bucket. Another cause: each of N app servers keeps its own counter in memory, so the real limit is N × 100. Shared atomic counters fix that.



Real examples


    

  • Stripe's rate limiters (2017). Stripe uses the token bucket: "a centralized bucket host where you take tokens on each request, and slowly drip more tokens into the bucket". It runs four limiters: a request rate limiter, a concurrent requests limiter, and two load shedders that drop less critical traffic when the fleet is busy: "If a box is too busy to handle its request volume, it will slowly start shedding less-critical requests." (stripe.com/blog/rate-limiters, read through a summary tool)

Questions


EasyWhat is the difference between polling, SSE and WebSockets?


Polling: the client asks every few seconds, simple but late and wasteful. Server-sent events: one long HTTP response the server writes events into, one way (server to client), with automatic reconnect. WebSocket: a full two-way channel after an HTTP upgrade, for when the client also sends often (chat typing, games, collaborative editing).



EasyHow does a WebSocket connection start?


As an HTTP request with Upgrade: websocket, Connection: Upgrade and a random Sec-WebSocket-Key. The server answers 101 Switching Protocols with Sec-WebSocket-Accept (a hash of the key), and the same TCP connection now carries WebSocket frames. Because it starts as HTTP, it uses ports 80 and 443 and passes most proxies. Cookies are sent on the upgrade, so check the Origin header, or a page on another site can open a socket with the user's session.



MediumWhich one would you pick for live notifications, and why?


Server-sent events if the data goes only from server to client: plain HTTP, works with HTTP/2 (many streams on one connection), reconnects by itself, and the Last-Event-ID header lets the server resend what was missed. WebSocket if the client also sends a lot. Polling is fine when a delay of tens of seconds is OK and clients are few, such as an admin dashboard. Whatever you pick, keep the data in a store the client can reload from, because the live channel will drop messages during reconnects.



MediumThe WebSocket drops after about a minute of silence. Why?


A proxy or load balancer closes connections that are idle for longer than its timeout (60 seconds is a common default, as a rough value). Send heartbeats (ping/pong frames, or an app message) more often than the shortest idle timeout on the path, and raise the timeout for the WebSocket route. On the client, reconnect with backoff and jitter, and resume from the last message ID you saw.



HardHow do you scale a chat to many servers with WebSockets?


Each server holds some of the connections. A message from a user on server A must reach channel members on servers B and C. Use pub/sub between servers: each server subscribes to the channels its connected users are in (Redis pub/sub, NATS, Kafka, or a dedicated channel service), and broadcasts each message to its local sockets. Store messages in a database first, with an ordered ID per channel, so clients can fetch what they missed. Balance by connection count, not request count, because connections live for hours. Plan for reconnect storms: after a deploy or a crash, every client reconnects at once, so add jitter to reconnects and drain servers slowly during deploys.



HardHow do you make sure a user sees every message, in order, after flaky mobile networks?


Don't trust the live channel for completeness. Give every message a server-assigned, increasing ID per conversation. The client keeps the last ID it has. On reconnect, it asks for everything after that ID (a cursor, chapter 3), then switches back to live events. Drop duplicates by ID, so a message that comes both from the fetch and the live stream shows once. Client-sent messages carry a client-generated ID, so a resend after a timeout does not post twice.

14. Deploy, migrate, observe


Covers: CI/CD, the test pyramid, rolling, blue-green and canary deploys, feature flags, schema changes without downtime (expand and contract), rollbacks with migrations, logs, metrics and traces, the four golden signals, debugging a slow production system, backups · Sources: martinfowler.com (BlueGreenDeployment, CanaryRelease, ParallelChange, Feature Toggles by Pete Hodgson), Google SRE book "Monitoring Distributed Systems", OpenTelemetry docs, SEC order 34-70694 (Knight Capital), Cloudflare blog (2 July 2019), CrowdStrike RCA (6 Aug 2024), Microsoft blog (20 July 2024), GitLab postmortem (2017)


Shipping code is a change to a running system, and most outages start with a change. So the goal of a deploy process is to make each change small, to expose it to a few users first, to see quickly if it hurts, and to undo it fast.


During any deploy that is not all at once, old and new versions run at the same time and share one database. So every change must work with both versions: the new code with the old schema, and the old code with the new schema. That rule drives how you change a schema.

Observability


To know if a deploy hurt, you need signals from production. Metrics are numbers over time (requests per second, error rate, p99 latency): cheap, good for alerts and dashboards. Logs are records of single events with detail: use structured (JSON) logs with a request ID. Traces follow one request through every service and database call, with the time of each step (a span). Google's SRE book names four golden signals to watch on any user-facing service: latency, traffic, errors and saturation (how full the service is).



Questions


EasyWhat are blue-green, rolling and canary deploys?


Blue-green: two full production environments. Deploy to the idle one, test it, then switch all traffic. Rollback is switching back. It costs double capacity. Rolling: replace servers a few at a time. No extra capacity, but old and new run together for a while. Canary: send a small share of traffic (one server, or 1% to 5% of users) to the new version, compare its errors and latency with the old version, then widen step by step or roll back.



EasyWhat is a feature flag?


A switch in config that turns a code path on or off at runtime, without a deploy. Uses: ship code dark and turn it on later, roll out to a percentage of users, turn off a broken feature in seconds, A/B tests. Costs: each flag doubles the paths to test, and old flags become dead code. Remove them once the rollout is done, and never reuse a flag name for a new meaning.



EasyWhat goes in a CI/CD pipeline?


On every push: install with the lockfile, lint, type-check, unit tests, build. On merge: integration tests against a real database (in a container), build an image tagged with the commit, deploy to staging, smoke tests, then deploy to production in stages with automatic rollback on bad metrics. Database migrations run as their own step before the code that needs them.



MediumHow do you change a database schema with no downtime?


Expand and contract (also called parallel change): add the new thing, deploy code that works with both, backfill, switch reads, then remove the old thing in a later deploy (the lab). Also watch locks: on a big table, some ALTER TABLE forms rewrite the whole table or hold an exclusive lock that blocks all reads and writes while it waits. Create indexes with CREATE INDEX CONCURRENTLY, add constraints as NOT VALID and validate later, backfill in small batches, and set a lock_timeout so a migration gives up instead of queueing every query behind it.



MediumWhat tests would you write for a full stack feature?


Many fast unit tests for pure logic (price rules, validation). Integration tests for the API against a real database, which catch wrong queries, constraints and transactions that mocks hide. A few end-to-end tests (Playwright) for the main user paths, such as signup and checkout. Component tests for complex UI states. If a front end and back end are deployed separately, contract tests check that the API still matches what the client expects. Test behaviour, not internals, so refactors don't break tests.



MediumWhat is the difference between logs, metrics and traces?


Metrics tell you that something is wrong (error rate went up at 14:02). Traces tell you where (the /checkout requests spend 2 s in the payment call). Logs tell you why (the payment provider returned "invalid currency" for one country). Link them with a shared trace ID in every log line. OpenTelemetry is the common standard to produce all three.



HardCheckout got slow after a deploy. Walk me through how you debug it.


  1. Limit the damage first: if the slowdown started with the deploy, roll back or turn off the flag. Debug after users are safe.
  2. Scope it with the golden signals: which endpoints, all users or one region, latency at p50 or only at p99, errors too?
  3. Open slow traces for /checkout and find the span that grew: a database query, an external call, or time in the app itself.
  4. Database: compare the query's plan before and after (EXPLAIN (ANALYZE, BUFFERS)). Look for a new query, a missing index, an N+1 loop.
  5. External call: timeouts, retries, rate limits from the provider.
  6. App: CPU (a blocked event loop, chapter 4), memory and GC, connection pool waits.
  7. Fix, add a test or an alert that would have caught it, and write a blameless postmortem.



HardHow do you roll back a deploy that included a migration?


Design so you don't need to undo the migration. Every migration is backward compatible with the code before it (expand only). Destructive steps (drop, rename) come in a later deploy, after the old code is gone for good. Then rolling back code is safe at any time, and the schema simply stays ahead. If a migration itself is broken, fix forward with a new migration. Test restores of backups regularly: a backup you have never restored is not a backup.

Questions


EasyHow do you start a system design question?


Don't draw yet. Ask what the main use cases are, how many users, the read and write mix, latency targets, and what may be stale. Say out loud what you will leave out. Then estimate, then define the API. The interviewer wants to see you shape a vague problem before you solve it.



MediumDesign a URL shortener. How do you make the short codes?


Option 1: a counter (database sequence, or ranges handed to each server) encoded in base62. Short and collision-free, but codes are guessable, which leaks how many links exist and lets people walk through them. Option 2: random 7-character base62 codes with a unique constraint, retry on collision. Not guessable, and collisions are rare while the table is a tiny part of 3.5 trillion. Option 3: a hash of the URL, cut short. The same URL gets the same code, but cutting causes collisions you must handle, and two users who shorten the same URL share stats. Pick option 2 unless codes must be as short as possible.



MediumDesign a news feed. Fan-out on write or on read?


Fan-out on write: when a user posts, add the post ID to each follower's feed list (in Redis or a table). Reading a feed is one fast lookup. But a user with 10 million followers makes 10 million writes per post. Fan-out on read: build the feed when it is opened, by querying the latest posts of everyone the user follows. Cheap writes, slow reads. Common answer: a hybrid. Fan out on write for normal users. For accounts with huge follower counts, merge their posts in at read time. Paginate the feed with a cursor.



HardDesign checkout for a flash sale: 1,000 items, 200,000 buyers at 10:00.


  • Before 10:00: static pages and assets on a CDN. Warm caches. Scale app servers ahead of time, because autoscaling reacts too late for a spike that starts in one second.
  • Admission: put buyers in a waiting room (a queue with a token) and let them in at the rate the back end can handle. Rate limit per user and per IP. Answer the rest with "sold out" from cache, not from the database.
  • Inventory: never read-then-write. Reserve with an atomic decrement (a Redis DECR that refuses below 0, or UPDATE ... WHERE stock > 0, chapter 10). A reservation expires after a few minutes if not paid.
  • Payment: call the provider with an idempotency key per order, so a retry or a double click does not charge twice. Mark the order paid from the provider's webhook, and handle the webhook idempotently too.
  • After: emails and receipts go through a queue. Watch the golden signals, and have a feature flag to close the sale.
Say which part must be exactly right (inventory, payment) and which may be stale (stock count shown on the page).
