1. What DNS is

Sources: Cloudflare Learning Center "What is DNS?", RFC 1034 / 1035

DNS (the Domain Name System) is a worldwide, distributed database that turns names people can read, like www.cloudflare.com, into the data computers need, most often an IP address like 104.16.124.96.

Labs titled "with real dig" run real DNS tools in Docker: dig, curl and an Unbound recursive resolver at 127.0.0.1 that resolves from the real root servers. They need the page opened through the lab server with scripts/serve.sh --docker, then http://127.0.0.1:8787/. All other labs work offline. Real answers change over time, so your IPs, TTLs and times will differ from the examples in the hints. The lab container has no IPv6 route, so presets that name a server add -4 (use IPv4 only).

Computers find each other by IP address. People remember names. DNS sits between the two. Every time you open a website, send an email or call an API, a DNS lookup happens first. Usually it takes a few milliseconds because the answer is already stored nearby. When it is not, the lookup walks a chain of servers across the world.

No single company runs DNS. The database is split into pieces called zones. Each zone is run by whoever owns it. ICANN coordinates the top. Verisign runs .com. You run yoursite.com. A lookup follows pointers from one owner to the next until it reaches the one who knows the answer.

You type www.acmeshop.com
↓ "what is the IP of www.acmeshop.com?"
DNS
↓ 203.0.113.10
Browser connects to 203.0.113.10
…and stores the answer for its TTL, so the next visit skips DNS

The browser has a name. It can't open a connection to a name. The network only moves packets between IP addresses.

So it asks DNS. At this level DNS is a black box that answers one kind of question: "for this name and this record type, what are the records?"

DNS answers with an IP address. Only now can the browser start TCP and TLS to the server.

Every answer carries a TTL (time to live) in seconds. Anyone along the way may keep the answer that long. This caching is why DNS is fast and why it can handle the whole internet's traffic.

DNS stores much more than IP addresses. It tells mail servers where to deliver email (MX), proves who owns a domain (TXT), says which certificate authorities may issue certificates (CAA), and much more. Chapter 10 covers the record types.

The rest of this guide opens the black box: how names are built (ch. 2), every component in a lookup (ch. 3), the full lookup step by step (ch. 4), and then each part in depth.

2. How domain names are built

Sources: RFC 1034 §3, Cloudflare "What is a DNS zone?", "What is a top-level domain?"

A domain name is a path through a tree, read from right to left. Each part between dots is a label. The tree's top is the root, written as an empty label, which is why a fully written name ends with a dot.

www.acmeshop.com. is read backwards: start at the root (the final dot), go to com, then to acmeshop, then to www. The trailing dot is usually hidden, but it is always there. A name written with it is a fully qualified domain name (FQDN).

The root. It has no name. Every lookup that has nothing cached starts here.

Top-level domains (TLDs) sit under the root. Generic ones (gTLDs) like .com, .org, .app; country-code ones (ccTLDs) like .uk, .pk, .jp; and the infrastructure TLD .arpa, used for reverse lookups.

Second-level domains: the part people register, like acmeshop.com. Some ccTLDs add a level first. In acmeshop.co.uk, the registrable part sits under co.uk.

Subdomains: anything the owner creates under their domain, as many levels deep as they like. www is just a subdomain by tradition. It has no special meaning to DNS.

Domains vs zones

A domain is a branch of the tree: a name and everything under it. A zone is the part of the tree that one set of servers is responsible for. They are often the same, but not always. The .com zone does not contain www.acmeshop.com. It only contains a pointer that says "for anything under acmeshop.com, ask these nameservers". That pointer is a delegation, made with NS records. Delegation is what lets millions of owners each run their own piece without a central database.

Lab: take a name apart

Type any hostname. See its labels, levels, and who is responsible at each step.

Rules for names

  • Each label is 1 to 63 characters. The whole name is at most 253 characters as text (255 bytes on the wire).
  • For hostnames, labels use letters, digits and hyphens, and can't start or end with a hyphen.
  • Names are case-insensitive. WWW.AcmeShop.COM and www.acmeshop.com are the same name. (Chapter 13 shows how resolvers use this for security.)
  • Non-English names like münchen.de are stored as Punycode: xn--mnchen-3ya.de. The browser converts for display.

3. Every component involved

A lookup passes through two groups. On your side: the browser, the operating system's stub resolver, and a recursive resolver. On the internet's side: root servers, TLD servers and the domain's authoritative servers. Behind the scenes, registries and registrars decide what the TLD servers say.

The browser keeps its own small cache of recent answers. Chrome shows it at chrome://net-internals/#dns.

On a miss, the browser asks the operating system. The OS part that does this is the stub resolver: a simple client that can't walk the tree itself. It checks the hosts file (/etc/hosts) and its own cache first. Linux often uses systemd-resolved, macOS mDNSResponder, and Windows the DNS Client service.

The stub sends the question to a recursive resolver (also called a recursor). You got its address from your router or network through DHCP, or you set it yourself. It does all the hard work and keeps a big shared cache, so one user's lookup speeds up the next user's.

The root servers know only one thing: which servers run each TLD. Every resolver ships with their addresses built in, in a file called root hints.

The TLD servers know which nameservers are responsible for each domain under their TLD. The .com servers hold pointers for every .com domain.

The authoritative nameservers hold the actual records for a domain. Their answer is final. It comes with the AA (authoritative answer) flag set. These are often run by a DNS provider such as Cloudflare, Route 53 or your registrar.

The people and organisations who decide what the servers say. IANA (part of ICANN) manages the root zone. A registry runs one TLD and its servers. A registrar is the shop where you rent a domain. It passes your chosen nameservers to the registry. The registrant is you.

Two more parts are common. Your home router often acts as a small DNS forwarder: your laptop asks the router, and the router passes the question to the ISP's resolver. Big networks also use forwarders and internal DNS servers that answer for private names like db.internal.

4. The full lookup, end to end

Sources: Cloudflare "The 8 steps in a DNS lookup", RFC 1034 §5.3.3

With nothing cached, the resolver walks the tree from the top. The root sends it to .com. .com sends it to the domain's nameservers. Those give the answer. Each "go ask them" reply is called a referral.

A few things this shows.

  • The resolver sends the full name to every server, even the root. The root only reads the last label, but sending the full name is how DNS was designed. (Modern resolvers can send less, see QNAME minimisation in chapter 13.)
  • The root and TLD servers don't search for you. They answer with an AUTHORITY section (NS records: "these servers are responsible") and an ADDITIONAL section with those servers' IPs, called glue (chapter 5).
  • The .com delegation has a TTL of 172,800 seconds (2 days). So in practice the resolver almost never asks the root. It already knows the .com servers.
  • Only the last answer has the AA flag. That tells the resolver it came from the source, not from someone's cache.

5. Recursive vs iterative queries, referrals and glue

Sources: Cloudflare "What is recursive DNS?", "What is DNS?" (3 types of queries), RFC 1034 §4.2.1

There are two ways to ask a DNS server. A recursive query says "find the final answer for me". An iterative query says "give me the best answer you have, even if that is just a pointer". Your device asks recursively. The resolver asks iteratively.

Stub resolver
↓ recursive query (RD=1): "don't come back without the answer"
Recursive resolver
→ iterative: "who knows?"
Root
← referral to .com
→ iterative
.com TLD
← referral to ns1.acmeshop.com
→ iterative
Authoritative
← answer (AA=1)
↑ one final answer back to the stub

The stub sets the RD (recursion desired) flag. It hands off all the work. This makes stub resolvers tiny and simple.

The resolver asks the root. The root doesn't do recursion for anyone, so it answers with a referral.

The resolver follows the referral itself and asks .com. Another referral.

It follows that and gets the final answer.

The resolver returns one clean answer with the RA (recursion available) flag set. The third kind of query Cloudflare lists is non-recursive: a query the server can answer at once, from its own zone or its cache, with no referral needed.

Why split it this way? Root and TLD servers get enormous traffic. If they chased answers for everyone, they would need to hold state for billions of lookups and would be easy to overload. By only handing out referrals they stay stateless and fast. The work and the caching are pushed to resolvers, which are close to users and share a cache among many of them.

Glue records: the chicken-and-egg problem

Say .com tells you "acmeshop.com's nameserver is ns1.acmeshop.com". To contact it you need its IP. To get its IP you must ask… the nameserver for acmeshop.com. That is the one you are trying to reach. The loop is broken by glue: the parent zone (.com) also stores the nameserver's IP, and returns it in the ADDITIONAL section of the referral.

Lab: why glue exists

Glue is only needed when the nameserver's name is inside the zone it serves ("in-bailiwick"). If your nameservers are ns1.dnsprovider.net, the resolver just looks that name up separately. That costs an extra lookup, but no loop. You set glue at your registrar, usually on a page called "child nameservers" or "host records".

6. Caching, TTL and "propagation"

Sources: Cloudflare "What is DNS?" (DNS caching), RFC 2308 (negative caching)

Every answer carries a TTL, a number of seconds. Any cache that stores the answer counts it down and throws the answer away at zero. The zone owner sets the TTL. So the owner decides the trade-off between speed and how fast changes spread.

Where answers are cached

Browser cacheseconds to a minute or so
OS cachesystemd-resolved, mDNSResponder, Windows DNS Client
Home router cachemany routers keep a small cache
Recursive resolver cacheshared by thousands or millions of users
Cached referrals too.com servers (2 days), acmeshop.com NS (hours)

Browsers keep a short cache to skip even the OS call. Chrome shows it and has a "Clear host cache" button at chrome://net-internals/#dns.

The OS caches for all apps on the machine. Flush it with ipconfig /flushdns on Windows, resolvectl flush-caches on Linux with systemd-resolved, or sudo killall -HUP mDNSResponder on macOS.

Your router may cache too. Restarting it clears that.

The resolver's cache is the one that matters most. A popular name is almost always already there because someone else asked for it recently.

The resolver also caches the referrals, not just final answers. That is why most lookups skip the root and TLD entirely and go straight to the domain's nameservers.

Negative caching: "this name does not exist" (NXDOMAIN) is cached too. The zone's SOA record says for how long (the last SOA field, chapter 9). If you look up a name before you create it, resolvers may keep saying "no such name" for that time.

"DNS propagation" is really cache expiry

Nothing is pushed out when you change a record. The new value is on your authoritative servers at once. Resolvers around the world still hold the old value until their cached copy's TTL runs out. Each one cached it at a different moment, so they switch at different moments. That spread-out switch is what people call propagation.

Planning a move? Lower the TTL (say to 300) at least one old-TTL period before the change. Then make the change: everyone switches within 5 minutes. Raise the TTL again afterwards. Some resolvers ignore very low TTLs and use a minimum of their own, so don't count on seconds.

7. Root servers

Sources: Cloudflare "DNS root server", root-servers.org (checked 2026-09-30), IANA root zone management

Root servers answer for the root zone, the top of the tree. The root zone is small: it lists every TLD (about 1,500) and the nameservers for each. There are 13 root server identities, named a.root-servers.net to m.root-servers.net, but far more physical machines.

According to root-servers.org, as of 30 September 2026 the root server system has 2,045 operational instances run by 12 independent operators. (Cloudflare's page says "over 600", which is older.) Verisign runs two letters, A and J. Each letter is one IP address shared by many machines through anycast.

Why only 13?

Original DNS over UDP limited a message to 512 bytes. A resolver starting up asks a root server "who are the root servers?" (a priming query). The whole reply, with names and addresses, had to fit in 512 bytes. Thirteen was the most that fit. The limit is on addresses, not machines, and anycast removed the machine limit.

Anycast: one address, many places

Normally one IP address means one machine. With anycast, many sites announce the same IP address to the internet's routing system (BGP). Routers send each packet to the "nearest" site in network terms. If a site fails, it stops announcing, and traffic flows to the next nearest one within moments. This gives low latency and spreads attacks across hundreds of sites.

How resolvers find the root, and who controls it

No one can refer you to the root, because it is the top. So every resolver ships with the root servers' addresses in a root hints file (named.root), published by IANA. On start-up it primes from one of them and gets the current list.

The content of the root zone is managed by IANA (part of ICANN). Changes, such as a TLD changing its nameservers, are checked by IANA and then published by Verisign as the Root Zone Maintainer. All 13 letters serve the same zone file. The root zone is also signed with DNSSEC. The key that signs it (the root KSK) is managed in public "key signing ceremonies" (chapter 13).

The root is rarely the bottleneck. Because resolvers cache TLD referrals for 2 days, only a small share of lookups ever reach it. Much of the traffic roots do see is junk: queries for TLDs that don't exist, like .local or .lan, leaking from misconfigured networks.

9. Authoritative servers and zone files

Sources: Cloudflare "What is a DNS SOA record?", "Primary vs secondary DNS", "What is a DNS zone?", RFC 1035 §5, RFC 1995/1996

An authoritative nameserver holds a zone's records and answers for them with final authority. The records live in a zone file, a plain text format from 1987 that is still the standard way to write DNS data.

$ORIGIN acmeshop.com.
$TTL 3600
@     IN SOA  ns1.acmeshop.com. hostmaster.acmeshop.com. (
              2026093001 ; SERIAL   version of the zone
              7200       ; REFRESH  secondaries check every 2 h
              3600       ; RETRY    if the check fails, retry after 1 h
              1209600    ; EXPIRE   stop answering after 14 days without contact
              300 )      ; MINIMUM  how long to cache "no such name"
@     IN NS   ns1.acmeshop.com.
@     IN NS   ns2.acmeshop.com.
ns1   IN A    198.51.100.53
ns2   IN A    203.0.113.53
@     IN A    203.0.113.10
www   IN CNAME acmeshop.com.
@     IN MX   10 mail1.acmeshop.com.

Read each line as name · TTL · class · type · data. @ means the zone's own name (the "apex"). Names without a trailing dot get the origin added, so ns1 means ns1.acmeshop.com.. A classic mistake is writing mail.acmeshop.com without the final dot, which becomes mail.acmeshop.com.acmeshop.com.. The class is almost always IN (internet).

Primary and secondary servers

A zone should have at least two nameservers on different networks, so one outage doesn't take the domain offline. Classic setups have one primary where edits happen, and secondaries that keep copies.

Primary (ns1)you edit here, serial → 2026093002
↓ NOTIFY (UDP): "zone changed"
Secondary (ns2)
↑ SOA query: "what is your serial?"
↓ IXFR / AXFR over TCP: the changes, or the whole zone
Both answer the same data. Resolvers pick either.

An edit on the primary must increase the serial. A common format is the date plus a counter: YYYYMMDDnn.

The primary sends a NOTIFY message to its secondaries (RFC 1996) so they don't wait for the refresh timer.

The secondary asks for the SOA and compares serials. Higher serial means there is new data.

It pulls a zone transfer over TCP: IXFR sends only the changes, AXFR sends the whole zone. Transfers should be allowed only to your own secondaries. An open AXFR gives anyone a full list of your hostnames.

If NOTIFY is lost, the REFRESH timer still makes the secondary check. If the primary is gone for longer than EXPIRE, the secondary stops answering rather than serve data that may be very old. Large providers today often skip this model and replicate with their own internal systems to anycast servers worldwide.

Each record has a name, a type, a TTL and data. The type says what the data means. A lookup always asks for one name and one type: "A records for www.acmeshop.com".

CNAME rules

A CNAME says "this name is an alias. Go look up that other name instead." The resolver then restarts the lookup for the target, which can mean more round trips. Two rules follow from how it works:

  • A name with a CNAME can have no other records. If www is a CNAME, it can't also have an MX or TXT, because the CNAME means "everything about this name is over there".
  • So the apex (acmeshop.com itself) can't be a CNAME, because the apex must have SOA and NS records. Providers get around this with CNAME flattening (Cloudflare) or ALIAS / ANAME records: the authoritative server follows the CNAME itself and returns plain A/AAAA records.

11. The DNS message on the wire


Sources: RFC 1035 §4, RFC 6891 (EDNS0), RFC 7766 (DNS over TCP), DNS Flag Day 2020


A DNS query is one small binary message, usually sent in a single UDP packet to port 53. The reply uses the same format with more sections filled in. There is no connection and no handshake, which is why DNS is fast.


Every message has five parts: a 12-byte header, then the question, answer, authority and additional sections. The header holds a 16-bit ID that ties the reply to the query, flags, and a count for each section.




FlagMeaning


QR0 = query, 1 = response


AAauthoritative answer: from the zone's own server, not a cache


TCtruncated: the answer didn't fit, retry over TCP


RDrecursion desired: "please find it for me"


RArecursion available: "I am a resolver that does that"

These are the exact bytes a stub would send. You could paste them into a UDP socket to port 53 and get an answer.

 

 

 




Name compression


A reply repeats names a lot (acmeshop.com appears in the question and in every record). To save space, a name can end with a 2-byte pointer (first two bits set, 0xC0) to an earlier position in the message. C0 0C means "the name at byte 12", which is the question name right after the header.


Size limits, EDNS and TCP


    

  • Plain DNS over UDP is limited to 512 bytes. This is also why there are 13 root names (chapter 7).
    • 

  • EDNS(0) adds a fake "OPT" record to the additional section. It lets the client say "I can take bigger replies" and carries the DO flag for DNSSEC. Since DNS Flag Day 2020, the common advice is 1,232 bytes, small enough to avoid IP fragmentation.
    • 

  • If the answer still doesn't fit, the server sets TC. The client then repeats the query over TCP port 53. TCP is also used for zone transfers. Every DNS server must support it (RFC 7766).
    •

The reply flags add qr (a response) and ra (recursion available). The query has an EDNS line with udp: 1232, the size dig can take. 12. Reverse DNS


Sources: Cloudflare "What is reverse DNS?", "DNS PTR record"


Reverse DNS goes the other way: from an IP address to a name. It uses PTR records stored under the special domain in-addr.arpa (IPv4) or ip6.arpa (IPv6).


DNS names get more specific from right to left. IP addresses get more specific from left to right. So to fit an IP into the tree, the address is written backwards: 203.0.113.10 becomes 10.113.0.203.in-addr.arpa. Now the network part (203.0.113) sits higher in the tree. That lets an IP block be delegated just like a domain: the owner of 203.0.113.0/24 gets 113.0.203.in-addr.arpa.



 
Lab: IP to PTR name

 

 




Who controls the PTR? The owner of the IP block, not the owner of the domain. For a cloud server, you set it in your cloud provider's console. Main uses:


    

  • Email: many mail servers reject or down-rank mail from an IP without a PTR, or whose PTR name does not point back to the same IP ("forward-confirmed reverse DNS").
    • 

  • Logs and tools: traceroute and server logs show readable names instead of raw IPs.
    • 



A PTR proves nothing by itself. Anyone who controls an IP block can set any name. That is why mail servers check that the name's A record points back.



 
Lab: reverse DNS with real dig

 
dig -x writes the IP backwards and asks for the PTR record. Click 1: the lab resolver has a PTR for 192.0.2.10. Look at the name in the answer: 10.2.0.192.in-addr.arpa. Click 2 for two real PTRs: 1.1.1.1 and 8.8.8.8. The first lookup can take a few seconds. Click 3 to see who serves the reverse zone for 1.1.1.1. The ;; Received lines go from a root server to in-addr-servers.arpa, then to a server for APNIC's zone (APNIC is the registry for that IP block), then to Cloudflare, which holds the block. The IP owner sets the PTR, not a domain owner. Click 4 for the check a mail server does: PTR first, then the A record of that name. If the A record holds the same IP, the name is forward-confirmed. Click 5 for an IPv6 PTR, under ip6.arpa, one label per hex digit. To break it, click 6: an IP with no PTR gives NXDOMAIN. Names and times will differ.

 
 
 
 
 
 










13. Security and privacy


Sources: Cloudflare "DNS cache poisoning", "How does DNSSEC work?", "DNS over TLS vs. DNS over HTTPS", "DNS security", "What is recursive DNS?"


DNS was built in the 1980s on trust. Queries go in plain text over UDP, and a resolver accepts any reply that looks right. That leaves three problems: answers can be forged (poisoning), nobody could check they're genuine (fixed by DNSSEC), and anyone on the path can read your lookups (fixed by DoT and DoH).



Cache poisoning


UDP has no handshake. When a resolver sends a query, it accepts the first reply with the right source IP and port, the right 16-bit ID, and the same question. An attacker who sends a forged reply that matches, and arrives before the real one, gets their fake IP stored in the cache. Every user of that resolver is then sent to the attacker until the TTL ends.


In 2008 Dan Kaminsky showed how to make this practical. Instead of racing for www.bank.com (which is cached, so you get one try per TTL), ask for random names like x8a1.bank.com. Each one is a fresh race. The forged replies include a fake NS record for all of bank.com. Losing costs nothing. Just try the next random name.



 
Lab: how hard is it to win the race?

 
The attacker can send some forged replies in the short window before the real answer arrives. Turn on each defence and see the odds change.

 

 

 

 





DNSSEC: signed answers and a chain of trust


DNSSEC adds digital signatures to DNS data. It does not encrypt anything. It proves the answer came from the zone's owner and was not changed. The resolver checks each zone's key using its parent, all the way up to the root. The root's key is built into the resolver as the trust anchor.



 

  
Root zoneDNSKEY (root KSK) = trust anchor in every validating resolver

  
↓ root signs: DS for com = hash of com's KSK

  
.com zoneDNSKEY (com's KSK + ZSK)

  
↓ .com signs: DS for acmeshop.com

  
acmeshop.com zoneDNSKEY: KSK signs the ZSK

  
↓ ZSK signs each record set → RRSIG

  
www A 203.0.113.10 + RRSIG

 

 

  
The resolver trusts one key without proof: the root's key-signing key. It is managed in public key ceremonies, run by ICANN with trusted community representatives present.

  
The root zone publishes a DS (delegation signer) record for .com: a hash of .com's key. It is signed by the root. Now .com's key can be trusted.

  
Same step one level down. .com publishes a signed DS for acmeshop.com. You give this DS to your registrar, which sends it to the registry.

  
Each zone uses two keys. The KSK (key-signing key) signs only the zone's DNSKEY set. The ZSK (zone-signing key) signs everything else and makes an RRSIG for each record set. Splitting them lets you change the ZSK often without touching the parent's DS. For "no such name" answers, NSEC/NSEC3 records prove, with a signature, that nothing exists there.

 

 





 
Lab: validate the chain

 

 




If validation fails, a validating resolver returns SERVFAIL, not the bad data. A broken DNSSEC setup therefore takes a domain offline for everyone using validating resolvers (like 1.1.1.1 and 8.8.8.8). A common cause is changing DNS provider without removing the old DS first.

Click 1: with +dnssec (the DO bit), the A records come with an RRSIG, the signature. Click 2: the DS records, the hash of a zone's key published in its parent. example.com DS is served by .com, and com DS by the root. Click 3: ask 1.1.1.1. The reply flags have ad (authentic data), because 1.1.1.1 checked the chain up to the root. To break it, click 4: dnssec-failed.org is a test domain with a broken DNSSEC setup on purpose. 1.1.1.1 returns SERVFAIL, and an EDE line gives the reason (DNSKEY Missing: no key matches the DS). Click 5: the same query with +cd (checking disabled). 1.1.1.1 now returns the A record, without ad. Click 6: the lab resolver does not validate, so it returns the A record with no error. A non-validating resolver gives no protection: it would also return a forged answer.

 
 
 
 
 
 




Privacy: DoT and DoH


Classic DNS is plain text. Your ISP, Wi-Fi owner or anyone on the path can see every name you look up, even if the website itself uses HTTPS. Two standards encrypt the path between your device and the resolver:




DNS over TLS (DoT)DNS over HTTPS (DoH)

DoT and DoH protect the trip to the resolver. They don't stop the resolver from seeing your queries, and they don't prove the answer is genuine. DNSSEC does that part. Two other privacy features: QNAME minimisation (RFC 9156) makes the resolver send the root only com and .com only acmeshop.com, not the full name. Oblivious DoH adds a relay so the resolver sees queries but not who sent them.

Encryption protects the path to the resolver. It does not fix a broken zone. Answers and TTLs will differ.

 
 
 
 




Other attacks on DNS


    

  • Amplification DDoS: an attacker sends small queries to open resolvers with the victim's IP as a fake source. The large replies (a 60-byte query can bring back several KB) flood the victim. That's why resolvers should only answer their own users, and why servers use rate limits.
    • 

  • Domain hijacking: someone takes over your registrar account and changes your nameservers. Use 2FA and a registry lock.
    • 

  • DNS tunnelling: smuggling data out of a network inside DNS queries, because DNS is rarely blocked.
    • 

  • Dangling records: a CNAME pointing to a cloud resource you deleted. Someone else creates that resource and now serves content on your subdomain ("subdomain takeover").
    • 










14. DNS in practice: browsers, CDNs, load balancing, and dig


Sources: Cloudflare "What is round-robin DNS?", "What is Anycast DNS?", "What is 1.1.1.1?", RFC 8305 (Happy Eyeballs v2), RFC 9460 (HTTPS records)


In real systems, DNS does more than map names to fixed IPs. It picks servers based on where the user is, spreads load, and tells browsers how to connect before they open a single connection.



What the browser does around the lookup



 

  
You type acmeshop.com + Enteror even while you type: DNS prefetch

  
↓ in parallel

  
A query
AAAA query
HTTPS query

  
↓

  
Happy Eyeballs: try IPv6, fall back to IPv4 fast

  
↓

  
TCP/QUIC + TLS → HTTP request

 

 

  
Browsers start DNS early. They resolve names from the address bar as you type, and from links on a page. Sites can ask for it with <link rel="dns-prefetch" href="//cdn.example.com">.

  
The browser asks for the IPv4 (A) and IPv6 (AAAA) records at the same time, not one after the other.

  
Modern browsers also ask for the HTTPS record (RFC 9460). It can say "this site supports HTTP/3", give IP hints, and carry keys for Encrypted Client Hello. The browser learns how to connect without a trial round trip.

  
Happy Eyeballs (RFC 8305): prefer IPv6, but if it doesn't connect within a short time (around 250 ms), race IPv4 too, and use whichever connects first. This way a broken IPv6 path never leaves the user waiting.

  
Only now does the real connection start. On a cold cache, the DNS time is added to the page's first byte.

 

 





DNS for load balancing and CDNs


    

  • Round-robin DNS: return several A records (api has two IPs in the chapter 10 zone). Clients spread across them. It's simple, but DNS doesn't know if a server is down, and caches keep old lists.
    • 

  • GeoDNS / latency-based DNS: the authoritative server looks at where the query comes from and returns a nearby server's IP. The query comes from the resolver, not the user. So resolvers may pass a hint of the user's subnet, called EDNS Client Subnet. 1.1.1.1 does not send it, for privacy.
    • 

  • Health-checked DNS (e.g. Route 53 failover): stop returning an IP when its health check fails. Clients switch only after the TTL runs out, so use short TTLs.
    • 

  • Anycast (the method Cloudflare uses): return the same IP everywhere and let internet routing pick the nearest data center. DNS stays simple and failover is fast.
    •

The whole flow, one last time



 

  
Browser cache

  
OS: hosts file → OS cache → stub resolver

  
Router (forwarder)

  
Recursive resolver: cache

  
Root (anycast) → referral to .com

  
.com TLD → referral + glue

  
Authoritative → answer (AA), signed if DNSSEC

  
Resolver validates, caches every piece for its TTL

  
Answer back to OS and browser → both cache it → connect

 

 

  
The browser checks its own cache.

  
The OS checks the hosts file and its cache, then the stub sends a recursive query.

  
A home router often forwards it.

  
The resolver answers from cache if it can. Most of the time it can.

  
If not, it asks a root server, reached by anycast, which refers it to the TLD.

  
The TLD server refers it to the domain's nameservers, with glue if needed.

  
The authoritative server returns the records, with signatures if DNSSEC is on.

  
The resolver checks the signatures if it validates, and caches the answer and every referral.

  
The answer returns down the chain. Every layer caches it for its TTL. The browser can now open a connection. On a cold path this took four network round trips. On a warm path it took zero or one.
