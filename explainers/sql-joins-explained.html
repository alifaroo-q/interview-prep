1. Tables, rows and keys

Covers: table as a set of rows, why rows need identity, candidate key, primary key, UNIQUE, superkey vs key, composite key, natural vs surrogate key, UNIQUE and NULL. Sources: PostgreSQL 18 docs "Constraints" (§5.5.3 Unique Constraints, §5.5.4 Primary Keys), "Sorting Rows" (§7.5), "Identity Columns" (§5.3). Checked 2026-10-01.

A table holds rows that all have the same columns. A key is a column, or a group of columns, whose value is different in every row. With a key you can point at exactly one row. Every relation between tables, and so every join, is built on keys.

The example shop

All chapters use one small online shop, acmeshop.com. It has four customers and five orders. Order 105 is a guest checkout, so it has no customer. That NULL is on purpose. It shows up again in many chapters.

A table has no built-in row order. PostgreSQL returns rows in an order that depends on the plan and on the disk layout, unless you write ORDER BY (docs §7.5). So you can never say "the third row". You can only find a row by its values. That is why keys exist.

Start with rows. SQL allows two identical rows in a table with no key. Then you cannot update or delete one of them by its values alone.

A column is a key only if no two rows can ever share a value. name fails because two customers are called Ana. city fails too.

A candidate key is a smallest set of columns that is unique and never NULL. Here there are two: id and email.

The primary key is the candidate key you choose as the address of the row. PostgreSQL makes its columns NOT NULL and creates a unique B-tree index on them (§5.5.4). A table has at most one primary key.

The other candidate keys get a UNIQUE constraint. The database then rejects a second customer with the same email, even though email is not the primary key.

Key, superkey, and "unique today"

Any set of columns that is unique is a superkey. (id, name) is unique, because id alone is unique. It is not a key, because it is not minimal. You can remove name and it stays unique.

A key is a rule about all rows that can ever exist, not a fact about the rows you see today. In the sample data, (name, city) happens to be unique. Nothing in the real world stops a second Ana from Lyon signing up tomorrow. If you make it a key, her sign-up fails. Choose keys from the meaning of the data, then let the database enforce them.

Natural keys and surrogate keys

A natural key is a value from the real world, such as an email or an ISBN. A surrogate key is a value the database makes up, such as id bigint GENERATED ALWAYS AS IDENTITY, which takes numbers from a sequence (§5.3).

Surrogate key (id)Natural key (email)
Can it change?No. Nothing in the business changes it.Yes. A customer changes email, and every row that points to the old value must change too.
Size in other tables8 bytes for a bigint.The length of the text, copied into every row and index that points to it.
Stops duplicates?No. Two sign-ups with the same email get two ids. You still need UNIQUE (email).Yes, by definition.

The common design is a surrogate primary key plus UNIQUE on the natural key. A composite key has more than one column. Junction tables often use one, for example PRIMARY KEY (order_id, product_id) in chapter 3.

UNIQUE and NULL

A primary key column can never be NULL. A UNIQUE column can. The docs say that by default "two null values are not considered equal" (§5.5.3). So a UNIQUE (email) column accepts many rows with a NULL email. Since PostgreSQL 15 you can write UNIQUE NULLS NOT DISTINCT (email) to allow only one NULL. The same rule, "NULL is not equal to NULL", decides how joins treat NULL (chapter 11).

2. Foreign keys: how tables point to each other

Covers: foreign key, referencing and referenced table, what the database checks on insert, update and delete, ON DELETE actions (NO ACTION, RESTRICT, CASCADE, SET NULL, SET DEFAULT), NULL in a foreign key, MATCH FULL, the index a foreign key does not create. Sources: PostgreSQL 18 docs "Constraints" (§5.5.5 Foreign Keys); PostgreSQL source src/backend/utils/adt/ri_triggers.c for the check queries. Checked 2026-10-01.

A foreign key is a column in one table that holds the key of a row in another table. orders.customer_id holds a customer's id. That stored value is the relation. The foreign key constraint makes the database check that the value points to a row that exists.

The link is a value, not a pointer

There is no hidden pointer from an order to a customer. There is only the number 1 in the customer_id column. To go from order 101 to its customer, the database must search customers for a row with id = 1. A join is that search, done for many rows at once. This is why a relational database can join any two columns that hold the same kind of value, with or without a declared foreign key.

orders is the referencing table. It holds the foreign key column.

customers is the referenced table. The value 1 in an order means "the customer whose id is 1".

The constraint turns the convention into a rule. An insert with customer_id = 9 fails if no customer 9 exists. Deleting a customer who still has orders fails, or cascades, as you choose.

The docs: "A foreign key must reference columns that either are a primary key or form a unique constraint, or are columns from a non-partial unique index." If the target were not unique, one order could point at two customers.

The target side always has an index, because it is a key. The referencing side does not. The docs say the declaration "does not automatically create an index on the referencing columns". The next section shows why that matters.

What the database checks, and when

PostgreSQL enforces a foreign key with internal triggers (ri_triggers.c). Each trigger runs a small query.

  • Insert or update an order. It runs SELECT 1 FROM ONLY customers x WHERE id = $1 FOR KEY SHARE OF x. No row means the statement fails. FOR KEY SHARE locks the customer row, so no other transaction can delete it before this one commits. This lookup uses the primary key index, so it is always fast.
  • Delete a customer, or change its id. It runs SELECT 1 FROM ONLY orders x WHERE $1 = customer_id FOR KEY SHARE OF x, once per deleted row. Without an index on orders.customer_id, this is a full scan of orders for each customer you delete.
ON DELETE actionWhat happens to the orders of a deleted customer
NO ACTION (default)The delete fails if orders still point to the customer. The check can be deferred to commit with DEFERRABLE, so later commands in the transaction can fix it first.
RESTRICTThe delete fails. The docs: it "does not allow the check to be deferred".
CASCADEThe orders are deleted too. Their own foreign keys then apply, so a cascade can travel down many tables.
SET NULLThe orders stay, with customer_id set to NULL. It fails if the column is NOT NULL.
SET DEFAULTThe orders get the column default. It fails if no customer has that default value.

NULL skips the check. The docs: "a referencing row need not satisfy the foreign key constraint if any of its referencing columns are null". That is how guest order 105 exists. If an order must have a customer, declare customer_id bigint NOT NULL REFERENCES customers. For a multicolumn key, MATCH FULL rejects a row where some key columns are NULL and others are not.

Lab: the foreign key at work

3. Relationship shapes: one-to-one, one-to-many, many-to-many

Covers: cardinality, optional vs required side, where the foreign key lives for 1:1, 1:N and M:N, junction tables and their composite key, attributes of a relationship, self-referencing relations, crow's foot notation, wrong placements and the problems they cause. Sources: PostgreSQL 18 docs "Constraints" (§5.5.5, incl. the order_items many-to-many example and the self-referential tree example). Crow's foot notation is a common modelling convention, not part of SQL. Checked 2026-10-01.

A relationship says how many rows of one table can link to one row of another. There are three shapes. One-to-one: at most one partner on each side. One-to-many: one parent, many children. Many-to-many: many on both sides. The shape decides where the foreign key goes, and the shape of every join result.

One rule places every foreign key

A column holds one value per row. So a foreign key column can point to at most one row. Put it on the side that has one partner.

  • One-to-many: each order has one customer. So customer_id goes in orders, the "many" side. The "one" side stores nothing.
  • One-to-one: a foreign key that is also UNIQUE (or the primary key). The uniqueness stops a second child row for the same parent.
  • Many-to-many: neither side has one partner, so neither side can hold the key. You add a third table, the junction table, with one row per link.

An order holds many products. A product is in many orders. This is many-to-many.

A product_id column in orders holds one value, so an order could have one product only. A list of ids in one column breaks first normal form. You cannot put a foreign key or an index on each element.

The junction table order_items turns one many-to-many relation into two one-to-many relations. Each row is one link: this product is in this order.

A composite primary key on the two foreign keys stops the same pair twice. The PostgreSQL docs use this exact table as their many-to-many example.

The junction row is also the place for facts about the link. qty and the price paid belong to "this product in this order", not to the order or to the product alone.

Required or optional

Each end of a relationship also has a minimum: zero or one. In customers → orders, a customer can have zero orders (Dara). Can an order have zero customers? Only if customer_id allows NULL. In acmeshop it does, for guest checkout. NOT NULL on the foreign key makes the parent required. The database cannot enforce "a customer has at least one order" with a plain constraint. That minimum lives in application code or in a deferred trigger.

These minimums decide which join you need. If the child side can be empty, an INNER JOIN drops the parent (Dara disappears). If the foreign key can be NULL, an INNER JOIN drops the child (order 105 disappears). Chapters 5 to 7 show both.

4. What a join does: the pair model


Covers: join as every pair (cross product) filtered by ON, TRUE / FALSE / UNKNOWN, outer joins adding back unmatched rows, why a left row can appear many times, row count bounds, why Venn diagrams mislead, logical model vs real execution. Sources: PostgreSQL 18 docs "Table Expressions" (§7.2.1.1 Joined Tables). Checked 2026-10-01.


A join combines two tables into one result. Each result row is a pair: one row from the left table next to one row from the right table. The join condition in ON decides which pairs to keep. Outer joins then add back rows that found no partner, with NULL on the missing side.



Four steps that define every join


This is the logical meaning, the rule for which rows come out. It is not how the database runs it. Chapter 14 shows the real algorithms, which give the same rows with much less work.



 

  
customers4 rows
orders5 rows

  
↓

  
every pair4 × 5 = 20 pairs (CROSS JOIN)

  
↓ test ON for each pair

  
keep pairs where ON is TRUEINNER JOIN: 4 pairs

  
↓

  
add unmatched rows with NULLsLEFT: + Dara · RIGHT: + order 105 · FULL: + both

 

 

  
Two inputs. A join always works on two row sets. A join of three tables is two joins: the first result becomes the left input of the second.

  
Build every pair. The docs: for a CROSS JOIN, "If the tables have N and M rows respectively, the joined table will have N * M rows."

  
Test the ON condition on each pair. Keep the pair only if the result is TRUE. FALSE and UNKNOWN (from NULL) both drop it. This is the INNER JOIN. The docs: "the joined table has a row for each row in T2 that satisfies the join condition with R1."

  
Outer joins run the inner join first, then add each row that matched nothing, with NULL in the other table's columns. So a LEFT JOIN "always has at least one row for each row in T1" (docs).

Why a row appears more than once


The result is a list of pairs, not a list of customers. Ana has two orders, so she is in two kept pairs, and she appears twice. This is correct, and it is the source of the most common join bug: you join, then add up a column, and the sum counts some rows twice (chapter 12). Before you write a join, ask for each table: "for one row of the other side, how many rows can match here?" The answer is the shape from chapter 3.

If the join follows a foreign key to a key (each order to its one customer), the "many" side cannot multiply. orders JOIN customers returns at most one row per order. That is the safe direction. Joining from the "one" side to the "many" side multiplies the "one" side.



Why the Venn diagram misleads


Joins are often drawn as two overlapping circles. The picture is right about one thing: which unmatched rows an outer join keeps. It is wrong about three others.


    

  • A Venn diagram shows sets of the same kind of thing. customers and orders are different things. The middle is not "rows in both tables". It is pairs.
    • 

  • The middle can hold more rows than either circle. One left row can be in many pairs.
    • 

  • A CROSS JOIN has no Venn picture at all. A non-equality condition, such as ON o.total > c.limit, has none either.
    • 



The lab draws the circles with real counts. The middle number is the count of pairs. The pair grid is the full picture. The Venn is a summary of it.








5. INNER JOIN


Covers: INNER JOIN syntax and meaning, JOIN = INNER JOIN, rows that disappear (parents with no children, children with a NULL or orphan key), result row count per left row, the comma syntax, joining on more than one column, table aliases. Sources: PostgreSQL 18 docs "Table Expressions" (§7.2.1.1), "SELECT" (FROM Clause). Checked 2026-10-01.


An INNER JOIN returns only the pairs where the ON condition is TRUE. A row with no partner does not appear at all. JOIN alone means INNER JOIN. The docs: "INNER is the default".


SELECT c.name, o.id AS order_id, o.total
FROM customers AS c
JOIN orders    AS o ON o.customer_id = c.id;


c and o are table aliases. They are short names for the tables in this query. You need them when two tables have a column with the same name, like id, and you always need them in a self join (chapter 9).



Who disappears



 

  
4 kept pairsAna·101, Ana·102, Ben·103, Chen·104

  
Darano order points to her

  
order 105customer_id is NULL: NULL = 1 is UNKNOWN

  
rows per customer = number of matching ordersAna 2 · Ben 1 · Chen 1 · Dara 0

 

 

  
The kept pairs. Each result row has all columns of one customer followed by all columns of one order.

  
A parent with no children is dropped. "List customers and their orders" with INNER JOIN silently leaves out every customer who never ordered. If the report must show them, you need a LEFT JOIN (chapter 6).

  
A child with a NULL foreign key is dropped too. The test NULL = 1 is not FALSE, it is UNKNOWN, and a join keeps only TRUE. An orphan key, like customer_id = 9 in a table with no foreign key, is dropped the same way.

  
Each left row appears once per matching right row. The total is the sum of those counts: 2 + 1 + 1 + 0 = 4.

Other ways to write it


-- the same inner join, written three ways
FROM customers c JOIN orders o ON o.customer_id = c.id
FROM customers c INNER JOIN orders o ON o.customer_id = c.id
FROM customers c, orders o WHERE o.customer_id = c.id     -- comma = CROSS JOIN, then WHERE filters


The comma form gives the same rows for an inner join. It has one real risk. If you forget the WHERE line, you get the full cross product and no error (chapter 8). The JOIN ... ON form keeps each condition next to its table, and a missing ON is a syntax error. Use it.


A join condition can test more than one column. A composite key needs all its columns: ON oi.order_id = s.order_id AND oi.product_id = s.product_id. If you test only one of them, each row pairs with every row that shares that one column, and the result multiplies.


For an inner join, the order of the tables does not change the result, only the column order. customers JOIN orders and orders JOIN customers return the same pairs. The planner is free to pick the order it runs them in (chapter 14).








6. LEFT JOIN and RIGHT JOIN


Covers: LEFT OUTER JOIN, RIGHT OUTER JOIN, NULL padding, RIGHT as a mirrored LEFT, ON vs WHERE in outer joins, a WHERE test that turns a LEFT JOIN into an inner join, an INNER JOIN after a LEFT JOIN, parenthesised joins. Sources: PostgreSQL 18 docs "Table Expressions" (§7.2.1.1, §7.2.2); PostgreSQL source src/backend/optimizer/prep/prepjointree.c (reduce_outer_joins). Checked 2026-10-01.


A LEFT JOIN returns every pair an inner join returns, plus each left row that matched nothing, once, with NULL in every right-side column. The left table is never reduced. A RIGHT JOIN is the same with the sides swapped.


SELECT c.name, o.id AS order_id, o.total
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id;     -- Dara is kept: (Dara, NULL, NULL)


The docs: "First, an inner join is performed. Then, for each row in T1 that does not satisfy the join condition with any row in T2, a joined row is added with null values in columns of T2." LEFT OUTER JOIN is the same thing. The word OUTER is optional.


a RIGHT JOIN b returns the same rows as b LEFT JOIN a, with the columns in a different order. Most teams write only LEFT JOIN, so the table that is kept whole is always the first one you read.



ON and WHERE are not the same in an outer join


For an inner join, a test in ON and the same test in WHERE give the same rows. For an outer join they do not. The docs: "a restriction placed in the ON clause is processed before the join, while a restriction placed in the WHERE clause is processed after the join."



 

  
customers LEFT JOIN ordersON o.customer_id = c.id AND o.total > 100

  
result: Ana·101, Ben·103, Chen·NULL, Dara·NULLevery customer kept, only big orders attached

  
customers LEFT JOIN orders ON o.customer_id = c.idWHERE o.total > 100

  
result: Ana·101, Ben·103Chen and Dara are gone

 

 

  
The test is in ON. It decides which orders count as a match. A customer whose orders all fail it has no match.

  
So Chen (only order 80) and Dara (no orders) are padded with NULL and kept. This answers "every customer, with their big orders if any".

  
The same test in WHERE runs after the join, on the finished rows.

  
Dara's padded row has o.total = NULL. NULL > 100 is UNKNOWN, and WHERE drops it. Chen's row (80) fails too. The LEFT JOIN added rows and WHERE took them away again. The query now acts as an inner join. PostgreSQL notices this and plans it as one (reduce_outer_joins).

 

 




Rule of thumb: a test on the kept table (c.city = 'Lyon') goes in WHERE. A test on the optional table goes in ON, unless you mean to drop the rows. The one WHERE test on the optional side that keeps its meaning is IS NULL on a NOT NULL column: WHERE o.id IS NULL finds the rows that had no match (the anti-join, chapter 10).

An inner join after a left join


Joins run from left to right. Each join takes the result so far as its left input. So a later INNER JOIN can remove rows that an earlier LEFT JOIN kept:


SELECT c.name, o.id, oi.product
FROM customers c
LEFT JOIN orders o       ON o.customer_id = c.id
JOIN order_items oi      ON oi.order_id = o.id;     -- Dara: o.id is NULL, NULL = x is UNKNOWN, row dropped


Make the second join LEFT as well, or put the inner join in parentheses so it runs first: LEFT JOIN (orders o JOIN order_items oi ON oi.order_id = o.id) ON o.customer_id = c.id. The two fixes mean different things. The lab shows the difference.

7. FULL OUTER JOIN


Covers: FULL OUTER JOIN meaning, reconciling two lists, COALESCE on the key, classifying rows by which side is NULL, the equality-only limit in PostgreSQL, when a FULL JOIN is a smell. Sources: PostgreSQL 18 docs "Table Expressions" (§7.2.1.1), "Conditional Expressions" (COALESCE); PostgreSQL source src/backend/optimizer/path/joinpath.c for the FULL JOIN error text. Checked 2026-10-01.


A FULL OUTER JOIN returns every matched pair, plus every unmatched row from both sides, padded with NULL. No row from either table is lost. Its main use is to compare two lists and find what is missing on each side.


The example: acmeshop gets a daily file of card payments from its payment provider. It loads the file into a table payments with no foreign key, because the file can contain anything. Now it needs three lists: paid orders, unpaid orders, and payments for orders it does not know.


SELECT COALESCE(o.id, p.order_id) AS order_ref,
       o.total, p.amount,
       CASE WHEN o.id IS NULL  THEN 'payment for unknown order'
            WHEN p.id IS NULL  THEN 'not paid'
            WHEN p.amount <> o.total THEN 'amount differs'
            ELSE 'ok' END AS status
FROM orders o
FULL JOIN payments p ON p.order_id = o.id;



 

  
matched pairsorder and payment agree on the key

  
+ orders with no paymentp.* is NULL → not paid

  
+ payments with no ordero.* is NULL → unknown order

  
COALESCE(o.id, p.order_id)one key column that is never NULL

 

 

  
First the inner join, the pairs where p.order_id = o.id. Inside this set, compare the amounts. A short payment shows up here as "amount differs".

  
Then each order that matched nothing, once, with NULL payment columns. A LEFT JOIN would stop here.

  
Then each payment that matched nothing, with NULL order columns. This is what only a FULL JOIN gives in one pass.

  
The key is NULL on one side in every padded row. COALESCE returns its first argument that is not NULL, so it gives one key column for all rows. USING (col) does the same for you if both columns have the same name.

Limits and warnings


    

  • In PostgreSQL a FULL JOIN condition must be an equality that can run as a hash join or a merge join. Anything else fails with "FULL JOIN is only supported with merge-joinable or hash-joinable join conditions". The reason is in chapter 14: Nested Loop cannot produce the unmatched inner rows.
    • 

  • Every test in WHERE on either side removes padded rows, for the same reason as in chapter 6. Put filters in subqueries before the join, or test with IS NULL.
    • 

  • If you use FULL JOIN to glue two tables that have a foreign key, one side can never be unmatched. The FULL JOIN then does the work of a LEFT JOIN at a higher cost, and it limits the planner, because a FULL JOIN fixes the join order. Use it when both sides can really have rows the other does not.
    • 









8. CROSS JOIN


Covers: CROSS JOIN as the full cross product, N × M growth, real uses (variant grids, calendar × category report skeletons, one-row parameter tables), the accidental cross join (comma without WHERE, missing join column), equivalences with ON TRUE and the comma. Sources: PostgreSQL 18 docs "Table Expressions" (§7.2.1.1), "Set Returning Functions" (generate_series). Checked 2026-10-01.


A CROSS JOIN returns every pair of rows, with no condition. For N left rows and M right rows it returns N × M rows. The docs: FROM T1 CROSS JOIN T2 "is equivalent to FROM T1 INNER JOIN T2 ON TRUE" and to FROM T1, T2.



When you want it


    

  • All combinations. Sizes × colours gives every product variant to create.
    • 

  • A report skeleton. Every day of the month × every category, then a LEFT JOIN to the sales. Days with no sales then show 0 instead of missing. generate_series('2026-09-01'::date, '2026-09-30', '1 day') makes the days.
    • 

  • A one-row table of settings. CROSS JOIN (SELECT 0.2 AS vat_rate) s puts one value next to every row. With one row on one side, the result has the same rows as the other side.
    • 



SELECT d::date AS day, cat.name, COALESCE(sum(o.total), 0) AS sales
FROM generate_series('2026-09-01'::date, '2026-09-30', '1 day') AS d
CROSS JOIN categories cat
LEFT JOIN orders o ON o.created_at::date = d::date AND o.category_id = cat.id
GROUP BY 1, 2
ORDER BY 1, 2;

When you do not want it


The cross product grows as the product of the table sizes. An accidental one is the most expensive mistake a single line of SQL can make.



 

  
FROM customers c, orders ocomma = CROSS JOIN

  
WHERE o.customer_id = c.idturns it into an inner join

  
forget the WHERE line4 × 5 = 20 rows, no error

  
at scale100,000 × 1,000,000 = 10¹¹ rows

 

 

  
The comma in FROM makes a cross product. The join exists only because of a line in WHERE.

  
With the WHERE line, you get the inner join from chapter 5.

  
Without it, every customer is paired with every order. The query runs. The numbers look plausible on a small test database.

  
On production size (example counts), the query runs for hours or fills the disk with temporary files. A related bug: a join on only part of a composite key, or on a low-variety column such as status, gives a partial cross product.

A self join is a table joined to itself. It is not a special join type. It is any join where both inputs are the same table under two different aliases. You use it when a row relates to another row of the same table, or when you compare rows of one table in pairs.



A table that points to itself


The docs call this a self-referential foreign key: "if you want rows of a table to represent nodes of a tree structure". In acmeshop, each employee has a manager, and the manager is also an employee.


CREATE TABLE employees (
  id         bigint PRIMARY KEY,
  name       text NOT NULL,
  dept       text NOT NULL,
  manager_id bigint REFERENCES employees (id)   -- NULL for the top of the tree
);

The root. Maya has no manager, so manager_id is NULL. The foreign key allows it, because NULL skips the check.

The other use is comparing rows with each other. "Which employees work in the same department?" Join the table to itself on dept. Each employee then pairs with every employee of the department, including themself, and each pair comes twice, as (Omar, Sam) and (Sam, Omar).

Each extra level is one more alias. The grand-manager is LEFT JOIN employees g ON g.id = m.manager_id. That works when the depth is fixed and small. 10. Semi-join and anti-join: EXISTS, IN, NOT EXISTS, NOT IN


Covers: semi-join (EXISTS, IN), anti-join (NOT EXISTS, LEFT JOIN ... IS NULL, NOT IN), why JOIN + DISTINCT is not a semi-join, the NOT IN and NULL trap, which column to test for IS NULL, EXCEPT. Sources: PostgreSQL 18 docs "Subquery Expressions" (§9.24.1 EXISTS, §9.24.2 IN, §9.24.3 NOT IN), "Table Expressions" (§7.2.1.1); PostgreSQL source src/backend/commands/explain.c for Semi and Anti join node names. Checked 2026-10-01.


A semi-join returns each left row that has at least one match, once, with no columns from the right side. An anti-join returns each left row that has no match. SQL has no SEMI JOIN keyword. You write them with EXISTS, IN and NOT EXISTS, and the planner runs them as join nodes named Semi Join and Anti Join.



"Customers who ordered" is not a join


A join returns pairs, so Ana appears twice. You want Ana once. A semi-join answers the question "is there a match?" and stops at the first one. The docs: the subquery "will generally only be executed long enough to determine whether at least one row is returned".


SELECT c.* FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);


SELECT DISTINCT c.* FROM customers c JOIN orders o ... gives the same rows but does more work. It makes every pair, then sorts or hashes them to remove the copies. And if you select fewer columns, say only c.name, DISTINCT also merges two different customers who share a name. The select list inside EXISTS does not matter. The docs note the convention EXISTS(SELECT 1 WHERE ...).



The anti-join and the NOT IN trap



 

  
c.id NOT IN (SELECT customer_id FROM orders)list = 1, 1, 2, 3, NULL

  
4 NOT IN (1, 2, 3, NULL)= 4<>1 AND 4<>2 AND 4<>3 AND 4<>NULL

NOT EXISTS (... WHERE o.customer_id = c.id)NULL row never matches, so it cannot block

 

 

  
"Customers with no orders." The subquery returns every customer_id, and guest order 105 adds a NULL.

  
x NOT IN (list) means "x is different from every element". SQL writes that as <> tests joined with AND.

  
One test compares with NULL and gives UNKNOWN. An AND with an UNKNOWN can never be TRUE. So NOT IN returns no rows at all, with no error. The docs: the result "will be null, not true" when "at least one right-hand row yields null".

  
NOT EXISTS asks "is there a row where the condition is TRUE?". The NULL row gives UNKNOWN, which is not TRUE, so it is simply not a match. Dara is returned. Use NOT EXISTS.

If you test a nullable column instead, such as o.coupon_code IS NULL, you also get customers whose real orders have no coupon. Test the primary key, or the join column.

11. NULL and joins


Covers: three-valued logic (TRUE, FALSE, UNKNOWN), why NULL never matches in ON, joining on nullable columns, IS NOT DISTINCT FROM, NULLs added by outer joins vs NULLs stored in the table, COUNT(*) vs COUNT(column) after a LEFT JOIN, COALESCE, aggregates over padded rows. Sources: PostgreSQL 18 docs "Comparison Functions and Operators" (§9.2), "Aggregate Functions" (§9.21), "Table Expressions" (§7.2.1.1). Checked 2026-10-01.


NULL means "no value" or "unknown value". Any comparison with NULL, even NULL = NULL, gives UNKNOWN, not TRUE. A join keeps a pair only when ON is TRUE, so a NULL join column never matches anything.



Three values, not two


SQL logic has TRUE, FALSE and UNKNOWN. ON, WHERE and HAVING keep a row only on TRUE. That makes UNKNOWN act like FALSE for filtering, but not inside NOT: NOT UNKNOWN is still UNKNOWN. That is the reason NOT IN fails in chapter 10.


When you really want two NULLs to match, for example a composite key where a region column can be NULL, use IS NOT DISTINCT FROM. It treats NULL as a normal value that equals NULL (docs §9.2). Be careful. It can stop the planner from using a plain equality index, and a join on it can pair every NULL row on the left with every NULL row on the right.



 
Lab: compare with NULL

 
Pick an operator. Each cell is a op b. A join keeps the pair only in the TRUE cells.

 

 

 





Two kinds of NULL in a result


After a LEFT JOIN, a NULL in o.total can mean two things. The order exists and its total is NULL. Or there was no order, and the join padded the row. SQL shows both the same way. To tell them apart, test a column that is never NULL in the table, usually the primary key: o.id IS NULL means "no match".



Counting after a LEFT JOIN


Aggregates see padded rows as normal rows. The docs (§9.21) give the rules: count(*) counts rows, count(expr) counts rows where expr is not NULL, and sum of no non-NULL values is NULL, not 0.


SELECT c.name, count(*), count(o.id), sum(o.total), COALESCE(sum(o.total), 0)
FROM customers c LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.name;

12. Row multiplication: joining two children at once


Covers: fan-out along one-to-many joins, the product of two independent children, wrong sums and counts with no error, why sum(DISTINCT) and count(DISTINCT) are not fixes, aggregating each child before the join, checking the grain of a query. Sources: PostgreSQL 18 docs "Table Expressions" (§7.2.1.1), "Aggregate Functions" (§9.21), "Subquery Expressions" (§9.24). Checked 2026-10-01.


Row multiplication, also called fan-out, is what happens when you join a parent to two child tables in one query. Each row of one child pairs with each row of the other child of the same parent. Sums and counts over the result are then too big, and SQL gives no warning.



How it happens



 

  
order 1011 row

  
JOIN order_items →
3 item rows101 repeats 3 times

  
JOIN payments →
2 payment rowseach item row pairs with both

  
3 × 2 = 6 rowseach item counted 2 times, each payment 3 times

  
aggregate each child first, then join1 row per order

 

 

  
The grain of a query is "what one result row stands for". Here it starts as one row per order.

  
Join to order_items. The grain is now one row per item. That is correct, and order columns repeat once per item.

  
Join to payments through the same order. Items and payments have nothing to do with each other. The join still pairs every item row with every payment row of that order.

  
sum(item price) counts each item once per payment. sum(amount) counts each payment once per item. Both are wrong, and the more rows the children have, the more wrong they are.

  
The fix: reduce each child to one row per order in a subquery, then join those. Now every join is to at most one row, and nothing multiplies.

 

 






 
Lab: watch the sums go wrong

 
Move the sliders for order 101. The grid shows every row the naive join makes. Try 2 items at 25 each, then try the sum(DISTINCT ...) version.

 

 

 

 





SELECT o.id, i.items_total, p.paid
FROM orders o
LEFT JOIN (SELECT order_id, sum(qty * price) AS items_total FROM order_items GROUP BY order_id) i ON i.order_id = o.id
LEFT JOIN (SELECT order_id, sum(amount) AS paid FROM payments GROUP BY order_id) p ON p.order_id = o.id;


sum(DISTINCT x) is not a fix. It removes equal values, not duplicate rows. Two items that each cost 25 are two real rows with the same value, and DISTINCT counts only one of them. count(DISTINCT oi.product_id) is correct only if the column is unique per child row. Before you aggregate over a join, name the grain. If more than one table is on the "many" side of the same parent, aggregate them first.








13. More ways to join: USING, NATURAL, range joins, LATERAL


Covers: ON vs USING vs NATURAL, output columns of USING, how NATURAL breaks after a schema change, non-equality (range) joins, overlapping and missing ranges, half-open intervals, LATERAL subqueries for top-N per row, CROSS JOIN LATERAL vs LEFT JOIN LATERAL ... ON true. Sources: PostgreSQL 18 docs "Table Expressions" (§7.2.1.1 Joined Tables, §7.2.1.5 LATERAL Subqueries), "Range Types" (§8.17). Checked 2026-10-01.


ON is the general form: any boolean test. USING and NATURAL are short forms for equality on columns with the same name. A range join uses a test other than equality. A LATERAL subquery can read columns of the tables before it, so it runs once per left row.



USING and NATURAL


JOIN orders USING (customer_id) means ON customers.customer_id = orders.customer_id, and the result has one customer_id column instead of two. The docs: USING "produces one output column for each of the listed column pairs". NATURAL JOIN is USING on every column name the two tables share. The docs call it "considerably more risky since any schema changes to either relation that cause a new matching column name to be present will cause the join to combine that new column as well."



 
Lab: NATURAL JOIN after a migration

 
These tables use customer_id as the column name on both sides, so NATURAL works today. Now run the migration that adds an updated_at column to both tables. No query changed.

 

 




Use ON in application code. Use USING only when the names were designed to match and you want the merged column.



Range joins


A join condition does not have to be equality. Shipping fees come from weight bands. Each parcel matches the band its weight falls into:


SELECT p.id, p.kg, r.fee
FROM parcels p
JOIN shipping_rates r ON p.kg >= r.min_kg AND p.kg < r.max_kg;


Two things go wrong with ranges. If bands overlap, a parcel matches two bands and appears twice. If bands have a gap, a parcel matches none and an INNER JOIN drops it. BETWEEN min AND max includes both ends, so a parcel of exactly 5 kg matches the band that ends at 5 and the band that starts at 5. Use half-open bands: >= min AND < max. PostgreSQL range types, such as numrange with '[1,5)', make half-open bands the default, and an exclusion constraint can forbid overlaps in the table itself (docs §8.17).


A range join cannot run as a hash join or a merge join, because those need equality. It runs as a nested loop (chapter 14). On big tables that needs an index that can answer the range test, such as a B-tree on min_kg or a GiST index on a range column.



 
Lab: overlapping and missing bands

 
Lines link each parcel to every band it matches. Switch to BETWEEN and watch the 5 kg parcel. Open a gap and watch a parcel lose its line.

 

 
 

 

 

 





LATERAL: a subquery per row


A normal subquery in FROM runs once and cannot see the other tables. The docs: with LATERAL a subquery can "reference columns provided by preceding FROM items", so it is evaluated for each row of the tables before it. This answers "top N per group" directly:


SELECT c.name, t.id, t.total
FROM customers c
LEFT JOIN LATERAL (
  SELECT o.id, o.total FROM orders o
  WHERE o.customer_id = c.id          -- uses c, which a plain subquery cannot
  ORDER BY o.total DESC
  LIMIT 2
) t ON true;


CROSS JOIN LATERAL drops customers for whom the subquery returns no rows, like an inner join. LEFT JOIN LATERAL ... ON true keeps them with NULLs. With an index on orders (customer_id, total DESC), each run of the subquery reads only its N rows.

14. How the database runs a join: Nested Loop, Hash Join, Merge Join


Covers: logical join vs physical algorithm, Nested Loop (plain and with an inner index), Hash Join (build and probe), Merge Join (sorted inputs, mark and restore), which algorithm supports which join type and condition, how the planner chooses, the underestimate failure. Sources: PostgreSQL 18 docs "Planner/Optimizer" (§51.5), "Using EXPLAIN" (§14.1), "Resource Consumption" (§19.4.1, work_mem, hash_mem_multiplier), "Planner Method Configuration" (§19.7.1); source comments in nodeHashjoin.c, nodeMergejoin.c, joinpath.c (REL_18_STABLE). Checked 2026-10-01 (algorithm lab adapted from the SQL and PostgreSQL explainer, checked 2026-09-30).


The join type (INNER, LEFT, ...) says which rows you get. The join algorithm says how the database finds them. PostgreSQL has three: Nested Loop, Hash Join and Merge Join. None of them builds the full cross product from chapter 4. Each avoids it in a different way, and each needs something different: an index, memory, or sorted input.



 

  
logical joinpairs where ON is TRUE

  
Nested Loopfor each outer row, search the inner side

  
Hash Joinhash the smaller side, probe with the other

  
Merge Joinwalk two sorted inputs in step

  
plannerestimates rows, costs each option, picks the cheapest

 

 

  
The meaning is fixed. Any algorithm the planner picks must return exactly these rows.

  
Nested Loop. For each row of the outer input, run the inner input and keep the matches. With an index on the inner join column, each outer row costs one index lookup. It is the only algorithm that handles any condition, including ranges and <>.

  
Hash Join. Read the inner input once and put it in a hash table in memory. Then read the outer input once, and look up each row in the table. It needs an equality condition. The memory limit is work_mem × hash_mem_multiplier (defaults 4MB × 2.0). A bigger build side spills to disk in batches.

  
Merge Join. Sort both inputs on the join key (or read them from an index in key order). Then move forward through both at the same time, like merging two sorted lists. It needs an equality whose operator has a B-tree sort order.

  
The planner builds each possible plan, estimates its cost from table statistics, and keeps the cheapest. EXPLAIN shows its choice.

Lab: where each algorithm wins

 
A simplified model, not the planner's real formulas. One unit is one row read, comparison or hash operation. An index lookup costs log2(inner rows) comparisons plus 4 units for random page reads (4 is the ratio of the default random_page_cost 4.0 to seq_page_cost 1.0). A sort costs n × log2(n). A wrong row estimate is the classic failure. If the planner thinks the outer side has 1 row, a Nested Loop with an inner index looks cheapest. If the outer side really has 100,000 rows, the inner side runs 100,000 times. EXPLAIN ANALYZE shows it as a large gap between estimated rows and actual rows, and a high loops count on the inner node. The cause is almost always a bad estimate lower in the plan, such as stale statistics after a bulk load. ANALYZE on the table is the first thing to try.








15. Using joins efficiently


Covers: index the foreign key column, when an index helps a join and when it does not, keep the join column bare (no function or cast), matching data types, filter early, select only needed columns, EXISTS instead of JOIN + DISTINCT, aggregate before joining, join order and the planner, LIMIT with nested loops, reading EXPLAIN for joins. Sources: PostgreSQL 18 docs "Constraints" (§5.5.5), "Indexes on Expressions" (§11.7), "Multicolumn Indexes" (§11.3), "Using EXPLAIN" (§14.1), "Controlling the Planner with Explicit JOIN Clauses" (§14.3), "Statistics Used by the Planner" (§14.2). Checked 2026-10-01.


A join is fast when the database can find the matching rows without reading everything. That depends on three things: an index the join can use, a condition the planner can use it with, and good estimates of how many rows each step returns. Most slow joins break one of these.



A checklist, in the order problems usually appear


    

  1. Index the foreign key column. PostgreSQL indexes the referenced key, not the referencing column (chapter 2). "Orders of customer 42" needs orders(customer_id). A composite primary key already covers its leading column: order_items(order_id, product_id) serves joins on order_id, not on product_id (§11.3).
    2. 

  2. Keep the join column bare. ON o.customer_id::text = c.code or ON lower(a.email) = lower(b.email) cannot use a plain index on the column. Fix the data type, or create an index on the same expression (§11.7).
    3. 

  3. Use the same data type on both sides. A bigint key joined to a text column forces a cast on every row. Declare the foreign key column with the exact type of the key.
    4. 

  4. Filter early, and on the table that has the filter. A selective filter, such as one customer's email, lets the planner start from a few rows and use a Nested Loop. The planner pushes WHERE tests down to the scan of their table for you. You help it by writing tests it can use, such as created_at >= '2026-09-01' instead of date_trunc('month', created_at) = ....
    5. 

  5. Ask the right question. Use EXISTS for "has a match" (chapter 10). Aggregate children before joining them (chapter 12). Every join that is not needed is work: a LEFT JOIN to a table whose columns you do not select can be removed by the planner only if it can prove the join returns at most one row, through a unique key.
    6. 

  6. Select only the columns you need. A hash join stores the build side in memory. Fewer and narrower columns mean a smaller table and fewer batches on disk.
    7. 

  7. Keep statistics fresh. The planner picks the algorithm and the order from row estimates (§14.2). After a bulk load, run ANALYZE.
    8. 




When an index helps a join, and when it does not


An index helps when the join touches a small part of the table. "Orders of one customer" reads about 10 of 1,000,000 orders (example numbers). A report over all customers reads every order anyway. Then a Hash Join over two sequential scans is cheaper than 100,000 index lookups, and the planner ignores the index. That is correct, not a bug.

Join order


For inner joins, the order you write the tables does not decide the order they run. The docs: explicit inner JOIN syntax "is semantically the same as listing the input relations in FROM, so it does not constrain the join order" (§14.3). The planner searches the orders itself, exhaustively up to join_collapse_limit items (default 8). Outer joins limit the reordering, because moving them changes the result. So you do not need to "put the small table first". You do need to give the planner correct estimates and usable indexes.
