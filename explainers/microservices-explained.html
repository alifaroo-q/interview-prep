1. The big picture

Covers: intro, mental model

A microservice system is a group of separate programs that work together over a network. Each program runs on its own, keeps its own data, and can be changed and shipped without touching the others.

It is not one app cut into many folders. Folders share one memory, one database connection and one crash. Separate programs share none of that. They can only talk by sending bytes across a network, and the network can be slow, lose messages, or fail. That one fact is the reason almost every tool in this guide exists.

Most people find the single parts easy. A load balancer, a cache, a queue: each makes sense alone. The hard part is knowing where each part sits, who owns which data, and what happens to one request as it moves through all of them. Click Next to build the system one part at a time.

Some labs run real tools: an nginx gateway with Toxiproxy, Kafka, Redis and PostgreSQL. Their titles end in "on real nginx", "on real Kafka" and so on. They run in Docker and need the lab server: run scripts/serve.sh --docker, then open http://127.0.0.1:8787/. All other labs work offline.

Everything starts with a client somewhere on the internet: a browser tab, a phone app, or a partner's server.

The CDN is a network of servers spread around the world. The request first lands on the one nearest the user. It can answer from a stored copy (images, scripts) and block attacks before they reach you.

The load balancer is the front door to your own servers. You run many copies of each server. It picks a healthy copy for each request.

The API gateway reads the URL and decides which service should handle it. It also checks the login token and rate limits, so each service does not repeat that work.

The services are the real application. Each one handles one business area: users, orders, products. Each is a separate program you can deploy alone.

Each service owns its own database. No other service reads or writes it directly. This is the rule that keeps services independent (chapter 3).

A cache such as Redis keeps hot data in memory so the service does not ask the database every time.

When something happens (an order is placed), the service drops an event into the message broker and moves on. It does not wait for anyone to react.

Other services read events from the broker at their own pace. Email sends a receipt. Analytics counts sales. If one is down, the order still succeeds, and the event waits.

What changes when a call crosses the network

Think about how long things take. These are rough, common numbers:

ActionTypical timeCompared to a function call
Function call in the same program~1–100 nanoseconds1×

Speed is only half of it. A function call has two results: it returns, or it throws. A network call has a third: you do not know. The request may never have arrived. Or it arrived, the work was done, and only the reply got lost. The caller sees the same timeout in both cases. Chapters 8 and 9 are all about living with that third result.

2. From monolith to services

Covers: §1 the monolith you know · §2 what a microservice is

A monolith is one program that holds every feature and talks to one database. A microservice setup splits those features into separate programs that call each other over the network.

The monolith you already know

In an e-commerce monolith, users, products, orders, payments and notifications all live in one codebase. They run in one process and share one PostgreSQL database. When the order code needs a payment, it calls a function:

await paymentService.charge(order);

Here is what really happens at that line. The CPU jumps to another place in the same memory. The order object is passed by reference, so nothing is copied. The function either returns or throws. If the server dies, the whole program dies at the same moment, so there is never a state where "orders is alive but payments is dead". The database can wrap the order and the payment in one transaction. Either both are saved, or neither.

The same line, split into services

Now Payment is its own program. The same line becomes a trip across the network. Build it up:

↓
Payment Serviceparse JSON, run logic
↓
Payment DB
↑reply travels back the same way

Order Service still writes something that looks like a function call. Often it is a small client library that hides the HTTP call.

The order object must become bytes (usually JSON). Those bytes go out through DNS lookup, a TCP connection, TLS encryption and maybe a load balancer. Every one of these can fail or be slow.

Payment Service is a different program, maybe on a different machine. It turns the bytes back into an object and runs its own code. It may be restarting right now, or it may be busy.

Payment writes to its own database. Order's database transaction cannot cover this write. The two saves are now separate.

The reply must travel all the way back. If it is lost, Order Service does not know if the charge happened. That doubt did not exist in the monolith.

The call could also go through a message broker instead of HTTP. Then Order Service does not wait for a reply at all (chapter 10).

What exactly is a microservice?

A microservice is a small program you can deploy on its own, and it is responsible for one business capability. A business capability is something the business does, in words a manager would use: "take payments", "track stock", "ship parcels". It is not a technical layer. "Database service" or "validation service" are not business capabilities, and splitting by layer creates services that must all change together.

Order Service reaching into Payment's tables is the thing to avoid. It works on day one, and that is why teams do it.

Why the rule matters

If Order Service runs SQL on Payment's tables, then Payment's table layout becomes a hidden API. Nobody wrote it down, but Order now depends on it. Three things go wrong:

  • Payment can no longer change its own tables. Rename one column and Order breaks, even though Payment's real API did not change. The Payment team may not even know Order reads that table.
  • Rules get skipped. Payment's code may enforce "refund cannot exceed the amount charged". A direct write from another service skips that check.
  • You can't deploy separately any more. A table change forces both services to release together. That is the monolith's coupling, with network costs on top.

DNS


DNS (Domain Name System) is the internet's phone book. Computers connect by IP address, like 104.18.2.7. People and code use names, like api.example.com. DNS turns one into the other.


How a lookup works: the browser asks the operating system. The OS asks a resolver (your ISP's, or 1.1.1.1 / 8.8.8.8). If the resolver doesn't know, it asks the root servers, which point to the .com servers, which point to the servers that hold example.com's records. Every answer carries a TTL (time to live), such as 300 seconds. Everyone along the way may keep the answer for that long. That is why DNS is fast most of the time, and why a DNS change can take minutes to spread.


In the cloud, the record is often a CNAME, an alias: api.example.com → example.cdn-provider.net. The CDN's DNS then returns the address of an edge server close to the user. Some CDNs use anycast: the same IP is announced from hundreds of cities, and internet routing sends each user to the nearest one.



CDN (Content Delivery Network)


A CDN is a company that runs servers in many cities (Cloudflare, AWS CloudFront, Fastly, Akamai). Each is called an edge server. Your own servers are the origin. The edge keeps copies of files so users near it don't have to cross the world.


How it decides what to keep: your origin sends a header like Cache-Control: public, max-age=86400. That tells the edge "you may store this for one day". The edge stores the response under a cache key, usually the URL. The next request for that URL is a hit: answered from the edge in a few milliseconds. The first request, or one after expiry, is a miss: the edge fetches from origin, stores it, then answers.


POST /orders is different. It changes data and is different for every user, so it is never cached. It passes through the edge to your origin. Even so, the CDN still helps: the TLS handshake happens with the nearby edge, and the edge often keeps a warm connection to your origin over a fast private network.

5. Load balancers


Covers: §8 load balancer · §39 load balancing at many levels


A load balancer sits in front of many copies of the same server. For each request it picks one healthy copy. The client only ever sees one address.


You run several copies ("instances") of Order Service for two reasons: one copy can't handle all the traffic, and one copy is a single point of failure. But the client should not need a list of five addresses, and should not care when one dies. The load balancer hides all of that.

Health checks


Every few seconds the load balancer calls a URL on each instance, such as GET /health. If an instance fails a few checks in a row, it is removed from the pool. When it passes again, it is added back. This is an active health check. Some load balancers also do passive checks: they watch real traffic, and if requests to one instance keep failing they stop using it.


There is always a gap. Between the moment an instance dies and the next failed check, the load balancer still sends it traffic, and those requests fail. The lab shows this gap.

Keep business logic out of the gateway


The gateway sits in front of everything, so it is tempting to add "just one small rule" there. Over time, the gateway turns into a huge service that every team must change. That is a new monolith at the front door.


A simple test: does the rule need to know what an order, a product or a user means? Then it belongs in a service. "Users cannot order more than the stock available" is a business rule. It needs Inventory's data, and it will change when the business changes. It belongs in Order or Inventory Service. "Reject requests without a valid token" does not care what the request is about. That can live in the gateway.

9. Timeouts, retries, idempotency, circuit breakers


Covers: §15 timeout · §16 retries · §17 idempotency · §18 circuit breaker


These four tools let a service stay up when the services it calls are slow or broken. Each one fixes a problem that the one before it creates.



Timeouts


A timeout is the longest you will wait for an answer. Many HTTP clients have no timeout by default, so await fetch("http://payment-service/pay") can wait for minutes.

Retries and backoff


Many failures are short: a pod restarting, a dropped packet, a brief overload. Trying again often works. But how you retry matters.


    

  • Exponential backoff: wait 100 ms, then 200, then 400. Each wait is double the last. This gives the other side time to recover.
    • 

  • Jitter: add a random part to each wait. Without it, 1,000 clients that failed together all retry at the same instant and knock the service over again.
    • 

  • Limit retries: 2–3 attempts. And retry only errors that might pass: timeouts, 503, connection reset. Never retry a 400 Bad Request. It will fail the same way every time.
    • 

  • Retry at one layer only: if the gateway, Order and Payment's client each retry 3 times, one failure can become 3×3×3 = 27 calls.
    • 



Retries have a sharp edge. A retry repeats the request. If the first request did succeed and only the reply was lost, the retry does the work a second time.

The post office


Synchronous: Alice walks to Bob's house, hands him a letter, and waits while he reads it. If Bob is out, Alice is stuck. Asynchronous: Alice drops the letter at the post office and leaves. Bob picks it up later. The two don't need to be available at the same time. The broker is the post office. It also keeps the letter safe (written to disk) until Bob confirms he has it.



Delivery guarantees


A consumer reads a message, does the work, then tells the broker "done" (an ack). If it crashes after doing the work but before the ack, the broker delivers the message again. So in practice, brokers promise at-least-once delivery. The same message can arrive twice. Consumers must be idempotent: record the IDs of events already handled and skip repeats. ("Exactly once" exists only in narrow cases, such as inside Kafka with transactions.)



Kafka vs RabbitMQ


Both move messages. They think about them differently.


RabbitMQ is a queue. A message goes in, one worker takes it, the worker acks, and the message is deleted. Great for handing out jobs. Kafka is a log: an append-only list of events, kept on disk for days or forever. Reading does not delete. Each consumer group keeps its own offset (its position in the log). What a worker looks like


A worker usually has no public API. It is a loop:


while (true) {
  const job = await queue.consume();   // blocks until a job is available
  try {
    await processJob(job);
    await queue.ack(job);              // "done, delete it"
  } catch {
    await queue.retry(job);            // put it back (usually with a delay)
  }
}


The ack comes after the work. If the worker crashes halfway, there is no ack, and the broker gives the job to another worker. Nothing is lost, but a job may run twice, so processJob must be idempotent. Need more speed? Run more workers. They share one queue, so 4 → 20 workers is a config change.



Dead-letter queue (DLQ)


Some jobs fail every time: a corrupt image, a bug that one input triggers. These are called poison messages. Retrying forever wastes workers and can block the jobs behind them. So after N failed attempts the broker moves the job to a separate dead-letter queue. Nothing reads the DLQ automatically. You alert on its size, a person looks at the jobs, fixes the bug, and re-sends them.

Common strategies, from simplest:

    •

    •

    •

The dual-write problem

Why not one transaction across all databases?


In a monolith, one transaction protects everything:


BEGIN;
UPDATE orders ...; UPDATE inventory ...; INSERT INTO payments ...;
COMMIT;


With three services and three databases, there is no simple "BEGIN across all of them". A protocol for this does exist: two-phase commit (2PC). A coordinator asks every database "can you commit?", waits for all yes votes, then says "commit". But while it waits, every database holds locks. If the coordinator dies at the wrong moment, those locks stay held until it comes back. Every service's availability now depends on every other's. Kafka, Stripe and most modern systems don't support it at all. So microservice systems avoid distributed transactions and accept eventual consistency instead.

In a monolith you expect every change to appear at once. In a distributed system, a short delay is normal and you design for it.









15. Sagas: undoing work across services


Covers: §32 saga · §33 orchestration · §34 choreography


A saga is a business process split into steps, each done by a different service with its own local transaction. If a step fails, the saga runs compensating actions that undo the earlier steps, in reverse order.


Checkout needs: reserve stock, then charge payment, then create shipment. Say shipping fails. In one database you would ROLLBACK. Here the stock reservation and the charge are already committed in other databases. You can't roll them back. You can only do new actions that cancel their effect: refund the payment and release the stock.


A compensation is not the same as never having done the step. The customer may see a charge and then a refund on their card. An email may already be sent. Some steps can't be undone at all (a shipped parcel). Put steps that can't be undone last, and put the step most likely to fail early.

16. REST vs gRPC


Covers: §37 REST vs gRPC


REST sends readable JSON over plain HTTP URLs. gRPC sends compact binary messages, defined in a strict schema file, over HTTP/2. Both are ways to make synchronous calls between services.


REST: GET /users/123 returns JSON. Anyone can call it with a browser or curl and read the answer. Every language has an HTTP client. That is why it is the default for public APIs.


gRPC: you write the contract first, in a .proto file. A tool then generates client and server code for each language. You call userClient.getUser({id}) and get a typed object back.


service UserService {
  rpc GetUser(GetUserRequest) returns (User);
}
message User {
  int64  id    = 1;   // the number is the field's tag on the wire
  string name  = 2;
  string email = 3;
  bool   active = 4;
}


Why gRPC is smaller and faster: JSON repeats every field name as text in every message ("email":). Protobuf sends only the tag number (1 byte) and the value, and numbers are packed tightly. HTTP/2 also lets many calls share one connection at the same time, and supports streaming in both directions.

Trust between services


"It is inside our network, so it is safe" is an old idea. If an attacker gets into one pod, a flat network lets them call every service and every database. Zero trust means each call must prove who it comes from, and each service gets the smallest set of rights it needs (least privilege).


    

  • mTLS (mutual TLS): both sides show a certificate. Payment knows the caller really is Order Service, and the traffic is encrypted.
    • 

  • Service identities and short-lived certificates: each service has its own identity, and its certificate expires in hours, so a stolen one soon becomes useless.
    • 

  • Network policies: firewall rules in the cluster. "Only Order may connect to Payment on port 8080."
    • 

  • IAM and OAuth client credentials: services get their own tokens to call APIs, with their own scopes.
    •

Service mesh


Timeouts, retries, mTLS, metrics and tracing are needed by every service. Writing them into each service's code, in each language, is a lot of repeated work. A service mesh (Istio, Linkerd, Consul) moves that work into a small proxy that runs next to each service, called a sidecar. All traffic in and out passes through it.

20. Deploying, scaling and failure isolation


Covers: §47 deployment · §48 scaling independently · §49 failure isolation


These are the three main payoffs of microservices: each service ships on its own schedule, scales on its own, and can fail without taking the others down. Each comes with a price.



Independent deployment and API compatibility


A monolith has one version: everything ships together. With services, you have User v17, Product v8, Order v31, Payment v12, all at once. Teams release when they are ready. 21. Traps: the distributed monolith and chatty services


Covers: §50 distributed monolith · §51 one service per table · §54 service call chains


A distributed monolith is a system split into services that still can't work, change or deploy without each other. You get all the coupling of a monolith plus all the network problems of microservices.


It usually happens like this. A team takes the User, Order and Payment modules and turns each into a service, keeping the same calls. Now one request goes Order → User → Profile → Inventory → Payment → Fraud → Notification, one after the other, and every service must be up for anything to work.




 
Lab: the cost of a deep call chain

 
Each service is up 99.9% of the time (about 43 minutes down per month). Each hop takes 100 ms. Add hops.

 

 

 




The math is simple and harsh. If every service must succeed, the chances multiply: 0.9997 ≈ 0.993. That is about 5 hours of failure a month, not 43 minutes. Latency adds up too, and the slowest hop sets the pace. So good systems keep synchronous chains short (1–2 hops is ideal), fetch in parallel when they can, and move everything that isn't needed for the answer to async events.
