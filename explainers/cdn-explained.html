1. What a CDN is, and why distance costs time

Covers: notes 1, 4, 5 · Sources: Cloudflare Learning Center (What is a CDN, CDN performance), RFC 9293 and RFC 8446 via the Cloudflare TLS 1.3 blog for round trip counts

A content delivery network (CDN) is a group of servers in many places that keeps copies of web content close to users. Cloudflare's definition: "a geographically distributed group of servers that speeds up the delivery of web content by caching it closer to users."

The server that holds the real content is the origin. A CDN server near users is an edge. The building that holds edges in one city is an edge location (vendors also say PoP, point of presence).

The problem a CDN solves is distance. Data in fibre cannot go faster than light in glass, so a request from Mumbai to an origin in Virginia and back takes a fixed minimum time. That time is the round trip time (RTT). Bandwidth does not help here. A faster link sends more bytes per second, but each question still waits one RTT for its answer.

A web page needs several round trips before the first byte of content arrives: one to open the TCP connection, one for the TLS 1.3 handshake (two for TLS 1.2), and one for the HTTP request. Then the browser reads the HTML and asks for the CSS, scripts and images, which costs more round trips. Every round trip costs the full RTT. If the RTT is 200 ms, four round trips cost 800 ms before anything else is counted.

A CDN shortens the RTT. The browser talks to an edge 10 to 30 ms away instead of an origin 200 ms away. When the edge has a copy (a cache hit), the long trip does not happen. When the edge has no copy (a cache miss), the edge fetches it from the origin, keeps a copy, and sends it on.

Without a CDN, the browser opens its connection to the origin. Each of its round trips costs the full 200 ms (example number).

With a CDN, the site's name points to the CDN. The browser opens its connection to a nearby edge, so the TCP and TLS handshakes cost 15 ms each, not 200 ms.

The edge keeps copies of responses. On a hit, it answers from its cache. The origin does no work and the long trip does not happen.

On a miss, the edge must go to the origin. It sends the request on a connection it opened earlier, so it pays one long round trip, not three. Chapters 8 to 11 are about this path.

2. Reaching the nearest edge: anycast and DNS

Covers: note 4 · Sources: Cloudflare Learning Center (What is Anycast), Cloudflare blog "A brief anycast primer" (2011, mechanism only), AWS CloudFront docs (How CloudFront delivers content), RFC 7871 (EDNS Client Subnet)

The browser does not know where edges are. The CDN sends it to a near edge in one of two ways: with anycast, where many edge locations announce the same IP address, or with DNS steering, where the CDN's DNS server gives each user the IP address of a near edge.

Anycast

Normally one IP address belongs to one machine (unicast). With anycast, every edge location announces the same IP address range to the internet's routers with BGP, the protocol that networks use to tell each other which addresses they can reach. Each router keeps the routes it heard and picks one, so a packet goes to the edge location that is "closest" in BGP terms. Cloudflare: "In the context of a CDN, Anycast typically routes incoming traffic to the nearest data center with the capacity to process the request efficiently."

BGP closest is not always fastest. BGP prefers the path through the fewest networks (AS hops) and the business rules of each network, not the lowest delay. Usually the two agree. When they do not, a user can land on an edge further away than the best one.

If one edge location fails or is taken offline, it stops announcing the route. Routers then pick the next route they know, and traffic moves to the next location without any DNS change.

DNS steering

Here each edge location has its own IP addresses. The site's name is a CNAME to a CDN name. The CDN's authoritative DNS server answers with the address of an edge near the person who asked. AWS: "DNS routes the request to the CloudFront POP (edge location) that can best serve the request, typically the nearest CloudFront POP in terms of latency."

The DNS server does not see the user. It sees the user's DNS resolver. If the user uses a resolver far away, the answer fits the resolver's location, not the user's. EDNS Client Subnet (RFC 7871) lets the resolver pass on a shortened form of the user's address so the CDN can choose better. The RFC notes it "has some known operational and privacy shortcomings".

3. Cache hit and cache miss

Covers: notes 1, 5 · Sources: RFC 9111 (HTTP Caching) §2, §4; Cloudflare Learning Center (What is caching, cache hit ratio); nginx docs (ngx_http_proxy_module: proxy_cache, $upstream_cache_status)

An edge is a reverse proxy with a cache. It receives the request, makes a cache key from it, and looks the key up in its storage. Found and still fresh: a hit, answered from storage. Not found: a miss, sent to the origin. The response is stored under the key if the rules allow it, then sent to the user.

The cache key is normally the scheme, host, path and query string, such as https://www.acmeshop.com/static/logo.svg. RFC 9111 §2: many caches "only cache GET responses and therefore only use the URI as the cache key." Chapter 5 shows how the key can grow.

Each stored copy has a freshness lifetime, set by the origin with headers such as Cache-Control: max-age=3600 (fresh for 3600 seconds). When it is older than that, it is stale. A stale copy is not used as is. The edge first checks with the origin (chapter 6).

Each edge location has its own cache. A file cached in Frankfurt is not in Singapore. The first user in each location gets a miss. The share of requests that are hits is the cache hit ratio: hits divided by hits plus misses.

The edge looks the key up. The first time, nothing is there. That is a miss.

The edge sends the request to the origin. The origin answers and says, in Cache-Control, how long the answer may be reused.

The edge stores the response under the key, with the time it was stored. Then it sends the response to the user.

The next request for the same key, at the same edge, before the lifetime ends, is a hit. The origin never sees it.

4. What may be cached: GET, POST and Cache-Control

Covers: notes 2, 6 · Sources: RFC 9110 §9.2.1, §9.3.3; RFC 9111 §3, §5.2.2, §7; nginx docs (proxy_cache_methods, proxy_cache_valid, proxy_ignore_headers)

A CDN may only reuse a response when the HTTP rules say it is safe for other users. In practice that means responses to GET and HEAD requests, which the origin marks as cacheable. Everything else goes to the origin every time.

Methods

GET and HEAD are safe methods (RFC 9110 §9.2.1): they read and do not change anything. One answer can serve many users. POST changes something, such as placing an order. Each POST must reach the origin. RFC 9110 §9.3.3 allows caching a POST response only with explicit freshness and a Content-Location equal to the request URI, and says "the overwhelming majority of cache implementations only support GET and HEAD." nginx caches GET and HEAD by default (proxy_cache_methods GET HEAD). So a CDN acts as a plain proxy for POST: it passes the request on, over its pooled origin connections.

Cache-Control from the origin

Two more rules matter. A request with an Authorization header may only be stored by a shared cache if the response has public, s-maxage or must-revalidate (RFC 9111 §3). And Set-Cookie: RFC 9111 §7 says it "does not inhibit caching", but nginx does not cache a response that has it. Many CDNs are strict in the same way, because a cookie usually means a per-user response.

The common failure is a CDN rule that overrides the origin, such as "cache everything for 60 s". If it hits a logged-in page, the edge stores one user's page and shows it to everyone with the same cache key.

5. The cache key and Vary

Covers: notes 1, 2 · Sources: RFC 9111 §2, §4.1 (Vary); nginx docs (proxy_cache_key, Vary handling in proxy_cache_valid)

The cache key decides which requests share one stored copy. Two requests with the same key get the same response. If the key is too short, users get each other's content. If it is too long, every request is a miss.

When the origin sends different content for the same URL, for example by language, it must say so with Vary. Vary: Accept-Language tells the cache that the Accept-Language request header is part of the key. RFC 9111 §4.1: a cache must not reuse a stored response "unless all the presented request header fields nominated by that Vary field value match". nginx does not cache a response with Vary: *.

The query string is part of the key by default. ?utm_source=mail and ?utm_source=ad are two keys for the same file. CDNs let you drop or sort query parameters in the key for this reason. It also gives attackers a way past the cache (chapter 12): each random query string is a new key, so each request is a miss.

6. Freshness, revalidation and stale copies

Covers: notes 1, 5 · Sources: RFC 9111 §4.2 (freshness, heuristic), §4.3 (validation), §5.1 (Age); RFC 9110 §8.8.3 (ETag), §13.1.2 (If-None-Match), §15.4.5 (304); RFC 5861 (stale-while-revalidate, stale-if-error); nginx docs (proxy_cache_revalidate, proxy_cache_use_stale)

A stored copy is fresh while its age is under its lifetime. After that it is stale. The edge does not throw a stale copy away. It asks the origin "has this changed?" with a small request. That check is revalidation.

How the check works

With the first response, the origin sent a validator: an ETag (a tag for this version of the content) and often Last-Modified. To revalidate, the edge sends the same GET with If-None-Match: "the-etag". If the content did not change, the origin answers 304 Not Modified with no body, and the edge marks its copy fresh again. If it changed, the origin sends 200 with the new content. A 304 saves the bytes, but it still costs one round trip to the origin.

The age of a copy is sent to users in the Age header (RFC 9111 §5.1), so a browser can tell that a response came from a cache. If the origin sends no lifetime at all, a cache may guess one. RFC 9111 §4.2.2 gives 10% of the time since Last-Modified as "a typical setting". It is an example, not a rule.

Serving stale copies on purpose

RFC 5861 adds two Cache-Control extensions. stale-while-revalidate=N: for N seconds after the copy goes stale, the cache may serve it at once and revalidate in the background, so no user waits for the origin. stale-if-error=N: if the origin fails (500, 502, 503, 504 or no answer), the cache may serve the stale copy for N seconds instead of an error. This is how a CDN keeps a site up while the origin is down. must-revalidate turns this off: a stale copy must never be served without a check.

The cost of a long lifetime is old content after a change. If you deploy a new app.js, edges keep the old one until it expires. Two fixes: purge (tell the CDN to drop the copy) or versioned names (app.3f9a1c.js, a new name for each version, cached for a year).

7. Many misses at once: coalescing and tiered cache

Covers: notes 5, 9 · Sources: nginx docs (proxy_cache_lock, proxy_cache_lock_timeout); AWS CloudFront docs (request collapsing, Origin Shield); Fastly docs (request collapsing, shielding); Cloudflare docs (Tiered Cache)

When a popular file is not in the cache, thousands of users can ask for it in the same second. Without help, each of those misses goes to the origin. CDNs prevent this in two places: request coalescing inside one edge location, and a tiered cache between edge locations.

Request coalescing

The first miss for a key goes to the origin. The edge marks the key as "being fetched". Other requests for the same key wait on that mark. When the response arrives, the edge stores it and answers all the waiting requests from it. nginx calls this proxy_cache_lock: "only one request at a time will be allowed to populate a new cache element". CloudFront calls it request collapsing, and logs the first request as "Miss" and the others as "Hit". It works only for requests with the same cache key.

It has a failure mode. If the response turns out to be not cacheable (private, no-store), the waiting requests cannot use it. Fastly: "each of the queued requests must then be sent to the backend independently". The waiting made them slower, not faster. nginx has a limit for the wait, proxy_cache_lock_timeout (default 5 s); after it, the request goes to the origin and the response is not cached.

Tiered cache (origin shield)

Coalescing works inside one edge location. With 300 locations, a new file can still cause 300 misses at the origin. A tiered cache puts one more cache layer in front of the origin: lower-tier locations ask an upper-tier location, and only the upper tier asks the origin. Cloudflare: "If the upper-tier does not have the content, only the upper-tier can ask the origin for content." AWS Origin Shield: requests are "consolidated with other requests for the same object, resulting in as few as one request going to your origin." The cost is one more hop on a miss.

8. Why a new connection is slow

Covers: note 7 · Sources: RFC 9293 (TCP three-way handshake); RFC 8446 §2.3, §8 (TLS 1.3, 0-RTT and replay); Cloudflare blog "RFC 8446 aka TLS 1.3" (round trip counts); RFC 5681 §3.1 (slow start); RFC 6928 (initial window of 10 segments); RFC 8470 (425 Too Early); RFC 9000 (QUIC); Cloudflare docs (SSL/TLS modes)

Before any request goes on a new connection, two handshakes must finish. TCP needs one round trip (SYN, SYN-ACK, ACK). TLS 1.3 needs one more, TLS 1.2 two more. After that, TCP still sends slowly at first and speeds up over several round trips. A reused connection skips all of this.

Handshakes

TCP: the client sends SYN, the server answers SYN-ACK, the client sends ACK. The client can send data with its ACK, so the cost is one RTT. TLS 1.3: the client's first message already holds its key share, so the server can answer with its certificate and finish in one RTT. The Cloudflare TLS 1.3 post: latency can "drop from two round-trips to only one round-trip". TLS 1.2 needs two. QUIC (HTTP/3) runs over UDP and does the transport and TLS 1.3 handshake together, in one RTT.

0-RTT: a client that connected before can send its request in the first flight, with no wait. RFC 8446 §2.3: this data "is not forward secret" and "There are no guarantees of non-replay between connections." An attacker who copies the packet can send it again. So only safe requests such as GET should use 0-RTT. A server can refuse early data with status 425 Too Early (RFC 8470).

Slow start

A new TCP connection does not know the path's capacity. It starts with a small congestion window (how much unacknowledged data it may have in flight) and grows it as acknowledgements come back (RFC 5681 §3.1). RFC 6928 raised the start to 10 segments, about 14.6 KB. So a 100 KB response on a new connection needs about 3 round trips of data (14.6, then 29.2, then 58.4 KB). A warm connection that has already grown its window sends it in one.

Two connections, not one

The user's TLS connection ends at the edge. The edge reads the request, then sends it to the origin on a second, separate connection. That is why the edge can cache and filter. It also means the CDN sees the plain request. The edge-to-origin leg needs its own TLS: Cloudflare's "Flexible" mode sends it unencrypted, "Full (strict)" encrypts it and checks the origin's certificate. Cloudflare recommends Full or Full (strict).

The split helps speed too. The user's handshakes happen over the short distance to the edge. Only the edge-to-origin leg is long, and the edge can keep that one open.

9. Connection pools to the origin

Covers: notes 7, 8 · Sources: nginx docs (upstream keepalive, keepalive_timeout, keepalive_requests, $upstream_connect_time, stub_status, CHANGES 1.29.7); RFC 9112 §9.3 (persistent connections); RFC 9110 §9.2.2 (retrying requests); AWS CloudFront docs (origin keep-alive timeout); Cloudflare blog "How we built Pingora" (2022)

A connection pool is a set of open, already-handshaken connections from the edge to the origin. When a request must go to the origin, the edge takes an idle connection from the pool, sends the request, and puts the connection back when the response is done. Only when no idle connection exists does it open a new one.

HTTP/1.1 keeps connections open by default (RFC 9112 §9.3: "persistent connections"). The pool uses this. The state the edge keeps for each origin is a list of connections, each busy (carrying a request) or idle (open, waiting), with the time it went idle.

The rules a pool follows

  • Take idle first. A request takes an idle connection if one exists. No handshake, no slow start.
  • Open when none is idle. If all are busy, the edge opens a new one and pays TCP and TLS. In nginx, keepalive N is how many idle connections each worker keeps. nginx docs: it "does not limit the total number of connections to upstream servers". Concurrency decides how many are open; N decides how many stay after a burst.
  • Close extras. When a request finishes and N idle connections already wait, the least recently used is closed.
  • Close after idle time. nginx keepalive_timeout (default 60 s) closes a connection that stays idle that long. CloudFront's origin keep-alive timeout is 5 s by default, up to 300 s by quota.
  • Close after many requests. nginx keepalive_requests (default 1000) closes a connection after that many requests, so memory is freed and load spreads.

Since nginx 1.29.7 (March 2026), upstream keepalive is on by default with 32 idle connections per worker. Before, it was off and every proxied request opened a new connection unless you configured it.

Each worker has its own pool

In nginx each worker process has its own pool. With many workers and many edge servers, a request often lands where no idle connection exists. Cloudflare wrote that its old nginx-based proxy pooled "per worker", and that Pingora, which shares one pool across threads, raised one customer's connection reuse from 87.1% to 99.92% and "reduced new connections to their origins by 160x" (2022 blog, numbers for one customer).

The idle close race

Both ends may close an idle connection. If the origin closes it at the same moment the edge sends a request on it, the request fails with a reset or an empty reply. The edge can send a GET again on a new connection, since GET is idempotent. It must not do that for a POST. RFC 9110 §9.2.2: "A proxy MUST NOT automatically retry non-idempotent requests." The fix is to make the edge close first: set the edge's idle timeout shorter than the origin's. With CloudFront's 5 s default, an origin that keeps idle connections for 60 s is safe. An origin with a 2 s timeout is not.

10. Multiplexing: many requests, few connections

Covers: note 9 · Sources: RFC 9112 §9.3.2 (pipelining); RFC 9113 §1, §5, §6.5.2 (HTTP/2 streams, SETTINGS_MAX_CONCURRENT_STREAMS); RFC 9114 §1 and RFC 9000 §13 (HTTP/3, QUIC loss recovery); Cloudflare docs (HTTP/2 to origin, page updated 2026-08-14); AWS CloudFront docs (requests to custom origins); nginx docs (proxy_http_version) and lab measurement

The edge turns many user connections into few origin connections in two ways. Reuse over time: one HTTP/1.1 connection carries one request at a time, but thousands one after another. Multiplexing: one HTTP/2 or HTTP/3 connection carries many requests at the same time, each as its own stream.

Why the edge needs few origin connections at all

Users hold many connections that are idle most of the time, between page loads or while reading. Most of their requests are hits, which need no origin connection. Only misses and uncacheable requests (POST, private pages) go to the origin, and each needs a connection only while it is in flight. So the number of origin connections follows the number of requests in flight to the origin at one moment, not the number of users.

HTTP/1.1: one request per connection at a time

On HTTP/1.1, a connection carries a request, waits for the whole response, then carries the next. Pipelining (sending more requests before the answers) exists, but responses must come back in order (RFC 9112 §9.3.2), so one slow response blocks the ones behind it. RFC 9113 §1: so "HTTP/1.0 and HTTP/1.1 clients use multiple connections". For an edge, N requests in flight to the origin means N connections. CloudFront "forwards requests to your custom origin using HTTP/1.1."

HTTP/2: streams on one connection

HTTP/2 cuts each request and response into frames. Each frame carries a stream ID. RFC 9113 §5: "A single HTTP/2 connection can contain multiple concurrently open streams, with either endpoint interleaving frames from multiple streams." The receiver puts frames back together by stream ID. So 100 requests can be in flight on one connection, and a slow response does not block the others. The server limits how many with SETTINGS_MAX_CONCURRENT_STREAMS; RFC 9113 recommends at least 100. Cloudflare: "HTTP/2 connection to the origin is enabled by default", "multiple HTTP/2 streams share a single long-lived TCP connection", and "If the stream limit has been reached, Cloudflare opens a new TCP connection".

Not every proxy that speaks HTTP/2 to the origin multiplexes. nginx added proxy_http_version 2 in 1.29.4. The real lab below shows that nginx 1.31.6 still sends one request at a time on each upstream HTTP/2 connection.

HTTP/3: streams without TCP's queue

HTTP/2 runs on one TCP connection, and TCP delivers bytes in order. If one packet is lost, every stream waits for its resend, even streams whose data arrived. RFC 9113 §1: "TCP head-of-line blocking is not addressed by this protocol." HTTP/3 runs on QUIC, which recovers loss per stream. RFC 9000 §13: "only streams with data in that packet are blocked waiting for a retransmission".

11. The backbone: edge to origin

Covers: note 10 · Sources: Google Cloud docs (Network Service Tiers overview); Cloudflare docs (Argo Smart Routing, Tiered Cache); Cloudflare blog "Argo" (2017); Cloudflare network page (checked 2026-10-07); Mathis et al., "The Macroscopic Behavior of the TCP Congestion Avoidance Algorithm", ACM CCR 1997 (throughput model)

The path from the edge to the origin is the middle mile. On the public internet, it crosses several networks, and each picks the next hop by its own BGP rules and costs, not by speed. A CDN with its own backbone (private links between its locations) carries the request most of the way on its own network, and leaves it near the origin.

Why the public path is often not the best

BGP chooses routes by policy and AS-path length. It does not measure delay or loss, and it does not move traffic away from a congested link. A request from Mumbai to Virginia may cross a busy exchange point even when a faster path exists. Loss hurts more than delay: TCP reads loss as congestion and cuts its sending rate. A rough model (Mathis et al., 1997) gives throughput of about MSS / RTT × 1.22 / √loss. Double the RTT and throughput halves. Raise loss from 0.01% to 1% and throughput falls 10 times.

What a CDN does on the middle mile

  • Enter its network early. Google's Premium Tier: "incoming traffic from systems on the internet enters Google's high-performance network at the PoP closest to the sending system". Standard Tier uses "regular ISP networks".
  • Pick paths by measurement. Cloudflare's Argo Smart Routing "detects real-time network issues and routes your web traffic across the most efficient network path, avoiding congestion." The 2017 launch post reported "an average 35% decrease in latency" (old number, one source).
  • Keep long-haul connections warm. The edge near the user and the location near the origin keep connections open between them. Their congestion windows are already large, so a miss does not pay handshakes or slow start over the long distance.
  • Exit near the origin. The last hop from the CDN to the origin is short, often in the same city or cloud region. A tiered cache (chapter 7) puts the upper tier there too.

Size, for scale: Cloudflare's network page lists 348 cities and says "95% of the world's Internet-connected population is within 50 milliseconds of a Cloudflare data center" (checked 2026-10-07; a Cloudflare blog from August 2026 says "330+ cities").

12. DDoS: the edge as the first line of defence

Covers: note 3 · Sources: Cloudflare Learning Center (What is a DDoS attack, SYN flood, What is Anycast); RFC 4987 §3.6 (SYN cookies); Cloudflare DDoS reports 2025 Q4 (2026-02-05) and 2026 H1 (2026-08-11); nginx docs (limit_req); AWS CloudFront docs (managed prefix list); Cloudflare docs (Tunnel, IP ranges)

A distributed denial-of-service (DDoS) attack floods a target from many machines at once, so real users cannot get through. A CDN stands in front of the origin, so the attack hits the CDN first. The CDN has far more capacity than one origin, spreads the attack over many locations, and drops attack traffic before it reaches the origin.

Three kinds of attack

Scale: Cloudflare reported "A record-setting 31.4 Tbps attack" that "lasted just 35 seconds" (2025 Q4 report, 5 Feb 2026). Its 2026 H1 report says its defence runs in "330+ cities globally, backed by 500 Tbps of network capacity". It also says "96.62% of network-layer attacks" stayed under 500 Mbps. Most attacks are small, but even a small one can fill one origin's link.

Two ways around the edge

Cache busting. The cache only helps when requests share a key. An attacker adds a random query string (?r=8812) to every request. Each is a new key, so each is a miss and goes to the origin. Rate limits, WAF rules, and dropping unknown query parameters from the key are the defence. This is reasoning from the cache key rule, not a quote.

Going straight to the origin. If the origin's IP address is known (old DNS records, a mail server on the same IP, a leak in a header), the attacker skips the CDN. Lock the origin down so it accepts only CDN traffic: a firewall that allows only the CDN's address ranges (AWS keeps a managed prefix list "which prevents non-CloudFront traffic from reaching your origin"), or a tunnel with outbound-only connections and no public IP, such as Cloudflare Tunnel. A firewall on the origin drops attack packets only after they have crossed the origin's own link, so a flood bigger than that link still hurts. With no public IP, there is nothing to send the flood to.

Lab: send an attack, switch defences on

Pick an attack and switch defences on and off. The meters show load as a share of capacity at each layer: the busiest edge location's link, the edge's connection table, and the origin. Over 100% means real users are refused. Capacities and attack sizes are example numbers. Try a GET flood on a cached file: the cache takes it all. Then break it twice: cache busting (random query strings) and an attack on the origin's IP without lock-down.

Lab: rate limit and cache busting on the real edge

/limited/ on the edge has limit_req: 5 requests per second per client IP, with a burst of 10 (burst=10 nodelay), and status 429 for the rest. nginx's limit uses the "leaky bucket" method. The last line of the flood presets counts requests that reached the origin.

"30 at once from one IP": 11 get 200 (1 plus the burst of 10), 19 get 429. Wait a few seconds and run it again: the bucket drained, so 11 pass again. "GET flood on a cached file": 200 requests, the origin gets 0 or 1. If the 10 s lifetime ends during the flood, one request shows REVALIDATED and others UPDATING: nginx serves the old copy while one request checks with the origin (proxy_cache_use_stale updating). Now break it. "Cache-busting flood" sends 50 requests, each with a random query string: 50 MISS, the origin gets 50. The cache did nothing. Run the rate-limited version, "Cache busting against /limited/": at most 11 pass and reach the origin (fewer if the bucket has not drained yet), the rest get 429 at the edge.

What to remember for an interview

QuestionShort answer
Why is a CDN faster on a hit?Every round trip is short, and the origin does no work.
Why is it faster on a miss?The user's handshakes end at the near edge. The edge uses a warm pooled connection, often over its own backbone, so the long distance costs one round trip, not three or more.
What does it cache?GET and HEAD responses that Cache-Control allows for shared caches. Not private, no-store or (in most CDNs) Set-Cookie responses. POST passes through.
How do many users become few origin connections?Hits need none. Misses reuse pooled connections one after another (HTTP/1.1) or share one connection as streams (HTTP/2). Coalescing and tiered cache cut repeated misses.
What goes wrong?Leaked private pages from a wrong cache rule, missing Vary, old content after a deploy, misses at many locations at once, the idle close race, cache busting, and a known origin IP.
