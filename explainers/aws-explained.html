1. The AWS map: Regions, AZs and API calls

Covers: Regions, Availability Zones, shared responsibility, how a tool talks to AWS · Sources: aws.amazon.com/about-aws/global-infrastructure (checked 2026-10-07), AWS Fault Isolation Boundaries whitepaper, AWS Shared Responsibility Model page, EC2 User Guide (Regions and Zones), CloudTrail concepts

Amazon Web Services (AWS) rents out computers, storage, databases and networks that you control with API calls. You do not buy hardware. You ask for a resource, use it, and pay for the time or the amount you use.

Every AWS resource lives in a place. To design anything on AWS, you must know these places, because they decide what fails together.

Regions and Availability Zones

A Region is a geographic area where AWS has a cluster of data centers, for example us-east-1 (N. Virginia) or eu-central-1 (Frankfurt). AWS designs each Region to be isolated from the others. On 2026-10-07 the AWS global infrastructure page lists 39 Regions and 124 Availability Zones. (The Regions table in the AWS docs still said 34 Regions on that date. The global infrastructure page is newer.)

An Availability Zone (AZ) is "one or more discrete data centers with redundant power, networking, and connectivity in an AWS Region". Each Region has at least three AZs. The AZs of one Region are "meaningfully distant from each other, up to 60 miles (~100 km)". They are far enough apart that a fire, flood or power cut usually hits only one AZ, and close enough that a round trip between them is short, so a database can copy each write to a second AZ before it says "done".

AZ names are the Region code plus a letter: us-east-1a, us-east-1b. The letter is per account. Your us-east-1a can be a different building from another account's us-east-1a. The AZ ID (use1-az1) names the same building for every account.

This gives three levels of failure. Design for each one:

Some services are zonal: an EC2 instance, an EBS volume, a NAT gateway and a subnet each live in exactly one AZ. Some are regional: S3, DynamoDB, SQS and Lambda spread their data and work over the AZs of a Region for you. A few are global: IAM, Route 53 and CloudFront. This one property explains many interview questions. Why must the EBS volume be in the same AZ as the instance? It is zonal. Why does an S3 bucket survive the loss of an AZ? It is regional.

Every action on AWS is an API call: create an instance, read an object, add a user. The console, the CLI and the SDKs are only different ways to send these calls.

The call goes over HTTPS to a service endpoint in one Region. The endpoint checks the signature (who is calling) and the IAM policies (may they do this). This part is the control plane: it creates and changes resources.

Zonal resources live in one AZ. If you put three instances in three AZs, the loss of one AZ takes one third of your capacity, not all of it.

Regional services copy your data over several AZs themselves. You do not choose an AZ for an S3 object or an SQS message.

A few services are global. An IAM user exists in every Region. A Route 53 zone answers from DNS servers all over the world.

Control plane and data plane

AWS splits most services into two parts. The control plane creates, changes and deletes resources (RunInstances, CreateBucket). The data plane does the work of a resource that already exists (an instance runs your code, S3 returns an object). CloudTrail calls the management calls "control plane operations". The data plane is simpler and is built to keep running when the control plane has trouble. So a good recovery plan does not depend on creating new resources during an outage. It keeps spare capacity already running.

Shared responsibility

AWS calls this split "Security of the Cloud" and "Security in the Cloud". AWS protects "the infrastructure that runs all of the services": buildings, hardware, the hypervisor, the network. You protect what you put on it: who has access (IAM), your network rules, your data, and the guest operating system on EC2. The line moves with the service. On EC2 you patch the OS. On RDS, AWS patches the database engine. On Lambda, AWS also runs the OS and the runtime.

2. VPS vs EC2: renting a server

Covers: VPS, Lightsail, EC2 instances, instance types, AMIs, instance states, purchase options, placement groups · Sources: aws.amazon.com/what-is/vps, Lightsail pricing and docs, EC2 User Guide (concepts, AMIs, user data, instance lifecycle, Spot interruption notices, placement strategies, Dedicated Hosts), EC2 instance type names, aws.amazon.com/ec2/pricing, Savings Plans User Guide

A virtual private server (VPS) is one virtual machine with a fixed size and a fixed monthly price. Amazon EC2 (Elastic Compute Cloud) also rents virtual machines, called instances, but you pick from hundreds of sizes, pay by the second, and create or delete them with API calls.

Both are virtual machines. A physical server runs a hypervisor, which splits its CPU and memory into several virtual machines. AWS says a VPS "only consumes a portion of the server's underlying physical resources", and each user "receives a virtual machine with dedicated resources". So the difference is not the technology. It is the deal around it.

The VPS deal

A VPS plan is a bundle: CPU, memory, an SSD and a monthly data transfer allowance, for one price. AWS sells this too, as Amazon Lightsail: "virtual private server (VPS) instances ... at a cost-effective monthly price". On 2026-10-07 the Lightsail pricing page listed, for example, $5 per month for 1 GB memory, 2 vCPUs, a 40 GB SSD and 2 TB transfer. The bundle makes cost easy to predict. You pay the same at 3 a.m. and at the peak. When traffic grows past the box, you move to a bigger plan by hand.

The EC2 deal

EC2 unbundles everything. You choose each part:

  • Instance type: the hardware. In m7g.large, m is the series (general purpose), 7 the generation, g an option (AWS Graviton, an Arm CPU) and large the size. Series letters: M general purpose, C compute, R memory, I storage, T burstable, P and G for GPUs. A bigger size doubles CPU and memory step by step.
  • AMI (Amazon Machine Image): the disk image to boot, with the OS. An AMI is specific to a Region, an OS and a CPU architecture, so an x86 AMI does not boot on Graviton.
  • Storage: EBS volumes, paid by size and speed (chapter 3).
  • Network: a subnet in one AZ and security groups (chapter 4). Data out to the internet is billed by the GB.
  • User data: a script that runs at first boot to install your app.

EC2 bills "in one-second increments, with a minimum of 60 seconds" (Amazon Linux, Windows, RHEL and Ubuntu). So 10 instances for one hour cost the same as one instance for 10 hours. This is what makes scaling out cheap: you add servers for the peak and delete them after.

EC2 runs on the Nitro System: dedicated hardware cards for network and storage, plus a small hypervisor whose performance "is indistinguishable from bare metal for most workloads".

3. Disks for servers: EBS, instance store, EFS

Covers: EBS volume types, snapshots, Multi-Attach, instance store, EFS · Sources: Amazon EBS User Guide (what is EBS, general purpose and provisioned IOPS volumes, HDD volumes, snapshots, Multi-Attach), EC2 User Guide (instance store, instance store lifetime), Amazon EFS User Guide and FAQ

An EC2 instance can use three kinds of disk. An EBS volume is a network disk in one AZ that lives on after the instance. An instance store is a disk inside the physical host that is erased when the instance stops. EFS is a shared network file system that many instances mount at once.

EBS: a disk over the network

Amazon Elastic Block Store gives a block device: the OS sees a raw disk and puts its own file system on it. The volume is not inside the host. It sits on storage servers in the same AZ, and AWS copies its data "across multiple servers in an Availability Zone". So if the host dies, the volume survives, and AWS can attach it to a new instance. "The volume and instance must be in the same Availability Zone", because the disk traffic must stay inside the AZ to be fast.

IOPS is input/output operations per second (many small random reads and writes, as a database does). Throughput is MiB per second (large reads, as a log scan does). A volume can run out of either one.

A snapshot is a backup of a volume, stored in S3 by AWS. It is incremental: "we save only the blocks on the volume that have changed since the most recent snapshot." From a snapshot you can make a new volume in another AZ, Region or account. This is how you move a disk out of its AZ.

Usually one volume attaches to one instance. Multi-Attach lets one io1 or io2 volume attach to up to 16 Nitro instances in the same AZ. The file system must then handle many writers (a normal ext4 does not), so this is for special cluster software.

Instance store: fast, but temporary

Some instance types (the d option, as in m6id, and the I series) have disks "physically attached to the host computer". There is no network in the way, so they are very fast. But the data "persists even if the instance is rebooted. However, the data does not persist if the instance is stopped, hibernated, or terminated", and "every block of the instance store volume is cryptographically erased." Use it for caches, scratch space, and data that another copy protects, for example one replica of a database cluster.

EFS: one file system for many servers

Amazon Elastic File System speaks NFS (v4.0 and v4.1). "Tens, hundreds, or even thousands of compute instances can access an Amazon EFS file system at the same time." A Regional file system stores data "across multiple geographically separated Availability Zones", so instances in every AZ mount the same files. It grows and shrinks with the data. It is slower per operation than EBS, because each file operation is a network call to a shared service.

The fourth option is not a disk at all: S3 (chapter 6). An app that keeps uploads in S3 instead of on a local disk can lose any instance without losing data. This is the usual way to make servers stateless.

4. VPC: your private network

Covers: VPC CIDR, subnets, reserved addresses, route tables and longest prefix match, internet gateway, NAT gateway, security groups, network ACLs, VPC endpoints, peering, Transit Gateway, default VPC · Sources: Amazon VPC User Guide (CIDR blocks, subnet sizing, configure subnets, route table priority, internet gateways, NAT gateways, security groups, network ACLs, default VPC), AWS PrivateLink guide (gateway endpoints, concepts), VPC Peering guide, Transit Gateway guide

A Virtual Private Cloud (VPC) is a private network inside one AWS Region. You choose its IP range, split it into subnets, and decide with route tables and firewall rules which traffic may go where.

Address space and subnets

A VPC gets an IPv4 CIDR block between /16 (65,536 addresses) and /28 (16 addresses), usually from the private ranges, for example 10.0.0.0/16. Pick a range that does not overlap your other VPCs or your office network. Two networks with the same addresses cannot be connected later.

A subnet is a part of the VPC range. "Each subnet must reside entirely within one Availability Zone." So the subnet is how you place things in AZs: an instance launched in subnet 10.0.1.0/24 in us-east-1a runs in that AZ. AWS keeps 5 addresses of every subnet: for 10.0.0.0/24, .0 (network), .1 (VPC router), .2 (DNS), .3 (future use) and .255 (broadcast). A /24 has 251 usable addresses, a /28 has 11.

Route tables

Every subnet uses one route table, the main one unless you set another. A route says "traffic to this range goes to this target". Every table has a local route for the VPC range, so all subnets of a VPC can reach each other. When several routes match, AWS uses "the most specific route that matches the traffic. This is known as the longest prefix match." A packet to 10.0.2.20 matches both 10.0.0.0/16 (local) and 0.0.0.0/0. The /16 is longer, so it stays inside the VPC.

A public subnet has a route to an internet gateway (IGW). A private subnet does not. That is the only difference. The IGW is "horizontally scaled, redundant, and highly available", and it does one-to-one address translation: an instance needs a public IPv4 address (or an Elastic IP) for the IGW to map it to.

A server in a private subnet that must call out (download updates, call a payment API) uses a NAT gateway. You put the NAT gateway in a public subnet and point the private route table's 0.0.0.0/0 at it. It lets private instances start connections out, and "external services can't initiate a connection with those instances." A NAT gateway is zonal and billed per hour and per GB processed. If one NAT gateway serves all AZs and its AZ fails, the private subnets in the other AZs lose internet access too. So production setups use one NAT gateway per AZ.

The stateless part is the classic mistake. A client opens a connection from a random high port (an ephemeral port, for example 49152) to port 443. The reply goes back to port 49152. A NACL that allows only 443 drops the reply. NAT gateways use ports 1024 to 65535, so a NACL must allow that range for replies.

Referencing a security group is the cleaner design: "allow 5432 from app-sg" keeps working when app servers come and go and change their IPs.

Reaching AWS services privately, and other VPCs

  • Gateway endpoint (S3 and DynamoDB only): a route in your route table, from a prefix list of the service's addresses to the endpoint. "There is no additional charge for using gateway endpoints." Private instances then reach S3 without a NAT gateway and its per-GB charge.
  • Interface endpoint (AWS PrivateLink): a network interface with a private IP in your subnet, for most other services and for services of other companies. Traffic "stays within the AWS network".
  • VPC peering links two VPCs, also across accounts and Regions. It "does not support transitive peering": if A peers with B and B with C, A cannot reach C through B. Both sides must add routes.
  • Transit Gateway is a hub: many VPCs and on-premises networks attach to it, and it routes between them. You pay per attachment hour and per GB.

Every Region has a default VPC: 172.31.0.0/16, a public /20 subnet in each AZ and an internet gateway. It is handy for tests. For production, build your own VPC with private subnets.

5. IAM: who may do what

Covers: principals, root user, users and roles, policy JSON, identity vs resource policies, evaluation logic, SCPs and permission boundaries, AssumeRole and temporary credentials, instance profiles, ARNs, least privilege, Access Analyzer · Sources: IAM User Guide (how IAM works, identity vs resource-based policies, policy elements, policy evaluation logic, best practices, root user best practices, instance profiles, ARNs), STS API Reference (AssumeRole)

AWS Identity and Access Management (IAM) decides, for every API call, whether the caller may do this action on this resource. "By default, all requests are denied." A call goes through only if a policy allows it and no policy denies it.

Who calls: principals

  • The root user signs in with the account's email address and has full access. AWS says: do not use it for daily work, turn on MFA, and "do not create access keys for your root user".
  • An IAM user is a person or program with long-lived credentials: a password and up to two access keys. Long-lived keys leak (in git, in logs), so AWS prefers roles.
  • An IAM role has no password and no keys of its own. A trusted principal assumes it and gets temporary credentials from STS (Security Token Service). An EC2 instance, a Lambda function, an ECS task, a person who signed in through single sign-on, or another AWS account can assume a role.

What a policy looks like

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject"],
    "Resource": "arn:aws:s3:::acme-reports/*",
    "Condition": {"IpAddress": {"aws:SourceIp": "198.51.100.0/24"}}
  }]
}

Effect is Allow or Deny. Action is a service and an API name. Resource is an ARN (Amazon Resource Name, arn:partition:service:region:account-id:resource). Condition adds tests on the request, such as the source IP, a tag or MFA. Version must be 2012-10-17, the current policy language.

Policies attach in two places:

  • An identity-based policy is attached to a user, group or role. It says what that principal may do.
  • A resource-based policy is attached to a resource: an S3 bucket policy, an SQS queue policy, a KMS key policy, a role's trust policy. It has a Principal element that says who may use this resource.

How AWS decides

  1. Start from deny.
  2. If any policy has an explicit Deny that matches, the answer is deny. "An explicit deny in any policy overrides any allows in any policy."
  3. Guard rails must allow: Service Control Policies of AWS Organizations, permission boundaries and session policies. "If one or more of these policy types exists, they must all allow the request." They grant nothing by themselves. "No permissions are granted by SCPs."
  4. In the same account, identity policies and resource policies are a union: an allow in either one is enough.
  5. Across accounts, both sides must allow: "There must be policies in both accounts that allow the operation."

So "it says Allow, why is it denied?" usually has one of three answers: a Deny somewhere else, a guard rail that does not allow it, or a cross-account call where only one side allows.

Roles and temporary credentials

A role has two policies. The trust policy says who may assume it. The permissions policy says what the role may do. sts:AssumeRole returns an access key ID (starting with ASIA), a secret key and a session token. They last 3,600 seconds by default, from 900 seconds up to the role's maximum of 1 to 12 hours. When they expire, the caller assumes the role again. A leaked temporary key is useful to an attacker only until it expires.

This is how code on AWS gets credentials without any key in its config. An EC2 instance gets a role through an instance profile (one role per profile) and the SDK reads temporary keys from the instance metadata service. ECS tasks (task role), Lambda functions (execution role) and EKS pods (IRSA or Pod Identity) work the same way.

Least privilege means "grant only the permissions required to perform a task." IAM Access Analyzer helps: it finds resources shared outside your account and can build a policy from the calls a role really made.

6. S3: object storage

Covers: buckets, objects, keys and prefixes, consistency, durability, storage classes, lifecycle, versioning, Block Public Access, encryption, presigned URLs, request rates, multipart upload, conditional writes, event notifications · Sources: Amazon S3 User Guide (what is S3, objects overview, object keys, storage classes, lifecycle, versioning, Block Public Access, Object Ownership, default encryption FAQ, presigned URLs, performance, conditional writes, event notifications, upload objects, quick facts)

Amazon S3 (Simple Storage Service) stores objects: a file of bytes plus metadata, saved under a key in a bucket. You do not mount it like a disk. You PUT a whole object and GET a whole object (or a byte range) over HTTPS.

AWS describes S3 as "a basic data map between 'bucket + key + version' and the object itself". There are no real folders: "The Amazon S3 data model is a flat structure." A key like img/icons/cart.svg is one string. Tools show folders by splitting keys at /: a LIST call with prefix=img/ and delimiter=/ returns the keys directly under img/ and groups deeper keys as common prefixes. A key can be up to 1,024 bytes.

Bucket names are unique across all AWS accounts in a partition, because they appear in URLs such as acme-assets.s3.amazonaws.com. An object can be from zero bytes to 50 TB. One PUT can send up to 5 GB. Bigger objects use multipart upload: up to 10,000 parts of 5 MiB to 5 GiB, sent in any order and in parallel, then joined by a final call. AWS suggests multipart from about 100 MB.

Guarantees

  • Strong read-after-write consistency for PUT and DELETE "in all AWS Regions". After a PUT returns, every GET and LIST sees the new object. For two PUTs to the same key at the same time, "the request with the latest timestamp wins". There are no transactions across keys.
  • Durability: the storage classes are designed for 99.999999999% (11 nines). Except for the One Zone classes, S3 keeps the data in several AZs, so the loss of one AZ does not lose objects.
  • Scale per prefix: "at least 3,500 PUT/COPY/POST/DELETE or 5,500 GET/HEAD requests per second per partitioned Amazon S3 prefix", with no limit on the number of prefixes. While S3 adds capacity for a fast-growing load, you can see 503 Slow Down, so clients must retry with backoff.

Versioning

With versioning on, every PUT to a key makes a new version with its own version ID, and "each version of an object is the entire object", billed in full. A DELETE without a version ID does not remove data: "Amazon S3 inserts a delete marker". The marker becomes the latest version, so a normal GET returns 404, but older versions are still there. Delete the marker and the object is back. This protects against a bad script or an attacker who deletes objects. Once on, versioning "can never return to an unversioned state". You can only suspend it. Objects that existed before versioning have the version ID null.

Security defaults

  • "By default, new buckets, access points, and objects don't allow public access." Block Public Access is on at the bucket level.
  • ACLs are off by default ("Bucket owner enforced"). Access is set by IAM policies and bucket policies only.
  • "Starting January 5, 2023, all new object uploads to Amazon S3 are automatically encrypted" with SSE-S3, at no cost. You can choose SSE-KMS to control the key yourself (chapter 20).
  • A presigned URL lets someone without AWS credentials GET or PUT one object until it expires, up to 7 days with an IAM user's key through the CLI or SDK. It carries the signer's permissions and works as a bearer token: anyone who has the URL can use it. Use it for direct browser uploads and private downloads.

Conditional writes and events

If-None-Match: * on a PUT means "write only if no object has this key". If one exists, S3 answers 412 Precondition Failed. Two workers that both try to claim orders/1001.json cannot both win. If-Match: <ETag> writes only if the object did not change since you read it.

Event notifications send a message to SQS, SNS, Lambda or EventBridge when an object is created or deleted. They are "delivered at least once", so the handler must be safe to run twice. A Lambda that writes back into the same bucket and prefix can trigger itself in a loop.

7. Elastic Load Balancing: ALB and NLB

Covers: ALB, NLB, Gateway Load Balancer, listeners, rules, target groups, health checks, fail open, deregistration delay, cross-zone, routing algorithms, sticky sessions · Sources: Elastic Load Balancing User Guide, Application Load Balancer guide (introduction, load balancers, target groups, health checks, target group attributes), Network Load Balancer guide, Gateway Load Balancer guide

A load balancer is one stable address in front of many servers. It sends each request or connection to a healthy server, and it stops sending to a server that fails its health checks.

Without one, clients would need the address of each server, and a dead server would get requests until someone noticed. Elastic Load Balancing (ELB) runs load balancer nodes in each AZ you choose, and it "monitors the health of its registered targets, and routes traffic only to the healthy targets."

The parts of an ALB

  • A listener waits on a port and protocol, for example HTTPS 443 with a certificate.
  • Each listener has rules. "Each rule consists of a priority, one or more actions, and one or more conditions." The ALB checks rules from the lowest priority number up. The first match wins. The default rule catches the rest. Actions: forward to a target group, redirect (HTTP to HTTPS), or return a fixed response.
  • A target group is a set of targets of one type: instance, ip or lambda. Auto Scaling groups and ECS services register their targets in a target group by themselves.

Health checks

Each target group sends a health check request to each target on a schedule. ALB defaults for instance and IP targets: every 30 seconds, 5 second timeout, path /, success code 200. A target becomes unhealthy after 2 failed checks in a row and healthy again after 5 good ones. So with defaults, a dead target can get traffic for up to about 60 seconds before the ALB stops using it, and a recovered one waits about 150 seconds. Clients in that first window get errors (an ALB answers 502 when the target resets the connection). Shorter intervals find failures faster but add check traffic.

If every target in a group is unhealthy, the ALB "fails open": it "routes requests to all those targets, regardless of their health status." This saves you when the health check itself is wrong (for example it checks a database that is down) but the app could still answer.

When a target leaves (scale in, deploy), it goes into draining. The ALB sends it no new requests but lets requests in progress finish. The default deregistration delay is 300 seconds. Set it a little longer than your slowest request, or deploys take five minutes for no reason.

Other settings that come up

  • Cross-zone load balancing: on for ALB (it "cannot be changed at the load balancer level"), so each node spreads over targets in all AZs. Off by default for NLB.
  • Algorithm: round robin by default. Least outstanding requests sends to the target "with the lowest number of in progress requests", which helps when request times vary a lot.
  • Sticky sessions: a cookie (AWSALB or your app's cookie) pins a user to one target, for 1 second to 7 days. It makes the load uneven and loses the session when that target dies. Keeping sessions in a shared store (chapter 15) is better.
  • Idle timeout: 60 seconds by default. A connection with no data for that long is closed.
  • An ALB needs subnets in at least two AZs, each with at least a /27 and 8 free IPs, because its nodes grow as traffic grows.

8. EC2 Auto Scaling

Covers: Auto Scaling groups, min / desired / max, launch templates, health checks and replacement, grace period, scaling policies (target tracking, step, simple, scheduled, predictive), cooldown, instance warmup, termination policy, lifecycle hooks, instance refresh, warm pools · Sources: Amazon EC2 Auto Scaling User Guide (Auto Scaling groups, capacity limits, launch templates, health checks, health check grace period, dynamic scaling, scheduled scaling, predictive scaling, cooldowns, default instance warmup, termination policies, lifecycle hooks, instance refresh, warm pools)

An Auto Scaling group (ASG) keeps a chosen number of identical EC2 instances running. It replaces instances that fail, and with a scaling policy it changes the number to follow the load.

The group has three numbers. Desired capacity is how many instances it should have now. Min and max are the limits: "The desired capacity must be equal to or greater than the minimum group size, and equal to or less than the maximum group size." The group runs a loop: compare the instances it has with desired capacity, launch or terminate to close the gap, repeat. This loop is a reconcile loop, the same idea as an ECS service (chapter 9) and a Kubernetes Deployment (chapter 10).

New instances come from a launch template: AMI, instance type, key pair, security groups, user data. You give the group subnets in several AZs, and it keeps the AZs balanced: "Maintaining Zonal balance takes precedence over the termination policy."

Replacing failed instances

The group checks health. By default it uses EC2 status checks (is the VM running). Turn on the ELB health check type and it also replaces an instance that the load balancer marks unhealthy: "If any of the health checks fail, the instance is replaced." This is usually what you want, because an app can crash on a running VM. The health check grace period gives a new instance time to boot before checks count. It is 300 s by default in the console and 0 s by default from the CLI and SDK, so set it on purpose.

Scaling policies

  • Target tracking: you give a metric and a target, for example average CPU 50%. The group adds instances when the metric is above the target and removes them when it is below, like a thermostat. AWS recommends this one.
  • Step scaling: a CloudWatch alarm with steps: CPU over 60%, add 1; over 80%, add 3.
  • Simple scaling: one alarm, one change, then a cooldown (300 s by default). AWS says: "we recommend that you do not use simple scaling policies and scaling cooldowns."
  • Scheduled: set desired capacity at a time, for example 10 at 08:00 on weekdays.
  • Predictive: learns the daily and weekly pattern and scales out before the load arrives.

Boot time is the weak point. A new instance needs minutes to boot, install and warm its caches. While it boots, the others carry the load. Two settings help. Default instance warmup (off unless you set it) tells the group how long after InService to wait before it counts the new instance's metrics. Without it, a new instance that reports low CPU while it starts pulls the average down, and the group stops adding instances too early. A warm pool keeps pre-started instances stopped and ready, for apps with long boots, at extra cost.

Changing the instances

A lifecycle hook pauses an instance as it launches or terminates (one hour by default), so a script can register it somewhere or copy its logs out. An instance refresh replaces the instances step by step after you change the launch template, for example to roll out a new AMI.

9. Containers: ECS and Fargate

Covers: ECR, task definitions, tasks, services, clusters, capacity (EC2, Fargate, Managed Instances, ECS Anywhere), awsvpc networking, task role vs task execution role, rolling deployments · Sources: Amazon ECS Developer Guide (welcome, task definitions, clusters, services, launch types, ECS Anywhere, awsvpc networking, Fargate tasks, service definition parameters, rolling deployments, task execution role, task IAM roles), Amazon ECR User Guide

Amazon ECS (Elastic Container Service) runs Docker containers for you. You say which image to run, with how much CPU and memory, and how many copies. ECS places the containers on servers, restarts them when they stop, and registers them with a load balancer.

A container image packs your app with its libraries, so it runs the same on a laptop and in production. Running one container is easy. Running 40 of them on 10 servers, replacing the ones that crash, and rolling out a new version without downtime is the hard part. That is the job of an orchestrator. ECS is AWS's own. EKS (chapter 10) is Kubernetes.

The four objects

  • Image registry: you push images to Amazon ECR (Elastic Container Registry), or use another registry.
  • Task definition: "a blueprint for your application. It is a text file in JSON format that describes the parameters and one or more containers". It names the image, CPU and memory, ports, environment variables, log settings and IAM roles. Each change makes a new revision: web:1, web:2.
  • Task: one running copy of a task definition: one or more containers that start together on one host.
  • Service: keeps N tasks of a task definition running. "If one of your tasks fails or stops, the Amazon ECS service scheduler launches another instance of your task definition to replace it." It also registers tasks in a target group and does rolling deployments.

A cluster is "a logical grouping of tasks or services" plus the capacity they run on.

10. EKS: managed Kubernetes

Covers: Kubernetes control plane and nodes, pods, Deployments, scheduling, EKS control plane layout, node options, pricing, version support, pod IAM (IRSA, Pod Identity), ECS vs EKS · Sources: Amazon EKS User Guide (what is EKS, architecture, compute, managed node groups, Kubernetes versions, IAM roles for service accounts, Pod Identity), EKS best practices (control plane), aws.amazon.com/eks/pricing, kubernetes.io (Kubernetes components)

Amazon EKS (Elastic Kubernetes Service) runs the Kubernetes control plane for you. You get a standard Kubernetes API endpoint, and you run your pods on nodes that you choose: EC2 instances, Fargate, or nodes that EKS manages.

Kubernetes in one page

Kubernetes is an open source orchestrator, like ECS, but with its own API and a large tool ecosystem. It has two halves:

  • The control plane: the API server (every change goes through it), etcd (the key-value store that holds the whole cluster state), the scheduler (picks a node for each new pod) and the controller manager (runs reconcile loops).
  • The nodes: machines that run a kubelet, which starts the containers that the control plane assigns to it.

The unit is a pod: one or more containers that share a network address. You rarely create pods by hand. A Deployment says "keep 6 pods of this template", and a controller keeps that count, as an ECS service does. A Service gives a stable name and address for a set of pods. Each pod asks for CPU and memory (requests). The scheduler puts it only on a node with that much free. If no node has room, the pod stays Pending.

What EKS adds

Running the control plane yourself is hard: etcd must keep a quorum, be backed up, and be upgraded with care. In EKS, "AWS manages the Kubernetes control plane". It places "at least two API server instances and three etcd instances across three AWS Availability Zones", and "if a control plane instance falters, Amazon EKS quickly replaces it". You pay $0.10 per cluster per hour for standard support (pricing page, 2026-10-07).

Each Kubernetes minor version gets 14 months of standard support, then 12 months of extended support at $0.60 per cluster per hour. After that, "your cluster is auto-upgraded". So EKS clusters need a planned upgrade about once a year.

For nodes, you can mix "EKS Auto Mode managed nodes, self-managed nodes, Amazon EKS managed node groups, AWS Fargate, and Amazon EKS Hybrid Nodes". A managed node group is an EC2 Auto Scaling group that EKS creates and updates: "Every managed node is provisioned as part of an Amazon EC2 Auto Scaling group". To add nodes when pods are Pending, clusters run an autoscaler (Cluster Autoscaler or Karpenter) or use Auto Mode.

Pods get AWS permissions through a Kubernetes service account linked to an IAM role: IRSA (IAM roles for service accounts) or the newer EKS Pod Identity, where "each EKS Pod Identity association maps a role to a service account in a namespace".

11. Lambda: functions without servers

Covers: execution environment lifecycle, cold and warm starts, limits, concurrency, reserved and provisioned concurrency, sync and async invocation, event source mappings, SnapStart · Sources: AWS Lambda Developer Guide (execution environment lifecycle, concurrency, quotas, synchronous and asynchronous invocation, async error handling, event source mappings, SQS, ephemeral storage, SnapStart)

AWS Lambda runs a function (your code) when an event arrives: an HTTP request, a queue message, a new S3 object, a schedule. You do not manage servers. You pay per request and per millisecond of run time, and nothing when no event arrives.

The execution environment

Lambda runs your function in an execution environment: an isolated micro VM with your runtime (Python, Node.js, Java...) and your code. Its life has three phases:

  1. Init: "Start all extensions, Bootstrap the runtime, Run the function's static code". Static code is everything outside the handler: imports, database clients, config. The Init phase is limited to 10 seconds.
  2. Invoke: Lambda calls your handler with one event. One environment handles one event at a time.
  3. Shutdown: after a while with no events, Lambda removes the environment.

When an event finds no free environment, Lambda creates one and runs Init first. This is a cold start. AWS says cold starts "typically occur in under 1% of invocations" and take "from under 100 ms to over 1 second". After an invocation, the environment is kept for a while. "When the function is invoked again, Lambda thaws the environment for reuse": a warm start, with no Init.

Reuse has two sides. Good: a database connection or a loaded model made in Init is reused by later calls, so put expensive setup outside the handler. Bad: global variables keep their values between calls. A list that the handler appends to grows forever. A user ID kept in a global can leak into the next user's request. Treat globals as a cache, never as per-request state.

Concurrency

"Concurrency is the number of in-flight requests that your AWS Lambda function is handling at the same time." Each in-flight request needs its own environment. So concurrency is about requests per second × average duration in seconds. 500 requests per second that each take 200 ms need about 100 environments. Above the account limit, calls are throttled (HTTP 429 for synchronous calls).

  • Reserved concurrency sets the maximum for one function and holds that share for it. It protects a database from too many connections, and protects other functions from one busy function. Its environments are not pre-started.
  • Provisioned concurrency is "the number of pre-initialized execution environments": they have run Init already, so there is no cold start for that many requests. You pay for them while they wait.
  • SnapStart (Java 11+, Python 3.12+, .NET 8+) runs Init once when you publish a version and saves a snapshot of memory and disk, so new environments start from the snapshot.

How events arrive

  • Synchronous: the caller waits for the result (API Gateway, an ALB, a direct Invoke). Errors go back to the caller.
  • Asynchronous: Lambda puts the event in its own queue and returns at once (S3 events, SNS, EventBridge). On error, "Lambda attempts to run it two more times", one minute and then two minutes apart. After that the event goes to an on-failure destination or dead-letter queue if you set one, or is dropped.
  • Event source mapping: Lambda itself polls a queue or stream (SQS, Kinesis, DynamoDB Streams, Kafka) and "invokes your function synchronously with an event" that holds a batch of records.

13. RDS and Aurora: managed SQL databases

Covers: RDS engines and what AWS manages, automated backups and point-in-time restore, Multi-AZ DB instance, Multi-AZ DB cluster, read replicas, storage autoscaling, RDS Proxy, Aurora storage, Aurora replicas and endpoints, failover, Serverless v2, Global Database · Sources: Amazon RDS User Guide (welcome, backup retention, point-in-time recovery, Multi-AZ single standby, Multi-AZ failover, Multi-AZ DB clusters, read replicas, MySQL read replicas, storage autoscaling, RDS Proxy), Amazon Aurora User Guide (overview, storage and reliability, high availability, endpoints, limits, Serverless v2, Global Database), AWS Database Blog "Amazon Aurora under the hood: quorum and correlated failure"

Amazon RDS (Relational Database Service) runs a SQL database engine for you: PostgreSQL, MySQL, MariaDB, Oracle, SQL Server or Db2. "Amazon RDS manages backups, software patching, automatic failure detection, and recovery." You still design the schema and tune the queries. Amazon Aurora is AWS's own MySQL- and PostgreSQL-compatible engine with a different storage layer.

How a SQL engine works inside (pages, MVCC, the WAL, indexes) is in the SQL and PostgreSQL explainer, with real labs. This chapter is about what AWS builds around the engine.

Backups

Automated backups keep daily snapshots plus the transaction log for 0 to 35 days (0 turns them off). RDS "uploads transaction logs for DB instances to Amazon S3 every five minutes", so you can restore to any second up to the LatestRestorableTime, usually about five minutes ago. A point-in-time restore makes "a new DB instance without modifying the source". The app must then switch to the new endpoint.

High availability: Multi-AZ

A Multi-AZ DB instance has a "synchronous standby replica in a different Availability Zone". Each commit is written in both AZs before the app gets "OK", so no committed data is lost when the primary fails. The cost: "increased write and commit latency", and "You can't use a standby replica to serve read traffic." On failure, RDS "automatically changes the Domain Name System (DNS) record of the DB instance to point to the standby". "Failover times are typically 60–120 seconds." Apps must reconnect and must not cache the old IP (AWS advises a DNS TTL of 60 s or less in the JVM).

A Multi-AZ DB cluster has "a writer DB instance and two reader DB instances in three separate Availability Zones". A commit needs "acknowledgment from at least one reader", and the readers serve reads.

Scaling reads: read replicas

A read replica gets changes "asynchronously". The primary does not wait for it. So writes stay fast, but the replica lags: a user who writes and then reads from a replica can see the old value. Use replicas for reports and pages that may be a little old. RDS MySQL allows "up to 15 read replicas from one DB instance within the same Region". You can promote a replica to a standalone database, for example after a Region failure, but changes it had not received yet are lost.

Other RDS parts

  • Storage autoscaling grows the disk when free space is at or under 10% for 5 minutes. It never shrinks it.
  • RDS Proxy keeps a pool of database connections and shares them among many clients. It helps Lambda functions, which can open thousands of connections, and "automatically connecting to a standby DB instance while preserving application connections" on failover.

Aurora: the storage is the difference

In RDS, each instance has its own EBS disk and replication copies data from instance to instance. Aurora separates compute from storage. All instances of a cluster share one cluster volume. Aurora "synchronously replicates the data across Availability Zones to six storage nodes": two copies in each of three AZs. Per the AWS database blog, a write is done when 4 of the 6 copies confirm it, and a read needs 3. So Aurora can lose a whole AZ (2 copies) and still write, and lose 3 copies and still read. (These two numbers are derived from the 4-of-6 and 3-of-6 quorums.) The volume grows by itself, up to 128 TiB or 256 TiB depending on the engine version.

Because storage is shared, "you can add a DB instance quickly because Aurora doesn't make a new copy of the table data." A cluster has one writer and "up to 15 Aurora Replicas". The cluster endpoint always points to the writer. The reader endpoint balances connections over the replicas. Both "automatically change which DB instance they connect to" after a failover. On failure, a replica is promoted and "service is typically restored in less than 60 seconds, and often less than 30 seconds".

  • Aurora Serverless v2 scales compute in steps "as small as 0.5 ACUs" between a min and a max (0 to 256 ACUs). One ACU is about 2 GiB of memory with matching CPU.
  • Aurora Global Database copies a cluster to "up to 10 secondary DB clusters in different Regions" through the storage layer, "with latency typically under a second".

14. DynamoDB: key-value at any scale

Covers: tables, items, partition and sort keys, partitions and their limits, capacity units, read consistency, on-demand vs provisioned, GSI and LSI, Query vs Scan, conditional writes, transactions, TTL, Streams, DAX, global tables · Sources: Amazon DynamoDB Developer Guide (core components, constraints, partition key design, read consistency, capacity modes, read and write operations, GSI, LSI, Query and Scan best practices, condition expressions, transactions, TTL, DAX, global tables, service quotas)

Amazon DynamoDB is a key-value and document database. You read and write items by their key, and each call takes single-digit milliseconds whether the table holds a thousand items or a billion. There are no servers to size, no joins, and no SQL query planner.

Keys decide everything

A table holds items, and each item holds attributes. "Other than the primary key, the table is schemaless." The primary key is either:

  • a partition key alone (for example userId), or
  • a partition key plus a sort key (for example customer + orderId). "All items with the same partition key value are stored together, in sorted order by sort key value."

DynamoDB "uses the partition key's value as input to an internal hash function. The output from the hash function determines the partition". A partition is a slice of storage and throughput. "Every partition ... is designed to deliver a maximum capacity of 3,000 read units per second and 1,000 write units per second." So the table scales by spreading keys over many partitions, and one key can never use more than one partition's share. If most traffic hits one key (today's date, one famous user, the status pending), that partition throttles while the others sit idle. This is a hot partition. AWS's advice: "design your application for uniform activity across all partition keys". Adaptive capacity helps with uneven load, but not past one partition's limits.

Capacity units and consistency

"One read capacity unit = one strongly consistent read per second, or two eventually consistent reads per second, for items up to 4 KB." "One write capacity unit = one write per second, for items up to 1 KB." Sizes round up: reads to the next 4 KB, writes to the next 1 KB. Transactional reads and writes cost double.

"Eventually consistent is the default". It may miss a write from the last moment, and costs half. ConsistentRead=true gives a strongly consistent read, on tables and LSIs only, not on GSIs.

On-demand mode ("the default and recommended throughput option") bills per request. Provisioned mode bills for the capacity you set, used or not, and is cheaper for a steady, known load.

Reading: Query, Scan and indexes

  • GetItem: one item by its full key.
  • Query: all items with one partition key, optionally a sort key range (begins_with(orderId, '2026-10')). It reads only those items.
  • Scan: "always scans the entire table or secondary index". A filter removes items after they are read, and you pay for every item read, not for the items returned. Query and Scan return at most 1 MB per call; you page with LastEvaluatedKey.

To query by another attribute, add an index. A global secondary index (GSI) has its own partition and sort key, is updated "in an eventually consistent fashion", and has its own throughput: a GSI that is too slow throttles writes to the table. A local secondary index (LSI) keeps the table's partition key with another sort key, supports strong reads, and must be "created when the table is created". The default limits are 20 GSIs and 5 LSIs per table.

This is why DynamoDB design starts from the access patterns: list every question the app asks, then choose keys and indexes so each one is a GetItem or a Query.

Writing safely

  • A condition expression makes a write happen only if a test passes. attribute_not_exists(orderId) stops an overwrite; #s = :expected stops a lost update. On failure: "The conditional request failed", and the failed write still uses capacity.
  • Transactions group "up to 100 write actions in a single all-or-nothing operation", at twice the cost.
  • Items are at most 400 KB. Big blobs go to S3, with the S3 key in the item.

More features

  • TTL: an attribute with an expiry time. DynamoDB deletes expired items "within a few days", free. Filter them out of reads until then.
  • Streams: an ordered log of item changes with "before" and "after" images, kept 24 hours. Lambda can read it to update a search index or send events.
  • DAX: an in-memory cache in front of the table, for eventually consistent reads in microseconds.
  • Global tables: replicas in several Regions, any of which "can serve reads and writes", replicated "typically within a second", last writer wins.

15. ElastiCache: an in-memory cache

Covers: engines, serverless vs node-based, replication groups, cluster mode and hash slots, Multi-AZ failover, cache-aside (lazy loading), write-through, TTL, eviction · Sources: Amazon ElastiCache User Guide (what is ElastiCache, components, replication, auto failover, scaling cluster mode enabled, caching strategies, engine parameters), ElastiCache API Reference (NodeGroupConfiguration), AWS whitepaper "Database caching strategies using Redis"

Amazon ElastiCache runs an in-memory key-value store for you: Valkey, Redis OSS or Memcached. Apps keep hot data there, so they read it in under a millisecond instead of asking the database each time.

A cache does two jobs: it makes reads fast, and it takes load off the database. The price is that the cache holds a copy, and a copy can be out of date. Every cache design is a choice about when the copy is filled and when it is thrown away.

Shapes

  • Serverless: no nodes to choose, it "removes the need to plan and manage caching capacity".
  • Node-based: you pick node types. A Valkey or Redis OSS replication group has "2 to 6 nodes", one read/write primary and "1 to 5 read-only nodes". Replication is asynchronous, so "some data may be lost if it is the primary read/write node that fails."
  • Cluster mode splits data over up to 500 shards. Keys map to 16,384 hash slots (0 to 16,383), and each shard owns a range of slots. Resharding moves slots while the cluster "continues to serve requests".
  • Multi-AZ with automatic failover: "ElastiCache automatically promotes the replica with the least replication lag to primary", which "usually takes just a few seconds". Without a replica, "the new primary starts empty".
  • Memcached has no replication. It only spreads keys over nodes. A lost node loses its keys.

Two ways to fill a cache

Cache-aside (AWS calls it lazy loading): the app reads the cache first. On a miss, it reads the database and writes the value into the cache. Only data someone asked for is cached, and "node failures aren't fatal": a new empty node fills up again. The costs: "Each cache miss results in three trips" (cache, database, cache), and data goes stale when the database changes, because nothing updates the cache.

Write-through: every database write also writes the cache. Cached data is never stale. The costs: every write is slower, the cache fills with data nobody reads, and a new node has nothing until data is written again.

AWS's advice is to add a TTL (time to live) to every key in both: "By adding a time to live (TTL) value to each write, you can have the advantages of each strategy." The TTL is the longest time a stale value can live. Many apps also delete the key when they update the database, so the next read loads the new value.

When memory is full, the engine evicts keys by the maxmemory-policy parameter (the ElastiCache parameter table lists volatile-lru as the default: remove the least recently used key among keys that have a TTL).

16. SQS: queues

Covers: standard and FIFO queues, at-least-once delivery, idempotent consumers, visibility timeout, retention, message size, short and long polling, dead-letter queues, delay queues, in-flight limits · Sources: Amazon SQS Developer Guide (queue types, standard queues, message quotas, queue quotas, visibility timeout, short and long polling, dead-letter queues, delay queues)

Amazon SQS (Simple Queue Service) is a message queue. A producer sends a message, SQS stores it, and a consumer receives it later and deletes it when the work is done. The producer does not wait for the consumer, and it does not need the consumer to be up.

A queue between two services absorbs spikes (1,000 orders arrive in one second, workers take them at their own speed), survives consumer crashes (messages wait), and lets you add workers to drain a backlog. The backlog is unlimited: "The number of messages that an Amazon SQS queue can store is unlimited."

Receive does not remove

This is the core of SQS. ReceiveMessage hands a message to a consumer and hides it for the visibility timeout (default 30 s, up to 12 hours). The message is now in flight. The consumer does its work and calls DeleteMessage with the receipt handle. "If you don't delete it before the timeout expires, the message becomes visible again in the queue and can be retrieved by another consumer."

So a consumer that crashes halfway loses nothing: the message comes back. But a consumer that is only slow also makes the message come back, and a second consumer then does the same work. Set the visibility timeout longer than the slowest normal processing time, or extend it with ChangeMessageVisibility during long work.

With a standard queue, write consumers to be idempotent: processing the same message twice must have the same effect as once. For example, store the order ID with a unique constraint, or use a DynamoDB conditional write (chapter 14), and skip IDs you already did.

Numbers and settings

  • Message size: 1 byte to 1 MiB (1,048,576 bytes). Bigger payloads go to S3, with a pointer in the message.
  • Retention: 4 days by default, 60 s to 14 days. Then the message is deleted, processed or not.
  • Long polling: WaitTimeSeconds up to 20 s. The call waits until a message arrives, instead of returning empty at once. It means fewer empty responses and lower cost. Short polling is the default.
  • Dead-letter queue (DLQ): after maxReceiveCount receives without a delete, SQS moves the message to the DLQ. A poison message (one that always crashes the consumer) then stops blocking the queue, and you can look at it. Set the DLQ retention longer than the source queue's.
  • Delay queue: hides new messages for 0 to 15 minutes after send. (The visibility timeout hides a message after it is received.)
  • About 120,000 messages can be in flight per standard queue. Above that, receives return nothing (long polling) or an OverLimit error (short polling).

17. SNS, EventBridge and Kinesis: fan-out and events

SQS is one queue for one kind of consumer. When one event must reach many consumers, you need publish/subscribe: the producer publishes once, and the system delivers a copy to every subscriber. On AWS that is SNS (topics), EventBridge (event buses with routing rules), or Kinesis (a replayable stream).

SNS: topics

"Publishers communicate asynchronously with subscribers by sending messages to a topic". Subscribers can be SQS queues, Lambda functions, HTTP(S) endpoints, email, SMS and mobile push. A message "is replicated and pushed to multiple endpoints".

The common pattern is SNS + SQS fan-out: one topic, one SQS queue per consumer service. The topic pushes at once. Each queue holds its copy until its service is ready, so a slow or broken service does not lose messages or slow the others.

"By default, an Amazon SNS topic subscriber receives every message". A filter policy on a subscription selects messages by attributes or body. Example: the billing queue only wants type = paid. Raw message delivery sends the original body; without it, the SQS message wraps the original in a JSON envelope with Type, MessageId, TopicArn and Message.

Delivery to SQS and Lambda is retried 100,015 times over 23 days. For HTTP(S), only 5xx and 429 answers are retried, by a policy you can tune. When retries end, the message is dropped "unless a dead-letter queue is attached to the subscription". FIFO topics keep strict order and deduplicate, paired with FIFO queues.

EventBridge: a router with rules

An event bus "receives events and delivers them to zero or more destinations". AWS services send events to the default bus (for example every EC2 state change). Your apps send to custom buses. A rule has an event pattern, a JSON template that matches fields of the event, and up to 5 targets. "An event might match multiple rules". So EventBridge routes by content: "OrderPlaced events from acme.shop where country is DE or FR go to the EU audit queue".

  • Failed deliveries are retried "for 24 hours and up to 185 times with an exponential back off and jitter", then sent to a DLQ (a standard SQS queue) if you set one.
  • Archive and replay keeps events and sends them to the bus again, for example after a bug fix.
  • The schema registry stores the shape of events and can generate code.
  • EventBridge Scheduler runs cron, rate and one-time schedules against hundreds of AWS APIs.
  • Pipes connect one source to one target ("point-to-point") with filtering and enrichment in between.

Kinesis Data Streams: an ordered log

A stream "is a set of shards". The partition key of each record is hashed (MD5) to pick a shard, and records with the same key stay in order. Each shard takes up to 1 MB/s or 1,000 records/s of writes and 2 MB/s of reads. Records stay for 24 hours by default, up to 365 days, whether or not anyone read them. Each consumer keeps its own position, so many consumers read the same data independently and can go back to replay it. One hot partition key throttles even in on-demand mode.

18. CloudFront: the AWS CDN

Covers: edge locations and regional edge caches, distributions, origins, cache behaviors, cache key and cache policies, TTLs, Origin Access Control, invalidations, CloudFront Functions and Lambda@Edge, Origin Shield, signed URLs, WAF and Shield · Sources: Amazon CloudFront Developer Guide (introduction, how CloudFront works, cache behavior settings, cache key, expiration, restricting access to S3, paying for invalidation, invalidation, choosing edge functions, Origin Shield, private content, AWS WAF), aws.amazon.com/cloudfront/features, aws.amazon.com/shield/features

Amazon CloudFront is AWS's content delivery network (CDN). It keeps copies of your responses in data centers near users, so most requests are answered nearby and never reach your servers.

How a CDN works in general (round trips, cache keys, revalidation, connection pools) is in the CDN explainer, with a real nginx edge cache to experiment on. This chapter covers the CloudFront pieces you configure.

Where the copies live

CloudFront "delivers your content through a worldwide network of data centers called edge locations". On 2026-10-07 the CloudFront features page listed "750+ POPs in 100+ cities across 50+ countries", plus 1,140+ embedded POPs inside internet providers' networks. Between the POPs and your origin sit 15 regional edge caches, which "have a larger cache than an individual POP", so an object that dropped out of a POP may still be one hop away. Dynamic requests and methods such as POST and PUT "go directly to the origin from the POPs".

A distribution

You create a distribution. "CloudFront assigns a domain name to your new distribution" (for example d111111abcdef8.cloudfront.net); you add your own domain with a certificate and a Route 53 alias record (chapter 19).

  • Origins: where CloudFront fetches on a miss. An S3 bucket, an ALB, an API Gateway, or any HTTP server.
  • Cache behaviors: path patterns such as /static/* or /api/*, each with one origin and its own cache settings. "The first match determines which cache behavior is applied to that request." The default behavior (*) "is always the last to be processed". The order of the others is up to you, so a wrong order sends requests to the wrong rules.
  • Cache policy: what goes into the cache key (the URL path plus chosen headers, cookies and query strings) and the TTLs. "Including fewer values in the cache key increases the likelihood of a cache hit." Put a value in the key only if the response really changes with it.

TTLs: if the origin sends no Cache-Control, the default TTL is 86,400 seconds (one day). The maximum TTL is one year by default. With Cache-Control: max-age, CloudFront caches "the lesser of" max-age and the maximum TTL.

Private origins and removing content

  • Origin Access Control (OAC) keeps an S3 bucket private and lets only your distribution read it: the bucket policy allows the CloudFront service principal for that one distribution. Users cannot go around the CDN to the bucket.
  • Invalidations remove objects from the edges before their TTL ends. "The first 1,000 invalidation paths that you submit per month are free", and a * path counts as one. AWS recommends versioned file names (app.3f9a.js) for files that change often: a new name is a new key, with no invalidation and no stale copies.
  • Signed URLs and signed cookies limit private content to users who got a signature from your app.

Code at the edge, and protection

CloudFront Functions are small JavaScript functions on viewer request and viewer response, at "up to millions of requests per second", with no network access: header rewrites, redirects, simple auth. Lambda@Edge runs Node.js or Python, up to 10,000 requests per second per Region, for longer work and network calls. Origin Shield is an extra cache layer in one Region in front of the origin, so a miss from many POPs becomes "as few as one request going to your origin". AWS Shield Standard (layer 3 and 4 DDoS protection) is on for everyone at no extra charge; AWS WAF adds layer 7 rules. Data from AWS origins to CloudFront is free.

19. Route 53: DNS

Covers: hosted zones, alias records vs CNAME, routing policies, health checks and DNS failover, TTL, domain registration, SLA · Sources: Amazon Route 53 Developer Guide (hosted zones, choosing alias or non-alias records, routing policies, DNS failover, how health checks work, record values, registering domains, working with records), aws.amazon.com/route53/sla

Amazon Route 53 is AWS's DNS service. It answers DNS queries for your domains, can register domains, and can change its answers based on health checks, location and weights.

How DNS works in general (resolvers, root and TLD servers, caching, record types) is in the DNS explainer, with real dig labs. Here are the Route 53 parts.

Zones and records

"A hosted zone is a container for records." A public hosted zone answers on the internet. A private hosted zone answers only inside the VPCs you link to it, for internal names like db.internal.acmeshop.com.

An alias record is a Route 53 feature, not a DNS standard. It points a name at an AWS resource (a load balancer, a CloudFront distribution, an S3 website, another record), and Route 53 answers with that resource's current IPs. It solves two problems. First, "You can't create a CNAME record for example.com, but you can create an alias record for example.com": the zone apex (the bare domain) cannot be a CNAME in DNS. Second, an ALB's IPs change as it scales, and an alias follows them: "Route 53 detects changes in the resource on its own." Alias queries to AWS resources are free; CNAME queries are charged.

Health checks and TTL

Route 53 health checkers in many places test your endpoint every 10 or 30 seconds. For HTTP, the endpoint must connect within 4 seconds and answer 2xx or 3xx "within two seconds after connecting". "If more than 18% of health checkers report that an endpoint is healthy, Route 53 considers it healthy." A health check can also follow a CloudWatch alarm or other health checks. Records with an unhealthy check are left out of answers.

Then the TTL matters: it is "the amount of time, in seconds, that you want DNS recursive resolvers to cache information about this record". Route 53 changes its answer at once, but resolvers keep the old answer until their copy expires. So DNS failover takes about detection time plus the TTL, and some clients cache longer than they should. Use short TTLs (60 s) on records you may need to fail over. For alias records to AWS resources, you cannot set the TTL; Route 53 uses the resource's default. AWS suggests a short TTL such as 300 s before you change a live record, and a longer one after it works.

Registering a domain in Route 53 also "automatically creates a hosted zone for the domain". The first service credit tier of the Route 53 SLA is monthly uptime "Less than 100% but ≥99.99%".

20. KMS and Secrets Manager

Covers: KMS key types, HSMs, envelope encryption and data keys, the 4 KB Encrypt limit, encryption context, key policies, rotation, deletion; Secrets Manager versions and rotation; Parameter Store · Sources: AWS KMS Developer Guide (concepts, cryptography essentials, key policies, rotating keys, deleting keys), AWS KMS API Reference (Encrypt, GenerateDataKey, EnableKeyRotation), AWS Secrets Manager User Guide (what's in a secret, rotation, rotation with Lambda), aws.amazon.com/secrets-manager/pricing, AWS Systems Manager User Guide (Parameter Store tiers)

AWS KMS (Key Management Service) keeps encryption keys in hardware that you can use but never read. AWS Secrets Manager stores secrets such as database passwords, encrypts them with KMS, keeps versions, and can change them on a schedule.

KMS keys

A KMS key's key material "never leave[s] the AWS KMS FIPS 140-3 Security Level 3 validated hardware security modules unencrypted". "To use a KMS key, you must call AWS KMS." So you never hold the key: you send data to KMS and get the result. Every call goes through IAM and is logged in CloudTrail, which gives you an audit of each use.

  • Customer managed keys: you create them and control the key policy and rotation. Monthly fee plus per-call fee.
  • AWS managed keys (aws/s3, aws/rds): created by a service in your account, "no monthly fee", you cannot change them.
  • AWS owned keys: kept in an AWS account, used for default encryption, free.

Every KMS key "must have exactly one key policy", and "without permission from the key policy, IAM policies that allow permissions have no effect". This is unusual: for most services an IAM allow is enough, but for KMS the key policy must also let IAM decide. Key policies are per Region.

Envelope encryption

Encrypt takes "plaintext of up to 4,096 bytes". That is enough for a password, not for a file. And sending gigabytes to KMS would be slow. So AWS uses envelope encryption: "encrypting plaintext data with a data key, and then encrypting the data key under another key."

  1. Call GenerateDataKey. KMS returns "a plaintext copy of the data key and a copy that is encrypted under" your KMS key.
  2. Encrypt your data locally with the plaintext data key (AES-256), then "erase the plaintext data key from memory".
  3. Store the encrypted data key next to the encrypted data. That is safe: only KMS can decrypt it.
  4. To read: send the encrypted data key to KMS Decrypt, get the plaintext data key, decrypt the data locally.

S3 with SSE-KMS, EBS and RDS encryption all work this way inside. A bonus: to rotate, "you can re-encrypt only the data keys", not the data.

An encryption context is a set of key-value pairs bound to the ciphertext. Decrypt needs "the same encryption context (a case-sensitive exact match)". It stops someone from moving a ciphertext from one record to another.

Rotation and deletion

Automatic rotation makes new key material once a year by default (configurable from 90 to 2,560 days). The key ID stays the same and old ciphertext still decrypts: "Key rotation has no effect on the data that the KMS key protects." Deleting a key needs a waiting period of 7 to 30 days (default 30), because deletion "is destructive": everything encrypted under it becomes unreadable. AWS suggests to "consider disabling the KMS key instead".

Secrets Manager and Parameter Store

A secret has versions, tracked by labels: AWSCURRENT, AWSPREVIOUS and, during rotation, AWSPENDING. "A secret always has a version labeled AWSCURRENT", and that is what a read returns by default. Rotation "update[s] the credentials in both the secret and the database or service", usually with a Lambda function called four times with the steps create_secret, set_secret, test_secret, finish_secret. Apps that read the secret at start or cache it briefly pick up the new password without a deploy.

SSM Parameter Store also stores config and encrypted strings. Standard parameters are free, up to 4 KB, with no built-in rotation. Many teams keep plain config in Parameter Store and credentials that must rotate in Secrets Manager.

21. CloudWatch and CloudTrail: watching the system

Covers: metrics, namespaces, dimensions, resolution and retention, EC2 basic and detailed monitoring, alarms and their states, Logs (groups, streams, retention, metric filters, Logs Insights), CloudTrail management and data events, event history, X-Ray · Sources: Amazon CloudWatch User Guide (concepts, alarm evaluation), CloudWatch Logs User Guide (concepts, Logs Insights), AWS CloudTrail User Guide (concepts), AWS X-Ray Developer Guide

Amazon CloudWatch collects numbers (metrics) and text (logs) from your resources and apps, and raises alarms when a number crosses a line. AWS CloudTrail records who called which AWS API, when, and from where.

Metrics

"A metric represents a time-ordered set of data points". It is named by a namespace (AWS/EC2, or your own such as Shop), a name (CPUUtilization), and dimensions (InstanceId=i-123). "CloudWatch treats each unique combination of dimensions as a separate metric", so a dimension with many values (a user ID) makes many metrics, each billed.

Standard resolution is one data point per minute; high resolution is one per second. EC2 sends metrics every 5 minutes by default (basic monitoring) or every minute with detailed monitoring. Old data is kept in coarser form: 1-minute points for 15 days, 5-minute points for 63 days, 1-hour points for 455 days. EC2 does not report memory or disk use inside the OS by itself; the CloudWatch agent sends those.

Alarms

An alarm watches one metric (or a math expression) with a statistic (Average, Maximum, p99...), a period, a threshold, the number of evaluation periods, and "Datapoints to Alarm": how many of those periods must breach. It is in one of three states:

  • OK: inside the threshold.
  • ALARM: "outside of the defined threshold".
  • INSUFFICIENT_DATA: "The alarm has just started, the metric is not available, or not enough data is available".

"Alarms invoke actions for sustained state changes only": an SNS notification, an Auto Scaling policy, an EC2 action. Two traps: an alarm on a metric that stops arriving (the app died) goes to INSUFFICIENT_DATA, not ALARM, unless you set how missing data is treated. And a 1-period alarm on a noisy metric pages people for nothing; use "3 of 5" style settings.

Logs

"A log stream is a sequence of log events that share the same source", for example one container. A log group holds streams that "share the same retention, monitoring, and access control settings". Retention is set per group, and "expired log events get deleted automatically". Metric filters turn log lines into metrics (count of ERROR lines per minute). Logs Insights runs queries over log groups, billed by the data scanned.

CloudTrail

"An event in CloudTrail is the record of an activity in an AWS account": who (the principal and its access key), what (the API), when, from which IP, and the result. "By default, trails and event data stores log management events, but not data or Insights events." Management events are control plane calls such as RunInstances or PutBucketPolicy. Data events (S3 GetObject, Lambda Invoke) are many more and must be turned on per resource type. Event history shows "the past 90 days of CloudTrail management events" in each Region, free. A trail stores events in an S3 bucket for longer. CloudTrail answers "who deleted this?" and is the first place to look in a security incident.

AWS X-Ray collects traces: one request's path through the load balancer, services, database calls and queues, with time spent in each, drawn as a "trace map".
