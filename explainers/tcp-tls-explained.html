1. Two connections, not one

Covers: notes part 1 §1, §4, "one thing I would change"; part 2 §33, §34 · Sources: Cloudflare docs (TCP connections, page updated 2026-04-20); Cloudflare docs (SSL/TLS modes); AWS Global Accelerator docs (How it works); RFC 7239 (Forwarded header)

A CDN is a network of reverse proxies. A reverse proxy is a server that takes the user's request, reads it, and sends its own request to the real server (the origin). So a browser that uses a CDN does not have one connection to the origin. It has a connection to the CDN edge, and the edge has a separate connection to the origin.

Cloudflare's docs draw it as Visitor ↔ Cloudflare ↔ Origin, with one connection on each side. They say Cloudflare acts "as an intermediary between the user and the origin" and "will open a connection to the origin server" when it cannot answer from its own data centers. AWS Global Accelerator says the same in plain words: it "terminates TCP connections from clients at AWS edge locations and, almost concurrently, establishes a new TCP connection with your endpoints".

Because the two connections are separate, each one has its own:

  • Addresses and ports. The origin sees the edge's IP address, not the user's. The CDN passes the user's address in a header, such as Forwarded (RFC 7239) or X-Forwarded-For.
  • Handshakes. The user's TCP and TLS handshakes happen over the short distance to the edge. The edge's connection to the origin is usually already open.
  • Protocol. The browser can use HTTP/3 to the edge while the edge uses HTTP/2 or HTTP/1.1 to the origin.
  • Encryption. TLS ends at the edge. The edge decrypts the request, so it can read the URL and cookies, check its cache and apply security rules. To protect the second leg, the edge must start a new TLS session to the origin.

This gives a better mental model than "a CDN is a cache near users". A CDN is a distributed reverse proxy that also caches, filters attacks, manages connections, and routes traffic over its own network. The rest of this explainer takes each part in turn, starting at the bottom: what a connection costs.

2. TCP: the three-way handshake

Covers: notes part 2 §1 · Sources: RFC 9293 §3.3.2 (states), §3.4.1 (ISN, socket pair), §3.5 (three-way handshake); RFC 6298 §2.1, §5.5 (RTO 1 s, back off); Linux ip-sysctl docs (tcp_syn_retries, tcp_syn_linear_timeouts)

TCP is the protocol that gives two programs a reliable, ordered byte stream over the Internet. Before any data flows, the two sides do a three-way handshake: SYN, SYN-ACK, ACK. It costs one round trip (RTT) before the client can send its request.

Each side picks an initial sequence number (ISN). Every byte it sends later is numbered from there, so the other side can put bytes in order and ask again for missing ones. RFC 9293 says the ISN is a fresh 32-bit number for each connection, because "There are security issues that result if an off-path attacker is able to predict or guess ISN values". The handshake is how each side tells the other its ISN and gets proof that the other side heard it:

  1. SYN: the client sends its ISN (seq=x). The client is now in state SYN-SENT.
  2. SYN-ACK: the server sends its own ISN (seq=y) and acknowledges the client's (ack=x+1). The server is in SYN-RECEIVED.
  3. ACK: the client acknowledges the server's ISN (ack=y+1). Both are ESTABLISHED. The client can put its first request bytes right behind this ACK.

RFC 9293 gives the main reason for three messages: "to prevent old duplicate connection initiations from causing confusion". A connection is identified by its socket pair: local IP and port, remote IP and port (often called the 4-tuple). Keep that in mind for chapter 11.

What it costs

The cost is time, not bytes. With a 120 ms round trip (an example for Karachi to Frankfurt), the client waits 120 ms before its request can leave. With a 15 ms round trip to a nearby edge, it waits 15 ms. That is the first reason to end the connection close to the user.

When a handshake packet is lost

No data has been sent yet, so TCP has no measured RTT. It uses a timer. RFC 6298: the sender "SHOULD set RTO <- 1 second", and doubles it after each timeout. Linux differs a little. It keeps the first 4 retries at 1 s (tcp_syn_linear_timeouts = 4), then doubles, and gives up after 6 retries (tcp_syn_retries, "131seconds" until the final timeout). So one lost SYN adds about 1 s to the page. That is long compared with a 20 ms handshake.

3. TLS 1.3: the second handshake

Covers: notes part 2 §2 · Sources: RFC 8446 §1 (three properties), §2 Figure 1 (message flow, {} and [] marks), §2.1 and §4.1.4 (HelloRetryRequest), §4.4.2 (server_name); RFC 8744 §2 (SNI in cleartext); Cloudflare blog "RFC 8446 aka TLS 1.3" (TLS 1.2 two round trips); curl man page (time_connect, time_appconnect)

TLS is the protocol that makes a TCP connection secure. HTTPS is HTTP inside TLS. After the TCP handshake, client and server do a TLS handshake. In TLS 1.3 it takes one more round trip. TLS 1.2 took two.

RFC 8446 lists what TLS gives:

  • Authentication: "The server side of the channel is always authenticated". The client gets proof it talks to the real shop.acmeshop.com.
  • Confidentiality: data "is only visible to the endpoints".
  • Integrity: data "cannot be modified by attackers without detection".

How one round trip is enough

The client guesses which key exchange the server will accept (today usually X25519, or X25519 combined with the post-quantum ML-KEM). It puts its public key share in the very first message, the ClientHello. The server answers with its own key share in the ServerHello. Now both sides can compute the same secret, and derive keys from it. Everything after the ServerHello is encrypted: the server's certificate, its signature that proves it owns the certificate's key, and its Finished message. The client checks all of it, sends its own Finished, and sends the HTTP request in the same flight.

TLS 1.2 first agreed on the algorithms and only then exchanged keys, so it needed two round trips. Cloudflare's TLS 1.3 post: latency can "drop from two round-trips to only one round-trip".

What the certificate check covers

The client checks that the certificate names the host it asked for, that it chains up to a certificate authority the client trusts, that it is within its dates, and that the CertificateVerify signature is valid. If one check fails, the client stops with an alert. No request is sent.

What a watcher on the path still sees

The ClientHello is not encrypted. It carries the server_name (SNI) extension, so the server can pick the right certificate. RFC 8744: "The SNI extension is carried in cleartext". In TLS 1.3 the certificate is hidden, because "All handshake messages after the ServerHello are now encrypted" (RFC 8446 §1.2). In TLS 1.2 the certificate went in the clear.

When the guess is wrong

If the server does not support the group of the client's key share, it sends a HelloRetryRequest naming a group it does support. The client sends a second ClientHello. That costs one more round trip (RFC 8446 §4.1.4).

4. Resumption and 0-RTT

Covers: notes part 2 §2 (resumed connections, 0-RTT and replay) · Sources: RFC 8446 §2.2 (PSK, NewSessionTicket, no Certificate), §2.3 and §8 (0-RTT, replay), §4.6.1; RFC 8470 (425 Too Early); nginx docs (ssl_early_data, $ssl_early_data); OpenSSL docs (SSL_read_early_data, replay protection)

A client that connected to a server before can skip most of the TLS handshake. After a full handshake, the server gives the client a session ticket. Next time, the client shows the ticket and both sides reuse the secret. With 0-RTT, the client also sends its request in the very first flight.

Resumption

RFC 8446 §2.2: after the handshake, "the server can send the client a PSK identity that corresponds to a unique key derived from the initial handshake". PSK means pre-shared key. The message is NewSessionTicket. On the next connection the client puts the ticket in its ClientHello. "As the server is authenticating via a PSK, it does not send a Certificate or a CertificateVerify message." That saves bytes and the signature work, but it is still one round trip.

0-RTT early data

With the ticket, the client can encrypt a request right away and send it next to the ClientHello. The server can answer before the handshake finishes. The cost is security. RFC 8446 §2.3: this data "is not forward secret" and "There are no guarantees of non-replay between connections." Anyone who copies the packets can send them again, and the server may run the request again.

The defences:

  • Single-use tickets: the server records which tickets it has seen and rejects early data on a second use. OpenSSL does this by default, but only with its server session cache. nginx turns it off: "OpenSSL built-in replay protection is disabled, because it interferes with session resumption."
  • Only safe requests: send early data only for requests that are safe to run twice, such as GET. nginx sets $ssl_early_data to 1 for such requests, so the app can refuse them. HTTP has a status for that: 425 Too Early (RFC 8470).

5. Keep-alive: pay the handshakes once

Covers: notes part 1 §2; part 2 §3, §4 · Sources: RFC 9112 §9.3 (persistent connections), §9.6 (Connection: close); RFC 9293 §3.3.2, §3.4.2, §3.6.1 (TIME-WAIT, 2 MSL); Linux include/net/tcp.h (TCP_TIMEWAIT_LEN 60 s); curl man page (num_connects)

A persistent connection (keep-alive) is a connection that stays open after a response, so the next request can use it. It pays the TCP and TLS handshakes once instead of once per request.

RFC 9112 §9.3: "HTTP/1.1 defaults to the use of "persistent connections", allowing multiple requests and responses to be carried over a single connection." Either side can end it. Connection: close "is defined as a signal that the sender will close this connection after completion of the response".

A page with 6 files over TLS 1.3 at 120 ms RTT shows the difference. With a new connection per file, each file costs TCP (1 RTT) + TLS (1 RTT) + request (1 RTT) = 360 ms. With keep-alive, only the first does. The other five cost 120 ms each.

The cost after close: TIME-WAIT

Closing has a cost too. The side that closes first keeps the socket in TIME-WAIT. RFC 9293 §3.6.1: it "MUST linger in the TIME-WAIT state for a time 2xMSL". This makes sure late packets from the old connection do not land in a new one that reuses the same ports. The RFC takes MSL as 2 minutes. Linux uses a fixed 60 s. While a socket waits, its local port stays taken. A client that opens and closes thousands of connections to one server can run out of ports. Keep-alive avoids that, because there are few closes.

Keep-alive and a connection pool are different things

Keep-alive is a property of one connection: do not close after the response. A connection pool is a manager that holds many kept-alive connections to one destination, hands an idle one to each new request, opens more when all are busy, and closes extras. A CDN edge has a pool per origin. Chapter 6 is about the pool.

6. Pools: many users, few origin connections

Covers: notes part 1 §2, §4; part 2 §4, §5, §9, §28 · Sources: Little's law (L = λW, J. D. C. Little, 1961); RFC 9113 §6.5.2 (SETTINGS_MAX_CONCURRENT_STREAMS, at least 100 recommended); Cloudflare docs (HTTP/2 to origin); AWS CloudFront docs (persistent connections with origin servers, HTTP/1.1 to custom origins); nginx docs (upstream keepalive)

The edge keeps a connection pool for each origin: a set of open, kept-alive connections. A request that must go to the origin takes an idle one, so it pays no handshake. The number of origin connections then depends on how many requests are in flight to the origin, not on how many users are online.

The two counts are not related. 10,000 users can each hold a connection to the edge, and the edge can still need only 20 to the origin. Three things cut the number down:

  1. Most user connections are idle. A user reads the page between clicks. Their connection sends nothing most of the time.
  2. Hits need no origin connection. Only misses and requests that cannot be cached (POST, private pages) go on.
  3. Each origin request holds a connection only while it is in flight. Little's law gives the count: requests in flight = arrival rate × time each request takes. 200 requests per second at 50 ms each is 10 in flight.

On HTTP/1.1, one connection carries one request at a time, so 10 in flight needs 10 connections. On HTTP/2, one connection carries many requests at once as streams, up to the server's SETTINGS_MAX_CONCURRENT_STREAMS (RFC 9113 recommends at least 100). So 10 in flight fits on one connection.

This protects the origin from connection overload: fewer sockets, much less TLS handshake work, and no handshake delay on each request. CloudFront "keeps persistent connections with origin servers so objects are fetched from the origins as quickly as possible". The CDN explainer has a real nginx pool to try: CDNs, chapter 9.

Pools on every hop

The same idea repeats on each hop. The edge pools connections to a regional tier, the regional tier to an origin shield, the shield to the origin's load balancer, and the load balancer to the app servers. Each hop is its own connection with its own pool. None of them stretches end to end.

Where it goes wrong

Little's law works in both directions. If the origin slows down, each request holds its connection longer, so more are in flight at once. On HTTP/1.1 the edge then opens more connections. A slow origin gets more connections exactly when it can handle fewer. Origin limits, timeouts and HTTP/2 to the origin keep this in check.

7. HTTP/1.1: one response at a time

Covers: notes part 1 §3; part 2 §6 · Sources: RFC 9112 §9.3 (persistent), §9.3.2 (pipelining, responses in order), §9.4 (no fixed connection limit, head-of-line blocking); RFC 9113 §1; MDN "Connection management in HTTP/1.x" (6 parallel connections)

An HTTP/1.1 connection carries one response at a time, in order. If a large or slow response is first, every request behind it on that connection waits. This is head-of-line blocking at the HTTP level.

HTTP/1.1 has pipelining: the client may send several requests without waiting. But the server "MUST send the corresponding responses in the same order that the requests were received" (RFC 9112 §9.3.2). The bytes of one response are not marked with which request they belong to, so they cannot mix. A slow first response still blocks the rest. Browsers turned pipelining off.

The fix browsers used was more connections. RFC 9112 §9.4: "Multiple connections are typically used to avoid the "head-of-line blocking" problem". The RFC gives no number, but MDN says browsers commonly use "6 parallel connections" per host. That works, but each connection pays its own handshakes, its own slow start, its own memory and socket on both ends, and its own congestion control, which compete with each other.

A proxy has the same problem towards the origin. With HTTP/1.1, 300 requests in flight to the origin need 300 connections.

8. HTTP/2: frames and streams

Covers: notes part 1 §3; part 2 §7, §8, §9 · Sources: RFC 9113 §4.1 (frame header), §4.2 (frame size), §5 (streams), §5.1.1 (odd stream IDs, stream 0), §6 (frame types), §6.4 (RST_STREAM), §6.5.2, §6.8 (GOAWAY), §6.9.2 (initial window 65,535); RFC 7541 (HPACK); curl verbose output

HTTP/2 cuts every request and response into frames. Each frame carries the number of the stream it belongs to. A stream is one request and its response. Frames from many streams can be mixed on one connection, and the receiver sorts them back by stream number. This is multiplexing.

RFC 9113 §5: "A single HTTP/2 connection can contain multiple concurrently open streams, with either endpoint interleaving frames from multiple streams."

The frame header

Every frame starts with the same 9 bytes (RFC 9113 §4.1):

FieldSizeMeaning
Length24 bitspayload size. At most 16,384 bytes unless the receiver allows more
Type8 bitsDATA (0x0), HEADERS (0x1), RST_STREAM (0x3), SETTINGS (0x4), GOAWAY (0x7), WINDOW_UPDATE (0x8), and others
Flags8 bitsfor example END_STREAM (0x1): the sender is done with this stream
Reserved + Stream ID1 + 31 bitswhich stream. 0 means the connection as a whole

Client streams use odd numbers: 1, 3, 5. Server streams use even numbers. Stream 0 is for connection control, such as SETTINGS (§5.1.1). Headers are compressed with HPACK (RFC 7541), so repeated headers such as cookies cost a few bytes after the first request.

Limits and controls

  • Concurrent streams. Each side announces SETTINGS_MAX_CONCURRENT_STREAMS. A request past the limit waits, or the proxy opens another connection.
  • Flow control. Each stream and the connection start with a 65,535-byte window (§6.9.2). The receiver opens it with WINDOW_UPDATE. So a fast stream cannot fill the receiver's memory.
  • Cancel one stream. RST_STREAM ends one stream. "A stream error ... does not affect processing of other streams" (§5.4.2). On HTTP/1.1, cancelling a request means closing the connection.
  • Close politely. GOAWAY tells the peer to start no new streams, while open ones finish. Servers use it before a restart.

9. TCP head-of-line blocking

Covers: notes part 2 §10, §13 · Sources: RFC 9113 §1 ("TCP head-of-line blocking is not addressed"); RFC 9114 §1.1; RFC 9000 §13; RFC 9293 (in-order delivery); Linux nstat counters

HTTP/2 removed blocking between responses, but only at the HTTP level. Underneath, all streams share one TCP byte stream, and TCP hands bytes to HTTP/2 strictly in order. If one TCP segment is lost, every byte after it waits for the resend, even bytes of other streams that arrived fine.

TCP's receiver keeps a number: the next byte it expects. Segments that arrive after a gap go into a buffer. They are not delivered until the missing segment arrives and fills the gap. TCP does not know that the held bytes belong to stream 3 and the lost ones to stream 1. It only sees bytes.

RFC 9113 §1 says so directly: "TCP head-of-line blocking is not addressed by this protocol." RFC 9114 §1.1 describes the effect: "a lost or reordered packet causes all active transactions to experience a stall regardless of whether that transaction was directly impacted by the lost packet."

The loss is recovered in about one round trip if later packets keep coming (the receiver's duplicate ACKs tell the sender), or after the retransmission timer if not. With many streams on one connection, one loss now stalls all of them. With six HTTP/1.1 connections, one loss stalls only one. So on lossy networks such as mobile and busy Wi-Fi, HTTP/2 can do worse than HTTP/1.1 with several connections.

10. QUIC and HTTP/3

Covers: notes part 2 §11, §12, §14 · Sources: RFC 9000 §7, §13 (combined handshake, CRYPTO frames, loss per stream); RFC 9001 §1, §2.1, §4, §5.4 (TLS in QUIC, 1-RTT and 0-RTT, header protection); RFC 9114 §1.2, §3.1, §3.1.1 (HTTP/3, Alt-Svc, fall back to TCP); RFC 9460 (HTTPS DNS record, alpn)

QUIC is a transport protocol that runs on UDP and replaces TCP for HTTP/3. It is not "HTTP over plain UDP". QUIC does its own reliability, resending, congestion control, streams and encryption. HTTP/3 is HTTP mapped onto QUIC streams.

The old stack. HTTP/2 has streams, but TCP below it has one ordered byte stream. TLS is a separate layer with its own handshake.

The new stack. QUIC moves streams into the transport and carries TLS 1.3 inside its own handshake. UDP only carries the packets.

Streams that do not block each other

QUIC knows which stream each byte belongs to. RFC 9000 §13: "When a packet loss occurs, only streams with data in that packet are blocked waiting for a retransmission". RFC 9114 §1.2: "one stream that is blocked or suffers packet loss does not prevent progress on other streams." Each HTTP/3 request uses its own client stream (IDs 0, 4, 8, ...).

One handshake instead of two

RFC 9000 §7: "QUIC relies on a combined cryptographic and transport handshake to minimize connection establishment latency." The TLS 1.3 messages travel in QUIC CRYPTO frames. So the first flight both opens the connection and starts TLS. RFC 9001 §1: "most new connections can be established and secured within a single round trip". TCP + TLS 1.3 needs two. QUIC also has 0-RTT, with the same replay limits as chapter 4.

More is encrypted

In TCP, the headers (ports, sequence numbers, flags) are plain. QUIC encrypts its payload and protects parts of its header too, including the packet number (RFC 9001 §5.4). Middleboxes see less, and cannot freeze the protocol by depending on its fields.

How a browser finds out it can use HTTP/3

A browser starts with no knowledge that the server speaks QUIC. Two ways tell it. A response header: "An HTTP origin can advertise the availability of an equivalent HTTP/3 endpoint via the Alt-Svc HTTP response header field" (RFC 9114 §3.1.1), for example alt-svc: h3=":443". Or a DNS HTTPS record with alpn="h3,h2" (RFC 9460), which arrives before the first connection. Some networks block UDP. RFC 9114 §3.1: then "clients SHOULD attempt to use TCP-based versions of HTTP".

11. Connection migration

Covers: notes part 2 §15 · Sources: RFC 9293 §3.4.1 (connection = pair of sockets); RFC 9000 §5.1 (connection IDs), §8.2 (path validation), §9 (migration, client only, NAT rebinding), §9.5 (new connection ID), §18.2 (disable_active_migration)

A TCP connection is identified by its addresses and ports. When a phone moves from Wi-Fi to 5G, its IP address changes, so to the server its packets belong to no connection. A QUIC connection is identified by a connection ID instead, so it can survive the move. QUIC calls this connection migration.

The server looks up every incoming packet in a table. For TCP, the key is the socket pair: source IP and port, destination IP and port. A new source IP misses the table. The server answers with a reset or drops the packet, and the client must open a new connection: TCP handshake, TLS handshake, and the request again.

For QUIC the key is the connection ID in the packet header. RFC 9000 §5.1: its job is "to ensure that changes in addressing at lower protocol layers (UDP, IP) do not cause packets for a QUIC connection to be delivered to the wrong endpoint." When packets for a known ID come from a new address, the server first checks that the client really is at that address. This is path validation (§8.2). The server sends a PATH_CHALLENGE with random data, and the client must echo it in a PATH_RESPONSE. That stops an attacker from pointing a connection's traffic at a victim's address.

Rules and limits:

  • "Clients are responsible for initiating all migrations" (§9). The server's address stays fixed.
  • On a new path the client switches to a fresh connection ID that the server gave it earlier, so an observer cannot link the two paths (§9.5).
  • A server can send disable_active_migration. Then the client "MUST NOT use a new local address" (§18.2).
  • It also covers a change the client does not notice: NAT rebinding, when a home router gives the flow a new outside port (§9).
  • A load balancer in front of many QUIC servers must route by connection ID. If it hashes on the IP and port, the migrated packets go to a server with no state for them.

12. Anycast, BGP and the PoP

Covers: notes part 2 §16, §17, §18, §19, §20 · Sources: RFC 4271 §9.1.1, §9.1.2, §9.1.2.2 (BGP decision process); RFC 4786 §2, §3.2, §4.1, §4.4.3 (anycast catchments, topological nearness, TCP and route changes); RFC 7094 §1; Cloudflare docs (TCP connections: "shortest Border Gateway Protocol (BGP) path"); Cloudflare Learning Center (What is Anycast, DDoS); RFC 5398 (documentation AS numbers); RFC 4987 §3.6 (SYN cookies)

With anycast, many CDN locations announce the same IP prefix to the Internet. Each network's routers pick one route to that prefix, so each user reaches one location, usually a near one. The protocol that carries those announcements between networks is BGP.

The Internet is made of many separate networks called autonomous systems (AS): ISPs, CDNs, clouds, companies. Each has an AS number. With BGP, each AS tells its neighbours "I can reach this prefix", and passes on the path of AS numbers it came through (the AS_PATH). A CDN announces, say, 203.0.113.0/24 from Karachi, Dubai, Singapore and Frankfurt at once. An ISP in Pakistan then has several routes to the same prefix and must pick one.

How a router picks

RFC 4271 §9.1: first the route with the highest "degree of preference". Inside one network that is the LOCAL_PREF attribute, set by the ISP's own policy, often by cost: a free peering link is preferred over paid transit. Only among routes tied on preference, the tie-break rules apply "in the order specified": first the shortest AS_PATH, then several more.

So "nearest" means best by BGP policy and path, not by kilometres. Cloudflare's docs: traffic goes "to the nearest Cloudflare data center based on the shortest Border Gateway Protocol (BGP) path". RFC 4786 §3.2 warns that "Topological nearness within the routing system does not, in general, correlate to round-trip performance". A user in Karachi can land in Singapore if their ISP's policy prefers that route.

Anycast and TCP

Anycast works well for one-packet protocols like DNS. TCP needs every packet of a connection to reach the same machine. If routes change during a connection, packets start to arrive at another location that has no state for the connection, and it resets. RFC 4786 §4.1: node selection "ought to be stable for substantially longer than the expected transaction time". In practice routes are stable for most connections, and CDNs plan for the rest. Anycast also spreads a DDoS attack: each location takes the attack traffic from its own catchment (RFC 4786 §2: "the topological region of a network within which packets directed at anycast addresses are routed to one particular node").

13. Tiers, the backbone and split connections

Covers: notes part 1 §6, §7, §8, §9, §10; part 2 §21 to §29 · Sources: AWS CloudFront docs (Origin Shield, request collapsing); AWS Global Accelerator docs (How it works); Google Cloud docs (Network Service Tiers); Cloudflare docs (Tiered Cache, Argo Smart Routing); Mathis et al. 1997 and RFC 3649 §5 (throughput ≈ 1.2/√p segments per RTT)

Between the edge and the origin, a large CDN adds cache tiers and carries traffic on its own network. Each hop is a separate connection with its own pool. Splitting one long connection into short ones can make it faster, not slower.

Cache tiers and the origin shield

Every PoP has its own cache. Without tiers, a file that becomes popular causes one miss per PoP, and every miss hits the origin. A regional tier or origin shield sits between the PoPs and the origin. Edges ask the shield, and only the shield asks the origin. AWS: requests that miss in Origin Shield "are consolidated with other requests for the same object, resulting in as few as one request going to your origin". When many users miss on the same file at the same moment, the cache sends one request and makes the rest wait for it. This is request collapsing, and it prevents a cache stampede. The backbone

On the public Internet, a packet from Karachi to Frankfurt crosses several networks, each with its own policy, capacity and congestion. Nobody on the path controls it end to end. A large CDN or cloud takes the traffic onto its own network at the nearest PoP (early ingress) and carries it most of the way on links it controls. Google Cloud describes this as Premium Tier: traffic "enters Google's high-performance network at the PoP closest to the sending system". AWS Global Accelerator takes traffic "onto the AWS global network from the edge location that is closest to your users".

"Private backbone" does not mean private IP addresses such as 10.0.0.0/8. The edge may still connect to https://origin.example.com on a public IP. It means the provider controls the routers and links, so it controls routing, capacity, failover, and loss.

Why two short connections beat one long one

TCP's speed depends on round trip time and loss. A sender can send one window of data per round trip. After a loss it halves the window. The Mathis model puts the average window near 1.2/√p segments for loss rate p (RFC 3649 §5), so throughput ≈ window × segment size / RTT. Long RTT and loss both cut speed, and they multiply.

Split the path and each part improves. The user's handshakes run over a 20 ms leg, not a 150 ms one. Loss on the user's last mile is recovered over 20 ms, not 150 ms. The long leg runs on a warm connection with a grown window, on a network with little loss. And the edge's handshake with the browser does not create a new handshake to the origin, because connection B is already open.
