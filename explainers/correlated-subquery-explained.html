1. The 29 second query

Covers: § the post, § fact-check summary table, § step-by-step 1 (the query pattern). Sources: PostgreSQL 18 docs 4.2.11 Scalar Subqueries, 14.1 Using EXPLAIN. Timings: measured for this page on 2026-10-13.

A correlated subquery is a subquery that reads a column of the outer query. PostgreSQL must run it again for each outer row, because the value of that column changes from row to row.

The notes start with a post. A catalog query on a 30,000 row table took 29 seconds. The author found two problems in the plan: a sequential scan on a join with no index, and a correlated subquery with an aggregate. The author moved the aggregate into a CTE, joined it with LEFT JOIN, and added two indexes. The query then took 0.5 seconds. The author made the two changes together and did not know which one helped.

The post does not show the query. This page uses a query of the same shape. A shop has products, each product has a category, and each product has zero or more reviews. The catalog shows each product with its average rating.

SELECT p.id, p.name, c.category_name,
       (SELECT avg(r.rating)            -- scalar subquery
        FROM reviews r
        WHERE r.product_id = p.id)      -- p.id comes from the outer row
       AS avg_rating
FROM products p
JOIN categories c ON c.id = p.category_id;

A subquery in parentheses that returns one row with one column is a scalar subquery. The docs say that it "can refer to variables from the surrounding query, which will act as constants during any one evaluation of the subquery". The words "any one evaluation" tell you that there are many evaluations.

products3,000 rows on this page

The outer query reads products. Each row is one product.

Each product row gets its category name from categories. This is an ordinary join.

For each row, PostgreSQL puts the row's p.id into the subquery and runs it. 3,000 rows give 3,000 runs.

The output has one average for each product. The answer is correct. Only the cost is wrong.

What the notes claim, and what a real run shows

The notes contain a fact check and some EXPLAIN ANALYZE output. That output was written by a language model. It was not measured. For this page, every plan was run on PostgreSQL 18. Three claims in the notes did not hold.

2. How a correlated subquery runs

Covers: § fact-check 1, § step-by-step 2 (steps 1 and 2). Sources: PostgreSQL 18 docs 14.1.1 EXPLAIN Basics (subplans, hashed subplans, initplans), 4.2.11 Scalar Subqueries; PostgreSQL source src/backend/optimizer/plan/subselect.c.

In a plan, a subquery that PostgreSQL cannot merge into the outer query is a SubPlan. A correlated SubPlan has a parameter, here p.id. The executor sets the parameter from the current outer row and runs the SubPlan from its start. It does this for each outer row.

The subquery cannot run one time before the outer query, because its answer is different for each product. Without help, the only way to find the reviews of product 7 is to read all reviews and keep those with product_id = 7. Then the same for product 8, and so on.

Outer rowproducts: id = 1
↓ p.id = 1
SubPlan 1parameter: p.id
↓
Seq Scan on reviewsreads all 3,000 rows, keeps those with product_id = 1
↓ matching rows
Aggregateavg(rating): one value
↺ next outer row: id = 2
The scan starts again from the first page3,000 outer rows × 3,000 review rows = 9,000,000 rows read

The outer plan gives one product row.

The executor copies p.id into the SubPlan parameter.

With no index on reviews.product_id, the only access method is a sequential scan of the full table. The filter drops all rows of other products.

The aggregate node returns one value. This value goes into the avg_rating column of the output row.

The next outer row has a different p.id. Nothing from the last run can be used again, so the scan repeats. The work is the product of the two row counts.

Why the planner does not fix this for you

The planner can change some subqueries into joins. In the source file subselect.c, the function pull_up_sublinks changes IN (= ANY) and EXISTS subqueries in WHERE into semi joins and anti joins. A scalar subquery in the SELECT list is not in that group. It stays a SubPlan, and you must do the rewrite by hand.

A SubPlan does not always run many times. The docs name two cheaper forms. Each form needs a subquery that does not read outer columns.

3. Read loops in EXPLAIN ANALYZE

Covers: § raw EXPLAIN ANALYZE plans 1 and 2, with their "what to look for" lists. Sources: PostgreSQL 18 docs 14.1.2 EXPLAIN ANALYZE. Plan numbers: one run of PGlite in Node on my machine. In a browser the same engine is about 2 times slower. Yours will vary.

EXPLAIN ANALYZE runs the query and prints, for each plan node, the time it took and the rows it returned. For a node that ran more than one time, the time and the row count are averages for one run. You must multiply by loops to get the total.

The docs say: "the loops value reports the total number of executions of the node, and the actual time and rows values shown are averages per-execution" and "Multiply by the loops value to get the total time actually spent in the node."

In PostgreSQL 18, ANALYZE switches on BUFFERS by default. hit counts pages found in shared buffers. read counts pages that PostgreSQL had to get from the operating system. The notes show read=1200000 in this plan. That cannot be correct for a small table: after the first loop, all 17 pages are in shared buffers, and each later loop is all hits. The lab below shows it.

Times of 0.001 ms have only one useful digit. For very fast nodes, time × loops is a rough number. Use the parent node's time, or Execution Time, to check it.

4. The join was not the problem

Covers: § fact-check 2, § the minimal rewrite of the post, § step-by-step 2 (step 3). Sources: PostgreSQL 18 docs 51.5 Planner/Optimizer (join strategies), Planner Method Configuration, 14.1.2 EXPLAIN ANALYZE (Rows Removed by Join Filter).

A Hash Join reads one table one time and puts its rows into a hash table in memory. Then it reads the other table one time and looks up each row in the hash table. It needs no index.

The post lists "a full table scan on a join" as the first problem. The scan was real: the plan shows Seq Scan on products and Seq Scan on categories. But a sequential scan is the correct access method when the query needs all rows of a table. The cost of a join comes from how many times each table is read. In a Hash Join that number is one.

Seq Scan on categories15 rows, read one time
↓ build
Hashhash table in memory, key = c.id
↑ probe with p.category_id
Seq Scan on products3,000 rows, read one time
↓
Hash Join output3,000 joined rows

The planner makes the smaller table the build side. Here that is categories.

The Hash node puts all 15 rows into a hash table. The plan line shows its size: Memory Usage: 5kB.

The join reads products one time. For each row it computes the hash of category_id and finds the match in the table. One lookup, not a scan.

Total rows read: 15 + 3,000. The join took about 2 ms of the 710 ms in the slow plan.

The post expected the other join method. A Nested Loop with no index reads the full inner table for each outer row. That is the same shape as the SubPlan in chapter 2. The difference is who decides. For a join, the planner compares the methods and takes the cheapest. For the scalar subquery, there is no choice: it must run for each row.

Join with no indexCorrelated scalar subquery with no index
Planner can pick a one-pass methodyes: Hash Join or Merge Joinno
Times the inner table is read1one for each outer row
Cost of the missing indexnone hereall of the 29 seconds
The missing index did matter in the post, but because of the subquery, not because of the join. The post says two join columns had no index. It is possible that one of them was the column the subquery filters on.

5. The rewrite: aggregate once, then join

Covers: § fact-check 3 with the note on CTEs and derived tables, § step-by-step 3 (steps A and B). Sources: PostgreSQL 18 docs 7.8.3 Common Table Expression Materialization, 9.21 Aggregate Functions, 7.2.1.1 Joined Tables; PostgreSQL 12 release notes (CTE inlining).

The rewrite computes the average for all products in one pass over reviews, with GROUP BY product_id. Then it joins that result to products. No part of the plan runs more than one time.

SELECT p.id, p.name, c.category_name, pr.avg_rating
FROM products p
JOIN categories c ON c.id = p.category_id
LEFT JOIN (SELECT product_id, avg(rating) AS avg_rating
           FROM reviews
           GROUP BY product_id) pr ON pr.product_id = p.id;

The subquery in FROM does not read an outer column. So PostgreSQL can run it one time. For the grouping, the planner picks a HashAggregate: a hash table with one entry for each product_id. Each entry holds the running state of the aggregate. For avg that is a sum and a count.

Seq Scan on reviews3,000 rows, loops=1
↓ each row
HashAggregateGroup Key: product_id. 2,700 groups, each with sum and count
↓ 2,700 rows
Hashhash table, key = product_id
↑ probe with p.id
products joined to categories3,000 rows, from the Hash Join of chapter 4
↓
Hash Left Join output3,000 rows. 300 products with no reviews get NULL

One sequential scan of reviews. This is the only time the table is read.

Each review row goes to the entry of its product_id and adds to the sum and the count. At the end, each entry gives one average.

The 2,700 averages go into a second hash table, for the join.

Each product row looks up its id in that table. One lookup for each row.

A LEFT JOIN keeps a product with no match and fills the columns of the other side with NULL. Total rows read: 3,000 + 3,000 + 15, not 9,000,000.

Two ways to get a different answer

The rewrite must return the same rows as the original. Two details can change the result.

The join type. The scalar subquery returns a value for each product, also for a product with no reviews. The docs say: "if, during a particular execution, the subquery returns no rows, there is no error; the scalar result is taken to be null." Only a LEFT JOIN keeps those products. An inner JOIN removes them from the catalog.

The aggregate. The docs say about aggregates: "except for count, these functions return a null value when no rows are selected." So a correlated count(*) returns 0 for a product with no reviews. After the rewrite there is no group for that product, and the LEFT JOIN gives NULL. For count you must write COALESCE(pr.n, 0). For avg, NULL is the same in both forms.

CTE or subquery in FROM

The post used a CTE (WITH pr AS (…)). In current PostgreSQL the plan is the same. The docs say that a WITH query that is non-recursive, has no side effects and is referenced one time "can be folded into the parent query, allowing joint optimization of the two query levels".

FormBehaviour
Subquery in FROMAlways planned together with the outer query.
CTE, referenced one time, PostgreSQL 12 and laterFolded into the outer query. Same plan as the subquery in FROM.
CTE, PostgreSQL 11 and earlier, or AS MATERIALIZED, or referenced two or more timesComputed separately and stored. Filters of the outer query cannot go into it.

For the full catalog this difference does not matter, because the query needs all groups. It matters with a filter. Chapter 9 uses it.

6. The index without the rewrite

Covers: § EXPLAIN ANALYZE for the correlated subquery with an index on reviews(product_id), all three parts. Sources: PostgreSQL 18 docs 14.1.2 EXPLAIN ANALYZE (Index Searches), 11 Indexes, pageinspect (bt_metap). Timings: measured, will vary.

An index on reviews (product_id) does not change how many times the subquery runs. It changes what one run costs. Each run goes down a B-tree to the matching rows and does not read the other rows.

The plan keeps its shape. The SubPlan still shows loops=3000. Inside it, Seq Scan on reviews becomes Index Scan using reviews_product_id. The line Rows Removed by Filter: 2999 is gone, because the scan does not touch those rows.

SubPlan 1p.id = 7
↓
B-tree root pagefinds which leaf page holds key 7
↓
B-tree leaf pageentries for product_id = 7, each with a row address
↓
Heap page of reviewsthe row, to read rating

The SubPlan starts one index search for the current p.id.

The search starts at the root page. With 3,000 rows this tree has two levels: one root and the leaf pages below it.

The leaf page holds the entries for the key. Each entry points to a row in the table.

The scan gets the row from the table to read rating. That is 3 pages for one run, and 3 × 3,000 = 9,000 buffers in the plan, against 51,000 before.

Measured results. Yours will vary.

Correlated subquery3,000 rows, PGlite in my browser30,000 rows, PostgreSQL 18.6 in Docker
no index1,837 ms, 51,000 buffers22,041 ms, 4,890,193 buffers
index on reviews (product_id)33 ms, 9,000 buffers61 ms, 90,193 buffers

The notes give 415 ms for the indexed case at 30,000 rows. The real server needed 61 ms. The conclusion in that part of the notes is still correct: the index alone takes the query from tens of seconds to a small part of one second. Chapter 8 puts this next to the rewrite.

The planner uses the index only when the condition compares the indexed column itself. An expression on the column, such as r.product_id + 0 = p.id or a cast to a different type, makes the index unusable for that condition. The plan goes back to 3,000 sequential scans. Preset 5 shows it.
Lab: add the index, keep the subquery

Run the presets in order. In preset 2, look for Index Scan, Index Searches: 3000 and loops=3000, and compare Buffers with 51,000. Preset 3 reads the B-tree metapage: level 1 means the root is one step above the leaf pages. Preset 5 breaks it with an expression on the column.

Preset 4 answers a question from the notes. The rewrite reads all of reviews, so the planner keeps the sequential scan and does not use the index. For a query that needs each row of a table, an index on that table gives nothing.

7. Index Only Scan against one pass

Covers: § why an Index Only Scan on (product_id, rating) is slower than a HashAggregate, parts 1 to 5 and the mechanical comparison table. Sources: PostgreSQL 18 docs 11.9 Index-Only Scans and Covering Indexes, Visibility Map, pg_visibility, 51.6 Executor. Timings: measured, will vary.

An Index Only Scan answers a query from the index and does not read the table. It is possible when the index holds each column the query needs, and when the visibility map says that the table page has no rows that are hidden from some transaction.

The subquery needs two columns of reviews: product_id to search and rating to average. An index on (product_id, rating) holds both. Such an index is a covering index for this query. Each run of the SubPlan can now stop at the leaf page.

There is one more check. An index entry does not say which transactions can see the row. The docs say: "Visibility information is not stored in index entries, only in heap entries". So PostgreSQL keeps a visibility map with one bit for each table page. The bit is set when all rows on the page are visible to all transactions. VACUUM sets it. A write to the page clears it.

Index leaf entry(product_id = 7, rating = 4) → row address on heap page 3
↓
Visibility mapbit for heap page 3
↓ bit set
Return rating from the indexno table read
↓ bit not set
Heap fetchread the table page to check the row

The search finds the entry. The entry holds both columns the query needs.

Before it uses the entry, the scan reads the visibility map bit of the table page that the row is on.

If the bit is set, the row is visible. The scan returns rating from the index entry. The plan shows Heap Fetches: 0.

If the bit is not set, the scan must read the table row. The docs: "no performance advantage is gained over a standard index scan". The plan counts each such read in Heap Fetches.

Why it is still more work than one pass

With the covering index, the subquery form is fast. It is still not as fast as the rewrite for the full catalog. The notes give five reasons. Two of them show in a real plan, one has a source, and two have no evidence here.

Reason in the notesStatus
The SubPlan starts 30,000 times. The rewrite starts each node one time.Seen: loops=30000 and Index Searches: 30000, against loops=1.
Each run goes down the tree again. The pass reads each page one time.Seen: 60,194 buffers against 356 buffers at 30,000 rows.
Each index entry needs a visibility map check.Sourced (docs 11.9). The docs add that the map is very small and "remains cached in memory all the time" in most cases.
Buffer pin and unpin operations cost time.Not measured here. The buffer counts above are the nearest evidence.
CPU cache misses, and "vectorized" loops in the HashAggregate.No source. PostgreSQL's executor is not vectorized: the docs say each plan node "must deliver one more row" each time it is called.

The size of the difference in the notes is too large. Measured at 30,000 rows on PostgreSQL 18.6: 54 ms for the subquery with the covering index, 31 ms for the rewrite. The notes say 200 to 450 ms against 15 to 45 ms.

8. Measure the two changes apart

Covers: § fact-check 4, § step-by-step 4 (what the indexes contributed), § the takeaway table. Sources: PostgreSQL 18 docs 14.1.2 EXPLAIN ANALYZE. All timings: PostgreSQL 18.6 in Docker and PGlite 18.3 on my machine, 2026-10-13. Yours will vary.

The post made two changes and measured one time. To know what each change did, run all four cases: old query or new query, with the index or without it.

The author guessed that the rewrite did the work. The first answer in the notes agrees: "virtually all of the 28.5 seconds came from the rewrite", and the indexes "shaved off the remaining milliseconds". A later answer in the same notes says the opposite: the index alone was enough. Only one of these can be correct, and a measurement decides it.

Read the table by row and by column.

  • The rewrite alone: 22,041 ms to 31 ms.
  • The index alone: 22,041 ms to 61 ms.
  • Each change alone removes more than 99% of the time. Each one removes the cause, which is 30,000 full scans of reviews. The rewrite makes it one scan. The index makes each of the 30,000 runs read 3 pages and not 163.
  • When the rewrite is in, the index adds nothing for this query. When the index is in, the rewrite makes the query 2 times as fast.
So the question "how much was the rewrite and how much was the indexes" has no single answer. The two changes fix the same problem, and the second one applied finds almost nothing left. The correct statement for the post is: "Either change alone would have brought it under 0.1 seconds on this data. I did not measure them apart."

The slow case took 22 seconds here and 29 seconds in the post. The same order of size on different hardware, with 900 million rows read in both. That supports the post's diagnosis of the subquery.

9. When the correlated subquery is the correct tool

Covers: § step-by-step 4 ("where the indexes do help"), § the last line of the notes about a needle and a haystack. Sources: PostgreSQL 18 docs 7.2.1.5 LATERAL Subqueries, 7.8.3 Common Table Expression Materialization, 14.1 Using EXPLAIN. Timings: measured in PGlite, will vary.

The rewrite computes the aggregate for all products. That is correct when the query shows all products. When the query shows only a few, the rewrite can compute thousands of averages and use one. A correlated subquery with an index computes only the averages that the output needs.

The rule is to compare two numbers: the outer rows that stay after the filter, and the rows of the table inside the subquery.

QueryCorrelated subquery + indexAggregate once, then join
Full catalog, 3,000 products3,000 index searchesone pass. Faster.
WHERE p.id = 71 index searchalso 1 index search. The planner moves the filter into the grouped subquery.
WHERE p.name = 'product 7'1 index search. Faster.reads all 3,000 reviews, makes 2,700 groups, uses 1
ORDER BY p.id LIMIT 20 (one page)20 runs. The subquery runs only for rows in the output.reads all 3,000 reviews

The second row needs an explanation. The filter p.id = 7 is on the join column. The join condition says pr.product_id = p.id, so the planner knows that product_id = 7 also, and it puts that filter inside the grouped subquery. A filter on a different column, such as name, gives the planner no such value. The grouped subquery has no way to know which products the outer query keeps.

A CTE that is materialized stops the filter in each case. This is the "optimization fence" that the notes mention for PostgreSQL 11 and earlier. You get the same behaviour in current versions with AS MATERIALIZED.

LATERAL: a correlated subquery in FROM

A scalar subquery returns one column. When you need two or more values for each outer row, for example the average and the count, use LEFT JOIN LATERAL (…) ON true. A LATERAL subquery in FROM can read columns of the tables before it. The docs say that it is evaluated for each row of those tables. So it has the same cost model as the correlated subquery: one run for each outer row, and it needs the index.

Lab: few outer rows

That is the break case for the rewrite. Preset 4 filters on id: find product_id = 7 inside the grouped part of the plan. Preset 5 adds MATERIALIZED and the filter stays outside.

On a small table the slow form is not visible. At 300 products and 300 reviews it reads 90,000 rows and takes a few milliseconds. The cost grows with the product of the two tables, so 10 times the data gives 100 times the work. Test with the row counts that production will have.
